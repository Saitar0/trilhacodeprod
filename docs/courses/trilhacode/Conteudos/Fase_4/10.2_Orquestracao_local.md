## Objetivo
Descrever, iniciar e diagnosticar um ambiente local com múltiplos serviços usando Docker Compose, preservando dados e configurando conexões entre serviços com segurança adequada ao contexto.

## Teoria

### 1. Descreva a aplicação como serviços
Compose usa um arquivo declarativo, normalmente `compose.yaml), para descrever serviços, imagens ou builds, portas, variáveis, redes, volumes e dependências. Cada serviço define uma função da aplicação, como API, PostgreSQL, Redis ou MongoDB. O arquivo pode ser revisado e versionado junto ao projeto para que outra pessoa recrie um ambiente semelhante.

Um serviço não precisa corresponder a uma máquina. Compose cria containers para executar os serviços e recursos de rede/armazenamento necessários. A chave `services` organiza as definições; os nomes dos serviços funcionam também como nomes de descoberta de rede.

Compose pode usar uma imagem publicada com `image` ou construir a partir de um Dockerfile com `build`. Se a configuração muda, `docker compose up` reconcilia os containers conforme necessário. O comando `docker compose config` combina e valida a configuração e ajuda a inspecionar o modelo que será aplicado.

**Erro comum:** tratar o arquivo como uma sequência de comandos imperativos; ele descreve o estado desejado dos serviços.

### 2. Configure portas, rede e descoberta de serviços
Por padrão, Compose cria uma rede para o projeto e conecta nela os serviços. Containers da mesma rede resolvem uns aos outros pelo nome do serviço. Assim, uma API dentro do Compose conecta-se a PostgreSQL em `db:5432), Redis em `cache:6379) e MongoDB em `documentdb:27017). Use portas internas entre serviços; não use o IP atual do container, pois ele pode mudar quando for recriado.

A seção `ports` publica uma porta para clientes fora da rede dos serviços, como ferramentas executadas no host. A forma `127.0.0.1:5432:5432` restringe a publicação à interface local do host; `5432:5432` pode expor a porta em outras interfaces conforme a configuração do ambiente. Não publique um serviço para o host se o uso previsto não precisar dele.

**Erro comum:** configurar a API com `localhost:5432); dentro do container, localhost aponta para a própria API. Para acessar o banco pelo host, use a porta publicada e localhost no cliente do host.

### 3. Preserve dados e trate configurações com cuidado
Volumes nomeados mantêm dados além da recriação dos containers. Declare-os no nível superior e associe cada volume ao caminho de dados adequado à imagem. `docker compose down` remove containers e rede do projeto, mas preserva volumes nomeados por padrão. `docker compose down --volumes` remove também os volumes gerenciados pelo projeto e pode apagar os dados locais.

Variáveis de ambiente permitem parametrizar nomes de banco, portas e configurações. Um arquivo `.env` pode alimentar interpolação do Compose, mas não deve ser tratado automaticamente como cofre de segredos: não versione credenciais reais. Para recursos sensíveis, use mecanismo de secrets compatível com o ambiente e conceda acesso somente ao serviço que precisa deles. Valores de exemplo neste curso são locais e descartáveis.

Exemplo didático de desenvolvimento para PostgreSQL 18+, Redis e MongoDB:

```yaml
services:
  db:
    image: postgres:18
    environment:
      POSTGRES_DB: estudo
      POSTGRES_USER: estudo
      POSTGRES_PASSWORD: dev-only
    ports:
      - "127.0.0.1:5432:5432"
    volumes:
      - postgres_data:/var/lib/postgresql
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U $${POSTGRES_USER} -d $${POSTGRES_DB}"]
      interval: 5s
      timeout: 3s
      retries: 10
      start_period: 10s

  cache:
    image: redis:7-alpine
    ports:
      - "127.0.0.1:6379:6379"
    volumes:
      - redis_data:/data
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 5s
      timeout: 3s
      retries: 10

  documentdb:
    image: mongo:8
    profiles: ["document"]
    ports:
      - "127.0.0.1:27017:27017"
    volumes:
      - mongo_data:/data/db

volumes:
  postgres_data:
  redis_data:
  mongo_data:
```

Este exemplo usa credencial descartável, sem autenticação configurada para MongoDB, e destina-se somente a uma máquina de estudo. O serviço MongoDB só entra no modelo quando o perfil `document` é ativado, por exemplo com `docker compose --profile document up`. Se a aplicação não usa algum serviço, não o mantenha ativo sem necessidade. Para outras versões de PostgreSQL, confira o caminho de volume documentado pela tag.

**Erro comum:** acreditar que publicar portas ou colocar uma senha de exemplo no YAML torna a configuração apropriada para produção.

### 4. Separe ordem de inicialização e prontidão
`depends_on` controla a ordem de criação/inicialização, mas sua forma curta não espera que a aplicação dependente esteja pronta para aceitar conexões. Um serviço pode estar iniciado e ainda estar inicializando o banco. Configure um healthcheck para verificar uma condição útil e, quando apropriado, use a condição `service_healthy` na dependência.

```yaml
  api:
    build: .
    environment:
      DATABASE_HOST: db
      DATABASE_PORT: "5432"
    depends_on:
      db:
        condition: service_healthy
```

Mesmo com healthcheck, a aplicação deve tratar interrupções e reconectar: o banco pode reiniciar depois da inicialização da API, e uma atualização pode recriar um container. Uma verificação de saúde indica uma condição definida; não prova que toda consulta futura terá sucesso.

**Erro comum:** usar `depends_on` curto como garantia de que o banco já aceita consultas.

### 5. Opere e diagnostique o projeto
Comandos usuais:

```sh
docker compose config
docker compose up --build -d
docker compose ps
docker compose logs -f db
docker compose exec db psql -U estudo -d estudo
docker compose down
```

`up --build` constrói serviços que têm configuração de build e inicia o conjunto; `-d` executa em segundo plano. `ps` mostra estado e saúde reportada; `logs` ajuda a localizar falhas de inicialização; `exec` executa um comando em um container em execução. Antes de apagar dados, identifique o projeto, os volumes associados e o conteúdo que será removido.

Compose organiza ambientes locais e cenários simples. Ele não oferece automaticamente alta disponibilidade, backups, gestão completa de segredos, monitoramento ou estratégia de produção. Documente pré-requisitos, portas, serviços opcionais, dados descartáveis e o procedimento de limpeza.

**Checklist de revisão:**
- O arquivo descreve apenas serviços necessários ao cenário?
- Os serviços usam nomes DNS e portas internas para comunicação entre containers?
- Só as portas necessárias estão publicadas para o host?
- Os volumes têm caminho correto e política de descarte clara?
- Dependências estão prontas antes de a aplicação tentar usá-las?
- Logs e estado permitem diagnosticar falhas?
- Nenhum segredo real está versionado?

## Resumo
- Compose declara serviços e recursos para recriar um ambiente local.
- A rede padrão permite descobrir serviços pelo nome; portas internas servem à comunicação entre containers.
- Volumes nomeados persistem com `down`; `down --volumes` pode apagá-los.
- `depends_on` ordena a inicialização; healthcheck pode representar prontidão, e a aplicação ainda deve tolerar reconexões.
- Use portas e credenciais de acordo com o contexto e mantenha segredos reais fora do repositório.

## Quiz
1. Uma API em Compose deve conectar-se a PostgreSQL pelo endereço `localhost:5432) ou `db:5432)? **Resposta:** `db:5432), se `db) é o nome do serviço. **Feedback:** localhost dentro da API aponta para o próprio container.
2. O que `docker compose down` faz com volumes nomeados por padrão? **Resposta:** preserva-os. **Feedback:** `down --volumes` também remove os volumes gerenciados pelo projeto e pode apagar dados.
3. `depends_on: [db]` garante que o PostgreSQL aceita consultas quando a API inicia? **Resposta:** não. **Feedback:** a forma curta ordena a inicialização, mas não espera o estado saudável.
4. Por que publicar `127.0.0.1:5432:5432) pode ser preferível a `5432:5432) em um exercício local? **Resposta:** restringe o acesso publicado à interface local do host. **Feedback:** o formato sem endereço explícito pode expor a porta em outras interfaces, conforme o ambiente.
5. Uma configuração `.env) local foi adicionada ao projeto. Isso a torna segura para versionar? **Resposta:** não. **Feedback:** valores locais podem conter credenciais; não versione segredos reais e use mecanismo adequado ao ambiente.

## Práticas

### Atividade 1 — Monte o ambiente mínimo
Crie um `compose.yaml) para PostgreSQL e Redis destinados a desenvolvimento local. Use nomes de serviço claros, volumes nomeados, portas acessíveis apenas pelo host local e valores de credenciais descartáveis.

**Tarefas**
1. Declare os dois serviços e associe os volumes.
2. Publique as portas locais necessárias para ferramentas do host.
3. Inclua um healthcheck adequado para cada serviço.
4. Explique como a aplicação em container acessará cada serviço.

**Dica:** use os nomes DNS `db) e `cache); para PostgreSQL 18+, confirme o caminho de dados da imagem.

**Solução de referência:** declare `db) com imagem PostgreSQL 18+, volume em `/var/lib/postgresql), porta `127.0.0.1:5432:5432) e healthcheck com `pg_isready). Declare `cache) com Redis, volume em `/data), publicação local opcional e healthcheck com `redis-cli ping). A API na mesma rede usa `db:5432) e `cache:6379); clientes do host usam as portas publicadas. Credenciais são descartáveis e não devem ser usadas fora do exercício.

**Rubrica (0–5):** 1 ponto por serviço corretamente declarado; 1 por volumes nos caminhos adequados; 1 por publicação restrita e consciente; 1 por healthchecks apropriados; 1 por explicar endereços internos versus host.

### Atividade 2 — Acrescente um serviço documental opcional
O projeto pode usar MongoDB em algumas atividades, mas nem todos os exercícios precisam iniciá-lo. Ajuste o Compose para permitir ativação opcional do serviço e preservar seus dados.

**Tarefas**
1. Adicione um serviço MongoDB com volume nomeado em seu caminho persistente.
2. Configure um perfil para ativá-lo apenas quando necessário.
3. Explique como iniciar o ambiente com e sem o perfil.
4. Documente portas, autenticação e descarte de dados do exemplo.

**Dica:** serviço com perfil não é iniciado no conjunto padrão quando o perfil não está ativo.

**Solução de referência:** declare serviço `documentdb) com imagem de MongoDB escolhida e volume em `/data/db), depois associe `profiles: ["document"]`. Sem ativar o perfil, o conjunto padrão não inicia o serviço; com `docker compose --profile document up), o serviço fica disponível na rede do projeto pelo nome `documentdb) e porta interna 27017. Se uma porta for necessária a um cliente no host, publique-a apenas na interface local. Para material introdutório, deixe explícito que exemplo sem autenticação é local e descartável; não o exponha na rede. `down) conserva o volume; `down --volumes) pode apagar os dados.

**Rubrica (0–4):** 1 ponto por persistência correta; 1 por perfil e ativação; 1 por indicar acesso interno/host; 1 por documentar limites de autenticação e descarte.

### Atividade 3 — Faça API esperar pelo banco e investigue falhas
Adicione um serviço `api) construído pelo Dockerfile do projeto. A API depende do banco e deve receber o endereço interno do serviço. Simule conceitualmente falhas de configuração, inicialização lenta e credencial incorreta e descreva o diagnóstico.

**Tarefas**
1. Configure `build), variáveis de conexão e dependência do serviço `db).
2. Faça a dependência aguardar um healthcheck válido.
3. Explique por que a API ainda deve lidar com desconexões após iniciar.
4. Descreva como usar `config), `ps), `logs) e `exec) para localizar a falha.
5. Liste quais dados são preservados após `down) e o que `down --volumes) remove.

**Dica:** diferencie “container iniciou”, “healthcheck passou” e “aplicação conseguiu executar sua consulta”.

**Solução de referência:** configure a API com `DATABASE_HOST=db), `DATABASE_PORT=5432) e dependência `db: condition: service_healthy), após definir o healthcheck do banco. A API ainda precisa repetir/reabrir conexões diante de falhas ocorridas depois. Use `docker compose config) para resolver/inspecionar configuração, `ps) para estados e saúde, `logs api) e `logs db) para erros de inicialização e credenciais, e `exec) para inspecionar o container em execução. `down) remove containers e rede, mantendo volumes nomeados; `down --volumes) remove também os volumes gerenciados e seus dados.

**Rubrica (0–5):** 1 ponto por build e endereço interno; 1 por healthcheck/dependência saudável; 1 por explicar necessidade de reconexão; 1 por escolher comandos de diagnóstico; 1 por explicar o efeito de down e down --volumes.

## Critério de conclusão
Você concluiu quando outra pessoa consegue iniciar e diagnosticar os serviços com Compose, conectar componentes pelo nome, preservar dados intencionalmente e identificar com clareza quando uma operação descartará volumes.
