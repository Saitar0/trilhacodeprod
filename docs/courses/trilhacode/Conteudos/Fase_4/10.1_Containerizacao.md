# 10.1 — Containerização

- key: 10.1
- tipo: solo
- carater: obrigatorio
- profundidade: alta
- estimativa_minutos: 180
- tags: [#infra, #ferramentas]
- status: rascunho

## Objetivo
Construir uma imagem e executar containers compreendendo build, isolamento, armazenamento, portas, redes e ciclo de vida.

## Teoria

### 1. Diferencie imagem, container e processo
Imagem é um artefato construído em camadas que reúne arquivos e metadados para iniciar uma aplicação. Container é uma instância em execução criada a partir da imagem, com configuração própria de processo, rede e armazenamento. Ele compartilha o kernel do sistema hospedeiro e não é uma máquina virtual completa.

A imagem pode ser referenciada por tag, como `postgres:18`, ou por digest. Tags são nomes convenientes e podem apontar para conteúdo atualizado; um digest identifica um conteúdo específico. Para aprender, tags explícitas ajudam a reconhecer a versão principal. Para builds que precisam de repetibilidade rigorosa, registre e revise o digest de forma deliberada.

O container tem uma camada gravável própria. Arquivos criados ali podem desaparecer quando ele é removido. Não trate essa camada como armazenamento persistente.

**Erro comum:** supor que remover e recriar um container preserva tudo o que foi gravado dentro dele.

### 2. Construa imagens com contexto controlado
O Dockerfile descreve como montar a imagem: imagem base, diretório de trabalho, dependências, arquivos copiados e comando de inicialização. O contexto é o conjunto de arquivos disponibilizado ao builder; o argumento final do comando de build costuma ser `.`, o diretório atual. COPY só alcança arquivos presentes nesse contexto.

Exemplo de aplicação Node.js:

```dockerfile
FROM node:22-alpine
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
CMD ["node", "consulta.js"]
```

Esse exemplo exige `package.json`, `package-lock.json` e `consulta.js` dentro do contexto. Copiar primeiro os arquivos de dependências permite aproveitar o cache de `npm ci` quando apenas o código da aplicação muda. `npm ci` é apropriado quando o projeto mantém um lockfile coerente com package.json.

Use `.dockerignore` para excluir arquivos que não precisam ser enviados ao builder, como `node_modules`, `.git`, arquivos locais de ambiente e artefatos temporários. Segredos não devem ser copiados para a imagem nem enviados no contexto. A imagem precisa receber configuração em tempo de execução por um mecanismo adequado ao ambiente.

**Erro comum:** executar o build na pasta errada ou enviar o repositório inteiro, inclusive credenciais e arquivos locais.

### 3. Execute e inspecione o ciclo de vida
`docker build -t consulta:dev .` constrói uma imagem com nome e tag. `docker run` cria e inicia um container. `docker ps` lista os ativos; `docker ps -a` inclui os parados; `docker logs` mostra a saída; `docker inspect` revela configuração; `docker stop` encerra; `docker rm` remove o container. A imagem continua existindo até ser removida separadamente.

Um container normalmente executa um processo principal. Se esse processo termina, o container deixa de estar em execução. Para observar o resultado, diferencie saída do processo, estado atual do container e existência da imagem. Opções como `--rm` removem o container ao terminar, mas não removem automaticamente a imagem nem volumes nomeados.

**Erro comum:** confundir um container parado com uma imagem removida ou com dados apagados.

### 4. Publique portas e escolha armazenamento
Portas internas não ficam automaticamente acessíveis no host. `-p 127.0.0.1:5432:5432` publica a porta 5432 do container apenas na interface local do host; `-p 5432:5432` costuma publicar em todas as interfaces do host, conforme o ambiente. A instrução EXPOSE documenta uma porta pretendida, mas não publica a porta por si só.

Volumes nomeados persistem fora do ciclo de vida do container. Bind mounts conectam um caminho do host ao container e são úteis em desenvolvimento, mas dependem da estrutura e permissões locais. Remover o container não é o mesmo que remover o volume; apagar o volume pode destruir os dados. Persistência também não é backup: um backup precisa de cópia recuperável independente e processo de restauração.

Exemplo para PostgreSQL 18 ou superior na imagem oficial:

```sh
docker volume create estudo_pg
docker run -d --name estudo-db \
  -e POSTGRES_PASSWORD=local-only \
  -p 127.0.0.1:5432:5432 \
  -v estudo_pg:/var/lib/postgresql \
  postgres:18
```

A imagem oficial do PostgreSQL 18 mudou o ponto de montagem recomendado para `/var/lib/postgresql`; em versões 17 e anteriores, a documentação da imagem indica `/var/lib/postgresql/data`. Confira a documentação da tag usada antes de reutilizar o comando. `local-only` é uma senha descartável para estudo, não uma credencial para produção.

**Erro comum:** montar o volume no caminho errado para a versão da imagem ou presumir que um volume equivale a backup.

### 5. Conecte containers por uma rede
Uma rede bridge criada pelo usuário permite que containers conectados a ela se encontrem pelo nome do container e se comuniquem nas portas internas. Isso evita configurar a aplicação para usar um IP que pode mudar. A porta publicada no host serve para clientes no host; containers da mesma rede podem usar a porta interna do serviço.

```sh
docker network create estudo-net
docker run -d --name estudo-db --network estudo-net \
  -e POSTGRES_PASSWORD=local-only \
  -e POSTGRES_DB=estudo \
  -v estudo_pg:/var/lib/postgresql \
  postgres:18
```

Uma aplicação na mesma rede pode usar host `estudo-db` e porta `5432`. Uma aplicação executada diretamente no host geralmente usa `localhost` e a porta publicada. Credenciais e portas devem ser configuradas para o contexto certo.

Containerização melhora a repetibilidade do ambiente, mas não garante segurança, alta disponibilidade ou recuperação de dados. Restrinja portas, evite segredos na imagem, use imagens apropriadas e mantenha backup separado. A unidade 10.2 aprofunda a execução coordenada com Compose.

**Erro comum:** usar `localhost` dentro do container da aplicação esperando alcançar outro container; nesse contexto, localhost aponta para o próprio container.

## Resumo
- Imagem é o artefato; container é uma instância que executa processos com configuração própria.
- Build depende de um contexto; Dockerfile e .dockerignore controlam o que entra na imagem.
- A camada gravável do container não substitui volume persistente.
- Publicar uma porta conecta o host ao container; uma rede de usuário conecta containers pelo nome.
- Volume não é backup, e versão/caminho de dados precisam corresponder à imagem usada.

## Quiz
1. O que é removido ao executar `docker rm` em um container que usa volume nomeado? **Resposta:** o container; o volume nomeado permanece, salvo remoção explícita. **Feedback:** dados gravados apenas na camada do container podem se perder.
2. O que o `.` representa em `docker build -t app .`? **Resposta:** o diretório atual usado como contexto de build. **Feedback:** arquivos fora do contexto não ficam disponíveis para COPY.
3. A instrução EXPOSE publica a porta no host? **Resposta:** não; ela documenta a porta pretendida. **Feedback:** use `-p` em `docker run` para publicar.
4. Dois containers na mesma rede bridge criada pelo usuário devem conectar-se ao PostgreSQL usando qual host e porta? **Resposta:** nome do container do banco e porta interna 5432, por exemplo `estudo-db:5432`. **Feedback:** localhost dentro da aplicação se refere ao próprio container.
5. Um volume nomeado garante que os dados estejam protegidos contra perda? **Resposta:** não; ele mantém os dados além do ciclo de vida do container, mas ainda exige backup e teste de restauração. **Feedback:** armazenamento persistente e backup resolvem necessidades diferentes.

## Práticas

### Atividade 1 — Leia e corrija um Dockerfile
Considere um projeto Node.js com package.json, package-lock.json, consulta.js e node_modules local. A imagem deve executar consulta.js.

**Tarefas**
1. Escreva um Dockerfile que instale dependências usando o lockfile.
2. Crie um .dockerignore que exclua node_modules, .git, .env e arquivos temporários.
3. Explique qual pasta será o contexto e por que COPY não alcança arquivos fora dela.
4. Indique uma mudança na ordem de COPY que ajuda a reutilizar cache de dependências.

**Dica:** copie manifestos e lockfile antes do código da aplicação.

**Solução de referência:**
```dockerfile
FROM node:22-alpine
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
CMD ["node", "consulta.js"]
```
Exemplo de .dockerignore:
```
node_modules
.git
.env
*.log
```
Construa na raiz do projeto com `docker build -t consulta:dev .`. O ponto indica que a raiz do projeto é o contexto. Manter os manifestos antes do restante do código evita reinstalar dependências quando só o código muda.

**Rubrica (0–4):** 1 ponto por instalação coerente com lockfile; 1 por cópia ordenada para cache; 1 por excluir artefatos e segredo local; 1 por explicar contexto e limitação de COPY.

### Atividade 2 — Persista e investigue um PostgreSQL
Inicie PostgreSQL 18 com um volume nomeado, crie uma tabela e um registro, remova o container e recrie outro usando o mesmo volume. Não apague o volume nesta atividade.

**Tarefas**
1. Crie e nomeie o volume.
2. Execute a imagem usando o ponto de montagem adequado à versão.
3. Explique como verificar os dados após recriar o container.
4. Explique o que aconteceria com `docker volume rm estudo_pg`.

**Dica:** documente o nome do volume e consulte a documentação da imagem oficial para a versão escolhida.

**Solução de referência:** crie o volume `estudo_pg`, monte-o em `/var/lib/postgresql` para a imagem oficial PostgreSQL 18 ou superior, e use `docker stop` e `docker rm` para recriar o container mantendo o mesmo volume. Conecte-se novamente e consulte a tabela. Remover o volume apaga o armazenamento persistente associado. Para versões 17 ou anteriores, confirme o ponto de montagem documentado para aquela tag. Use uma senha descartável, mantenha o serviço restrito ao host de estudo e não confunda o exercício com backup.

**Rubrica (0–4):** 1 ponto por montar o volume; 1 por escolher o caminho conforme a versão; 1 por demonstrar persistência após recriação; 1 por explicar o efeito destrutivo de remover o volume e a ausência de backup.

### Atividade 3 — Conecte aplicação e banco em rede
Considere uma aplicação Node.js containerizada e um container PostgreSQL. A aplicação roda em container separado e precisa consultar o banco. Não use Compose nesta atividade.

**Tarefas**
1. Crie uma rede bridge de usuário e conecte os dois containers.
2. Configure a aplicação para usar o nome do container do banco e a porta interna.
3. Diferencie a conexão da aplicação daquela feita por um cliente executado no host.
4. Explique como diagnosticar falhas consultando estado, logs e configuração de rede.

**Dica:** teste primeiro se ambos estão na mesma rede; não suponha que localhost tenha o mesmo significado dentro e fora de um container.

**Solução de referência:** crie a rede `estudo-net`; conecte o banco e a aplicação com `--network estudo-net`. Configure a aplicação com host `estudo-db` e porta 5432. Um cliente no host usa uma porta publicada, por exemplo localhost:5432; um container na mesma rede usa o nome do banco e a porta interna. Investigue com `docker ps -a`, `docker logs`, `docker inspect` e a inspeção da rede para confirmar nomes, status e associação.

**Rubrica (0–5):** 1 ponto por criar e usar a rede; 1 por usar DNS do container; 1 por distinguir host/porta interna de host/porta publicada; 1 por escolher diagnósticos úteis; 1 por explicar por que localhost não alcança o outro container.

## Critério de conclusão
Você concluiu quando constrói uma imagem com contexto controlado, executa e inspeciona containers, mantém dados em volume, publica uma porta de forma consciente e conecta containers pela rede correta.
