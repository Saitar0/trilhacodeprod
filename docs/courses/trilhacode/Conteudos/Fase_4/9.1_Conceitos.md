## Objetivo
Explicar como bancos relacionais organizam dados e distinguir tabela, linha, coluna, chave primária, chave estrangeira e cardinalidades básicas.

## Teoria

### 1. Tabelas, linhas, colunas e esquema
Um banco de dados é uma coleção organizada de dados gerida por um sistema de gerenciamento (SGBD), que oferece formas controladas de armazenar, consultar e alterar informação. No modelo relacional, uma tabela agrupa ocorrências sobre um assunto; cada linha representa uma ocorrência e cada coluna um atributo com tipo definido. O esquema descreve tabelas, colunas, tipos e restrições; os dados são as ocorrências armazenadas.

O nome da tabela costuma representar a entidade ou relação, como pessoa ou pedido; nomes de coluna descrevem atributos, como nome ou criado_em. A ordem das linhas não é garantida sem ordenação explícita numa consulta. Também não presuma que duas linhas idênticas serão automaticamente impedidas: defina chaves e restrições que expressem as regras desejadas.

**Erro comum:** confundir posição de uma linha com identidade. A linha que aparece primeiro numa consulta não tem identidade estável por ocupar aquela posição.

### 2. Chave primária e identificação
Uma chave primária (PK) identifica uma linha sem ambiguidade. O valor ou combinação de valores da PK é único e não nulo. A chave pode ser natural, quando um atributo do domínio já é identificador adequado, ou substituta, quando se cria um identificador técnico. Uma chave composta usa mais de uma coluna, por exemplo duas referências numa tabela associativa.

Uma chave natural só é uma boa candidata se sua estabilidade, unicidade e disponibilidade forem garantidas pelo domínio. Nomes de pessoas, por exemplo, normalmente não são bons identificadores. Uma PK substituta identifica a linha, enquanto outras regras — como email único, quando essa regra realmente pertence ao domínio — podem ser expressas separadamente com restrições apropriadas.

**Erro comum:** escolher um campo porque “parece único” sem verificar se pode mudar, faltar ou repetir.

### 3. Chave estrangeira e integridade referencial
Uma chave estrangeira (FK) contém valor que referencia uma chave primária ou outra chave única de uma tabela referenciada. Ela expressa a relação entre registros e permite ao SGBD rejeitar referências inexistentes. Uma FK não substitui a PK da própria linha: cada uma tem um papel diferente.

```sql
CREATE TABLE pessoa (
  id integer PRIMARY KEY,
  nome text NOT NULL
);

CREATE TABLE telefone (
  id integer PRIMARY KEY,
  pessoa_id integer NOT NULL REFERENCES pessoa(id),
  numero text NOT NULL
);
```

Aqui, pessoa_id liga cada telefone a uma pessoa; NOT NULL exige que toda linha de telefone tenha essa referência. Sem NOT NULL, uma FK pode aceitar NULL conforme as regras do SGBD. Uma FK pode referenciar uma PK ou colunas com restrição de unicidade. Detalhes de sintaxe e ações ao atualizar/remover linhas variam por SGBD.

**Erro comum:** acreditar que escrever um nome de coluna como pessoa_id cria uma relação automaticamente. A referência precisa ser declarada como FK no esquema.

### 4. Cardinalidades: 1:1, 1:N e N:N
A cardinalidade descreve quantas ocorrências podem se relacionar:
- **1:1:** cada ocorrência de A se relaciona com no máximo uma de B, e vice-versa. Uma FK com unicidade ajuda a impor o limite de um lado; a obrigatoriedade depende também de NOT NULL e da regra de domínio.
- **1:N:** uma ocorrência do lado 1 pode se relacionar com várias do lado N. A FK normalmente fica na tabela do lado N, como pessoa_id em telefone.
- **N:N:** várias ocorrências de A podem se relacionar com várias de B. Represente o vínculo numa tabela associativa com FKs para ambas. A combinação das FKs pode ser uma PK composta quando o mesmo par só deve ocorrer uma vez.

Uma relação associativa também pode ter atributos próprios. Em matrícula, por exemplo, a data de inscrição pertence ao vínculo entre estudante e turma, não apenas ao estudante nem apenas à turma.

**Erro comum:** colocar uma lista de identificadores ou valores repetidos dentro de uma coluna para representar N:N. Isso dificulta validar referências, atualizar relações e consultar os dados de forma consistente.

### 5. Modelo relacional e representação JSON
O modelo relacional organiza entidades e relações em estruturas declaradas, com chaves e restrições. JSON é um formato de representação/intercâmbio de dados. Um banco relacional pode oferecer colunas que armazenam JSON, mas isso não transforma automaticamente o sistema num banco documental nem elimina as decisões sobre relações, identificadores e integridade.

Escolha a representação conforme consultas e regras que precisam ser sustentadas. Se pedidos precisam apontar para clientes e itens para produtos, uma referência explícita pode ser central para a integridade e para consultas. A modelagem detalhada e normalização serão aprofundadas nas próximas unidades; aqui, identifique o assunto de cada tabela e como as linhas se relacionam.

**Erro comum:** achar que “usa JSON” e “é banco relacional” são categorias mutuamente exclusivas. JSON pode ser um formato de dados dentro de uma coluna; modelo e garantias dependem do SGBD e do desenho adotado.

## Resumo
- Tabela agrupa ocorrências; coluna descreve atributo; linha representa uma ocorrência.
- Esquema define estrutura, tipos e restrições; ordem das linhas não é garantida sem ordenação.
- PK identifica uma linha de forma única e não nula; pode ser simples ou composta.
- FK declara uma referência e ajuda a manter integridade entre tabelas.
- 1:N normalmente coloca a FK no lado N; N:N usa uma tabela associativa.
- JSON é formato de dados e pode coexistir com um banco relacional.

## Quiz
1. O que distingue esquema de linha? **Resposta:** esquema define a estrutura e as restrições; linha é uma ocorrência nessa estrutura. **Justificativa:** esquema descreve como os dados podem ser organizados, enquanto a linha contém valores concretos.

2. Onde costuma ficar a FK numa relação 1:N? **Resposta:** na tabela do lado N. **Justificativa:** cada linha do lado N guarda a referência à linha relacionada do lado 1.

3. Como representar N:N sem repetir listas? **Resposta:** tabela associativa com FKs para as duas entidades. **Justificativa:** cada linha representa um vínculo e pode carregar atributos do próprio vínculo.

4. O que uma chave primária garante? **Resposta:** identifica cada linha de forma única e não aceita NULL. **Justificativa:** PK pode ser uma ou mais colunas; se a regra de domínio exigir outra unicidade, ela deve ser declarada separadamente.

5. Uma coluna chamada pessoa_id referencia uma pessoa automaticamente? **Resposta:** não; é preciso declarar a restrição de chave estrangeira. **Justificativa:** nomear a coluna sugere a intenção, mas a integridade referencial depende da restrição criada no esquema.

## Práticas

### 1. Guiada — pessoas e telefones
Transforme o exemplo de uma lista de pessoas com vários telefones por pessoa em tabelas. Desenhe as entidades, marque PK/FK e indique a cardinalidade. Explique se um telefone pode existir sem pessoa e qual regra de unicidade, se houver, foi assumida para o número.

**Dica:** comece perguntando se uma pessoa pode ter vários telefones e se cada linha de telefone precisa apontar para uma pessoa.

**Solução de referência:** tabela pessoa com id como PK e nome; tabela telefone com id como PK, pessoa_id como FK para pessoa.id e numero. A cardinalidade é 1:N, com a FK na tabela telefone. Se todo telefone precisa pertencer a alguém, pessoa_id é obrigatório (NOT NULL). A unicidade do número depende da regra: não imponha uma restrição global sem saber se o mesmo telefone pode ser compartilhado; se a regra for “não repetir telefone da mesma pessoa”, considere unicidade composta entre pessoa_id e numero.

**Aceite:** cada tabela tem uma chave identificada; FK representa a relação; cardinalidade e nulabilidade são justificadas; regra de unicidade não é presumida sem requisito.

### 2. Independente — estudantes e turmas
Uma escola oferece várias turmas e cada estudante pode se matricular em várias turmas. Cada turma contém muitos estudantes. Modele as tabelas e chaves para representar o vínculo. A matrícula deve guardar data_inscricao e estado. Explique por que esses campos pertencem à associação.

**Dica:** se cada lado pode se relacionar com várias ocorrências do outro, introduza uma tabela associativa; liste os campos que descrevem o vínculo.

**Solução de referência:** estudante e turma têm suas PKs; matricula guarda estudante_id e turma_id como FKs, além de data_inscricao e estado. A cardinalidade entre estudante e turma é N:N e se materializa em duas relações 1:N a partir de matricula. Se o mesmo estudante só puder se matricular uma vez na mesma turma, a combinação (estudante_id, turma_id) pode ser PK composta; se houver mais de uma tentativa/registro por período, inclua o atributo que diferencia a matrícula ou escolha outra chave e declare a regra de unicidade correspondente.

**Rubrica (0–2 cada):** cardinalidade reconhecida; tabela associativa incluída; duas FKs corretas; campos do vínculo colocados em matricula; unicidade explicada como regra de domínio. **Domínio:** pelo menos 8/10, sem omitir uma das referências.

### 3. Integrada — normalize o esboço de pedidos
Uma planilha repete cliente e produto em cada linha: id_pedido, nome_cliente, email_cliente, data_pedido, nome_produto, quantidade e preco_unitario. Modele tabelas para cliente, pedido, produto e itens do pedido. Identifique PK/FK, cardinalidades e indique onde manteria o preço praticado naquela venda. Declare qualquer hipótese sobre repetição de produto dentro de um mesmo pedido.

**Dica:** um cliente pode ter vários pedidos; um pedido pode conter vários produtos e um produto pode aparecer em pedidos diferentes. Os dados do vínculo pedido-produto podem descrever a linha vendida.

**Solução de referência:** cliente(id, nome, email); pedido(id, cliente_id FK, data_pedido); produto(id, nome, preco_atual); item_pedido(pedido_id FK, produto_id FK, quantidade, preco_unitario_venda). Cliente–pedido é 1:N. Pedido–produto é N:N, representada por item_pedido e suas duas FKs. O preço no momento da compra fica no item_pedido para preservar o valor praticado mesmo que o preço atual do catálogo mude. Se só houver uma linha do mesmo produto por pedido, (pedido_id, produto_id) pode formar a PK composta; caso contrário, use uma chave que identifique cada linha e declare a regra. Email só deve ser único se essa for uma regra confirmada do domínio.

**Entregáveis:** diagrama ou lista de tabelas, campos, chaves, cardinalidades e hipóteses adotadas; uma justificativa para cada campo que foi movido para a tabela associativa.

**Rubrica (0–2 cada):** entidades separadas com propósito; PKs/FKs coerentes; cardinalidades corretas; preço histórico no vínculo adequado; hipóteses e unicidade explícitas. **Domínio:** 8/10 ou mais, sem erro em PK/FK ou N:N.

## Critério de conclusão
Explicar tabela, linha, coluna, PK e FK com um domínio próprio; identificar cardinalidade 1:N e N:N; representar um relacionamento N:N com tabela associativa e justificar as chaves.
