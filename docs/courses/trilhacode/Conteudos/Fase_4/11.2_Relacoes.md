## Objetivo
Combinar tabelas com JOIN e subqueries, prever a cardinalidade do resultado e produzir agregações corretas com GROUP BY, WHERE e HAVING.

## Teoria

### 1. Relacione linhas pela chave correta
JOIN combina linhas de fontes diferentes segundo uma condição. Em um modelo relacional, a condição costuma ligar a chave primária de uma tabela à chave estrangeira da outra. Use aliases para deixar claro de onde vêm as colunas e qual papel cada tabela ocupa.

```sql
SELECT p.id AS pedido_id, p.criado_em, i.produto_id, i.quantidade
FROM pedido AS p
JOIN item_pedido AS i ON i.pedido_id = p.id;
```

INNER JOIN mantém apenas pares que satisfazem ON. Um pedido sem itens não aparece. A condição deve representar a relação real; ligar tabelas apenas por nomes iguais ou usar uma coluna sem unicidade pode criar associações erradas. JOIN sem condição pode gerar produto cartesiano, combinando cada linha de uma tabela com todas da outra.

Preveja quantas linhas podem sair: um Pedido ligado a seus ItensPedido gera uma linha por item, não necessariamente uma linha por pedido. Antes de agregar, inspecione a granularidade do resultado — o que cada linha representa depois da junção.

**Erro comum:** esperar que uma junção 1:N preserve uma linha por registro do lado 1.

### 2. Preserve linhas com LEFT JOIN e posicione condições
LEFT JOIN mantém todas as linhas da tabela à esquerda. Quando não existe correspondência à direita, as colunas da tabela direita vêm como NULL. Isso é útil para encontrar clientes sem pedidos:

```sql
SELECT c.id, c.nome
FROM cliente AS c
LEFT JOIN pedido AS p ON p.cliente_id = c.id
WHERE p.id IS NULL;
```

A posição da condição importa. Se o objetivo é manter clientes mesmo quando não têm pedido pago, coloque a condição de status no ON:

```sql
SELECT c.id, p.id AS pedido_id
FROM cliente AS c
LEFT JOIN pedido AS p
  ON p.cliente_id = c.id
 AND p.status = 'pago';
```

Colocar `p.status = 'pago') no WHERE elimina as linhas sem pedido, pois o valor NULL não satisfaz a condição. O LEFT JOIN passa a se comportar como uma filtragem de correspondências, o que pode ser o desejado, mas não preserva todos os clientes.

**Erro comum:** mover uma condição da tabela direita de ON para WHERE sem verificar se as linhas sem correspondência ainda devem aparecer.

### 3. Entenda o efeito da cardinalidade nas agregações
COUNT, SUM e AVG resumem as linhas que chegam à agregação. Se a tabela principal tem várias linhas relacionadas, um JOIN aumenta a granularidade. Por exemplo, um pedido com três itens aparece três vezes na junção Pedido–ItemPedido. Somar o total do pedido após essa junção pode contar esse total três vezes.

Agregue no nível adequado. Para receita por item, some quantidade × preço unitário vendido. Para total por pedido, agregue os itens por pedido antes de somar os pedidos. Não use SUM(DISTINCT valor) como correção genérica: dois pedidos diferentes podem ter o mesmo valor e ainda assim ambos devem ser contados.

COUNT(*) conta as linhas resultantes; COUNT(coluna) conta apenas valores não nulos nessa coluna. Com LEFT JOIN, `COUNT(*)) conta também a linha preenchida com NULL para um pai sem correspondência; para contar filhos, use uma coluna obrigatória da tabela filha, como `COUNT(p.id)).

**Erro comum:** somar um atributo do lado “um” após juntá-lo a várias linhas do lado “muitos”.

### 4. Separe WHERE, GROUP BY e HAVING
O fluxo mental útil é: FROM/JOIN formam as linhas; WHERE filtra linhas individuais; GROUP BY reúne as linhas que compartilham os valores indicados; agregações calculam resumos; HAVING filtra os grupos. Use WHERE para restringir registros antes de agregar e HAVING para uma condição que depende do agregado.

```sql
SELECT p.cliente_id, SUM(i.quantidade * i.preco_unitario) AS gasto
FROM pedido AS p
JOIN item_pedido AS i ON i.pedido_id = p.id
WHERE p.status = 'pago'
GROUP BY p.cliente_id
HAVING SUM(i.quantidade * i.preco_unitario) >= 500;
```

Cada coluna do SELECT em uma consulta agrupada precisa estar agrupada ou agregada, salvo dependências funcionais que o PostgreSQL reconheça. SUM e AVG ignoram entradas NULL; COUNT(coluna) também ignora NULL, enquanto COUNT(*) conta linhas. Defina o que NULL significa para a métrica e use COALESCE apenas quando substituir ausência por zero fizer sentido para a regra.

**Erro comum:** colocar uma condição como `SUM(total) >= 500) em WHERE, que filtra linhas e não grupos.

### 5. Use subqueries quando expressam melhor a pergunta
Subquery é uma consulta usada dentro de outra. EXISTS testa se há pelo menos uma linha correspondente e expressa bem perguntas como “quais clientes possuem algum pedido pago?”:

```sql
SELECT c.id, c.nome
FROM cliente AS c
WHERE EXISTS (
  SELECT 1
  FROM pedido AS p
  WHERE p.cliente_id = c.id
    AND p.status = 'pago'
);
```

A consulta interna pode referenciar a linha externa; por isso, é correlacionada. EXISTS não multiplica a linha do cliente quando há vários pedidos correspondentes. Uma junção também pode expressar essa pergunta, mas pode exigir DISTINCT ou agregação para remover repetição; compare pela clareza da semântica e do resultado.

IN testa pertencimento a um conjunto. Cuidado com NOT IN quando a subquery pode produzir NULL: a lógica de três valores pode impedir que linhas sejam retornadas como esperado. Para “não existe correspondência”, NOT EXISTS costuma deixar a intenção mais direta. Subquery não é automaticamente mais lenta nem mais rápida; desempenho depende do plano e dos dados.

**Erro comum:** escolher JOIN ou subquery por uma regra simplista de desempenho sem verificar o significado e o plano da consulta.

## Resumo
- INNER JOIN retorna pares correspondentes; LEFT JOIN preserva as linhas da esquerda.
- A condição ON deve seguir a relação do modelo e a granularidade resultante precisa ser prevista.
- Junções 1:N podem repetir atributos do lado 1 e inflar agregações.
- WHERE filtra linhas; HAVING filtra grupos depois da agregação.
- EXISTS expressa presença sem multiplicar a linha externa; escolha pela semântica e verifique o plano se desempenho importar.

## Quiz
1. Um pedido tem quatro itens. Quantas linhas ele pode gerar em Pedido JOIN ItemPedido? **Resposta:** quatro, uma por item, assumindo que cada item corresponde a esse pedido. **Feedback:** a junção está no nível de detalhe de ItemPedido, não no nível de Pedido.
2. Você precisa listar todos os clientes, incluindo quem ainda não tem pedido pago. Onde colocar `p.status = 'pago') em um LEFT JOIN? **Resposta:** na condição ON da junção com Pedido. **Feedback:** no WHERE, as linhas sem pedido têm status NULL e são removidas.
3. Após juntar Pedido a ItemPedido, por que `SUM(p.total)) pode ficar inflado? **Resposta:** o valor do pedido se repete em cada linha de item. **Feedback:** agregue no nível apropriado ou some os valores das linhas de item.
4. Qual cláusula filtra grupos cujo gasto agregado ultrapassa 500? **Resposta:** HAVING. **Feedback:** WHERE age antes do agrupamento e filtra linhas individuais.
5. Por que EXISTS pode ser adequado para consultar clientes que fizeram ao menos um pedido? **Resposta:** testa existência sem produzir uma linha do cliente para cada pedido correspondente. **Feedback:** uma junção pode multiplicar clientes e exigir deduplicação.

## Práticas

### Atividade 1 — Encontre clientes sem pedidos
Considere Cliente(id, nome) com as linhas (1, Ana), (2, Beto), (3, Caio) e Pedido(id, cliente_id) com as linhas (10, 1), (11, 1), (12, 3).

**Tarefas**
1. Escreva uma consulta que liste clientes sem pedidos.
2. Preveja exatamente os ids retornados.
3. Adapte a consulta para listar todos os clientes e somente os pedidos pagos, sem remover quem não tem pedido pago.

**Dica:** use a PK do lado direito para detectar ausência; preserve a condição de status dentro de ON na segunda consulta.

**Solução de referência:**
```sql
SELECT c.id, c.nome
FROM cliente AS c
LEFT JOIN pedido AS p ON p.cliente_id = c.id
WHERE p.id IS NULL;
```
O resultado é Beto (id 2). Para manter todos os clientes e combinar apenas pedidos pagos:
```sql
SELECT c.id, p.id AS pedido_id
FROM cliente AS c
LEFT JOIN pedido AS p
  ON p.cliente_id = c.id
 AND p.status = 'pago';
```
Clientes sem pedido pago permanecem com pedido_id NULL.

**Rubrica (0–4):** 1 ponto pela junção correta; 1 por detectar a ausência com uma coluna não nula; 1 pelo resultado esperado; 1 por manter o filtro do LEFT JOIN no ON.

### Atividade 2 — Calcule gasto sem multiplicar valores
Considere Pedido(id, cliente_id, status) e ItemPedido(pedido_id, quantidade, preco_unitario). Pedido 20 é pago e possui linhas (20, 2, 15) e (20, 1, 10); Pedido 21 é pago e possui (21, 1, 40). Pedido 22 está aberto e possui (22, 3, 20).

**Tarefas**
1. Escreva a receita total dos pedidos pagos.
2. Escreva o gasto por cliente e mantenha somente clientes com gasto pago de pelo menos 30.
3. Explique por que somar um total de pedido repetido em cada linha poderia inflar o resultado.

**Dica:** calcule valor por item como quantidade × preço unitário e filtre status antes de agrupar.

**Solução de referência:**
```sql
SELECT SUM(i.quantidade * i.preco_unitario) AS receita
FROM pedido AS p
JOIN item_pedido AS i ON i.pedido_id = p.id
WHERE p.status = 'pago';
```
Receita = 80: pedido 20 soma 40 e pedido 21 soma 40; pedido 22 é excluído. Por cliente:
```sql
SELECT p.cliente_id, SUM(i.quantidade * i.preco_unitario) AS gasto
FROM pedido AS p
JOIN item_pedido AS i ON i.pedido_id = p.id
WHERE p.status = 'pago'
GROUP BY p.cliente_id
HAVING SUM(i.quantidade * i.preco_unitario) >= 30;
```
Se cada pedido tivesse p.total repetido para cada item, somar p.total depois do JOIN contaria o pedido uma vez por item.

**Rubrica (0–5):** 1 ponto pelo JOIN; 1 pelo filtro antes de agrupar; 1 pela expressão correta de receita; 1 por GROUP BY/HAVING corretos; 1 por identificar a duplicação do total do pedido.

### Atividade 3 — Compare existência com junção
Escreva uma consulta que liste clientes com pelo menos um pedido pago. Compare uma versão com EXISTS e outra com JOIN; inclua dois pedidos pagos para um cliente e explique a diferença no resultado bruto.

**Tarefas**
1. Escreva a versão com EXISTS.
2. Escreva uma versão com JOIN.
3. Preveja quantas linhas o cliente com dois pedidos pagos produz na versão JOIN.
4. Explique por que EXISTS evita essa multiplicação.
5. Indique por que desempenho não pode ser deduzido só pela forma escrita.

**Dica:** a pergunta é sobre existência de ao menos um pedido, e não sobre listar cada pedido.

**Solução de referência:**
```sql
SELECT c.id, c.nome
FROM cliente AS c
WHERE EXISTS (
  SELECT 1
  FROM pedido AS p
  WHERE p.cliente_id = c.id
    AND p.status = 'pago'
);
```
A versão com JOIN:
```sql
SELECT c.id, c.nome
FROM cliente AS c
JOIN pedido AS p ON p.cliente_id = c.id
WHERE p.status = 'pago';
```
Um cliente com dois pedidos pagos aparece duas vezes na versão JOIN, uma por pedido; EXISTS retorna uma linha por cliente. Para decidir desempenho real, avalie dados, índices e plano de execução, além de preservar a semântica desejada.

**Rubrica (0–5):** 1 ponto pela correlação de EXISTS; 1 pela junção e condição; 1 por prever a multiplicação; 1 por explicar a diferença de semântica; 1 por não afirmar desempenho sem evidência.

## Critério de conclusão
Você concluiu quando explica o que cada linha representa após uma junção, escolhe INNER ou LEFT JOIN conforme a pergunta, calcula agregações sem duplicação e compara uma subquery com uma junção equivalente.
