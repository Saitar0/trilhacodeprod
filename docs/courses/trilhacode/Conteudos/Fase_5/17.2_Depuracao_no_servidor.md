## Objetivo
Investigar uma falha reproduzível em um servidor Node.js usando inspector, breakpoints, stack traces e logs com contexto seguro.

## Teoria

### 1. Reproduzir antes de alterar
Comece descrevendo o sintoma: rota ou operação afetada, entrada, resultado esperado e resultado observado. Reproduza com a menor entrada que ainda causa o problema e registre os passos. Se o erro for intermitente, anote condições relevantes, como ordem de chamadas, concorrência ou estado do banco. Uma hipótese de causa deve ser testada com uma mudança por vez; esconder a falha com um catch vazio ou alterar várias partes ao mesmo tempo reduz a informação disponível.

### 2. Inspector e breakpoints
O inspector do Node conecta o processo a uma ferramenta de depuração, como DevTools ou IDE compatível. Iniciar com node --inspect permite que a aplicação comece a executar; node --inspect-brk interrompe no início para conectar o depurador antes de seguir. Um breakpoint pausa a execução em uma linha; a partir dele, examine variáveis locais, pilha de chamadas e o caminho até a linha seguinte. Step over executa a linha atual sem entrar em outra função; step into entra na função chamada; continue retoma até o próximo breakpoint.

O inspector não é uma interface de leitura apenas: uma conexão pode controlar e executar código no processo. Por padrão, o inspector local usa 127.0.0.1:9229. Não o exponha em um endereço público ou a uma rede não confiável; um listener aberto pode permitir execução remota de código. [Node.js — Debugging Guide](https://nodejs.org/en/learn/getting-started/debugging) e [Node.js — opções do inspector](https://nodejs.org/api/cli.html#--inspecthostport).

### 3. Stack traces e falhas assíncronas
Uma stack trace registra frames que ajudam a localizar onde um erro foi criado e por quais chamadas síncronas chegou ali. Comece pela mensagem e pelo primeiro frame relevante da aplicação, mas não assuma que esse frame é automaticamente a causa: siga os valores e chamadas até encontrar a condição incorreta. Código de dependências, wrappers e limites assíncronos podem aparecer no trace; mapas de origem ajudam quando o código executado foi transformado.

Em Promises, preserve a rejeição e encaminhe-a para uma camada capaz de tratá-la. Se adicionar contexto e criar um novo Error, preserve a causa original quando possível, em vez de descartá-la. Diferencie erro esperado de entrada, falha externa e defeito inesperado; cada caso pede uma resposta e um nível de registro diferentes. [Node.js — Errors](https://nodejs.org/api/errors.html).

### 4. Logs úteis e seguros
Um log de diagnóstico deve responder o que aconteceu e em qual operação. Registre evento, horário, nível, identificador de requisição, rota ou operação, resultado e código/classe do erro quando disponíveis. Inclua apenas dados necessários para investigar. Não registre senha, token, cabeçalho de autorização, dados pessoais completos ou conteúdo de request sem motivo e proteção adequados. Prefira um identificador de correlação não secreto a copiar dados sensíveis para o log.

console.log e console.error são úteis para experimentos locais; o objeto console envia dados a stdout/stderr, mas não define por si só formato estruturado, níveis, retenção, alertas ou política de privacidade de logs. No servidor, use a estratégia de logging do projeto e evite engolir erros. [Node.js — Console](https://nodejs.org/api/console.html).

## Resumo
- Reproduza o sintoma e anote entrada e resultado antes de alterar o código.
- Inspector e breakpoints ajudam a observar estado e fluxo; step through testa uma hipótese.
- Stack trace é evidência para seguir, não uma prova automática da causa.
- Preserve a causa de falhas assíncronas e trate rejeições na camada adequada.
- Logs precisam de contexto útil e devem excluir segredos e dados desnecessários.
- Mantenha a porta do inspector acessível somente a quem está autorizado a depurar.

## Quiz

1. Para que usar node --inspect-brk ao depurar uma falha que ocorre durante a inicialização?  
   **Resposta:** para conectar o depurador e pausar no início da execução, antes de o programa avançar pelo fluxo inicial.  
   **Feedback:** node --inspect deixa o processo começar imediatamente; a pausa inicial é útil quando o problema ocorre antes de ser possível colocar um breakpoint manual.

2. Qual risco existe ao expor publicamente a porta padrão do inspector?  
   **Resposta:** uma conexão externa pode controlar o processo e executar código remotamente.  
   **Feedback:** o inspector é uma interface de controle do processo. Mantenha-o em loopback ou restrinja o acesso com controles de rede apropriados.

3. Como começar a ler uma stack trace extensa?  
   **Resposta:** ler mensagem e código do erro, localizar frames relevantes da aplicação e seguir os valores e chamadas que levaram à falha.  
   **Feedback:** o primeiro frame visível ajuda a localizar o ponto de emissão, mas a causa pode estar em um valor ou decisão anterior.

4. Uma camada captura um erro de banco e cria outra mensagem contextual, mas descarta o objeto original. O que se perde?  
   **Resposta:** a causa e detalhes originais que poderiam explicar a falha subjacente.  
   **Feedback:** ao acrescentar contexto, preserve o erro original como causa quando a versão e o padrão do projeto permitirem.

5. Qual conjunto de informações ajuda a investigar uma falha sem registrar dados sensíveis?  
   **Resposta:** evento, rota/operação, identificador de correlação, horário, resultado e classe/código do erro, evitando tokens e dados pessoais desnecessários.  
   **Feedback:** contexto operacional pode orientar a busca nos traces sem copiar credenciais ou conteúdo privado para os logs.

## Práticas

### Atividade 1 — Encontrar a causa de uma falha reproduzível
Considere uma rota de consulta de usuário que funciona para IDs existentes, mas retorna erro interno quando o ID não existe. A implementação tenta acessar o nome do resultado sem verificar se a consulta retornou um usuário. Reproduza o caso com um ID ausente, registre entrada e resposta, inicie o processo com node --inspect-brk ou node --inspect, coloque breakpoint antes do acesso ao nome e siga os valores. Corrija o fluxo para representar a ausência como resposta apropriada e acrescente uma verificação de regressão.

**Dica:** inspecione o resultado da consulta e o frame da aplicação antes de alterar a resposta HTTP. Diferencie ausência esperada de usuário de falha inesperada do banco.

**Solução de referência:** o breakpoint mostra que o resultado é ausente antes da leitura da propriedade. A causa é a suposição de que toda consulta encontra um registro. Trate a ausência explicitamente com resposta de recurso não encontrado; mantenha erros de banco no fluxo de falha apropriado. Reexecute o mesmo caso e confirme que a rota ainda funciona para ID existente.

**Rubrica:** reprodução é determinística; breakpoint foi usado para observar o valor; causa foi identificada em vez de mascarada; casos existente e ausente têm resultado definido; falha do banco não vira silenciosamente ausência.

### Atividade 2 — Seguir uma falha assíncrona
Monte ou use uma função que leia configuração ou arquivo e cuja Promise possa rejeitar quando a entrada não existe. Observe a stack trace, siga a rejeição até a camada que decide a resposta e acrescente contexto sem apagar a causa original. Explique qual parte pode responder ao usuário e qual detalhe deve permanecer apenas no diagnóstico.

**Dica:** diferencie mensagem útil para quem usa a aplicação da informação técnica necessária para depuração. Não devolva caminho local, stack trace ou segredo na resposta pública.

**Solução de referência:** propagar a rejeição para uma camada de tratamento definida; se criar um erro contextual, anexar a falha original como cause quando aplicável; registrar evento e classe/código com ID de correlação; retornar mensagem pública genérica e resposta adequada ao tipo de falha.

**Rubrica:** rejeição não é ignorada; origem da falha continua disponível; resposta pública não expõe detalhe interno; o registro permite correlacionar a requisição.

### Atividade 3 — Criar um registro de erro seguro
Defina um formato de log para uma falha em uma rota. Inclua um evento legível, timestamp, request ID, método/rota sem parâmetros pessoais, status, duração e classe ou código do erro. Prepare um exemplo de erro de autenticação e outro de banco. Liste campos que devem ser redigidos ou removidos. Use a saída de console apenas para demonstrar localmente e descreva como o projeto entregaria logs em execução normal.

**Dica:** não use o token do usuário como request ID. Um identificador aleatório de correlação serve para conectar eventos sem conceder acesso à conta.

**Solução de referência:** registrar, por exemplo, evento request_failed, request ID não secreto, rota-modelo, status, duração e error code; omitir senha, token e corpo completo. Falha de autenticação deve registrar categoria e resultado, sem valor de credencial. Falha de banco pode registrar a classe/código técnico em destino restrito, enquanto a resposta ao usuário permanece segura.

**Rubrica:** contexto identifica a operação; eventos podem ser correlacionados; dados sensíveis estão ausentes; autenticação e banco são distinguidos; o canal e a política de logs do projeto estão descritos.

## Critério de conclusão
Reproduza e localize a causa de uma falha de servidor usando stack trace e breakpoint, corrija-a sem mascarar a origem e produza um log contextual que não exponha dados sensíveis.
