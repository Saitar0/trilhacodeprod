## Objetivo
Explicar como Node.js executa JavaScript, distinguir I/O assíncrono de trabalho CPU-bound, organizar módulos e processar dados grandes com streams e backpressure.

## Teoria

### 1. Runtime Node.js e responsabilidades
Node.js é um runtime JavaScript construído sobre V8 e componentes como libuv. Em uma execução comum, o código JavaScript roda no thread principal. O runtime integra APIs do sistema operacional e um pool de workers para determinadas operações; por isso, uma chamada assíncrona não significa que todo o trabalho foi transferido a um thread separado. Operações de rede frequentemente usam I/O não bloqueante do sistema; operações de arquivo assíncronas e algumas tarefas custosas podem usar o pool. O comportamento depende da API usada. [Node.js — visão geral de blocking e non-blocking](https://nodejs.org/learn/asynchronous-work/overview-of-blocking-vs-non-blocking).

### 2. Event loop e concorrência de I/O
O event loop coordena callbacks JavaScript e a conclusão de operações assíncronas. Enquanto uma requisição aguarda I/O não bloqueante, o processo pode avançar trabalho de outras requisições. Isso permite concorrência de I/O com poucos threads JavaScript; não significa que várias funções JavaScript síncronas rodem em paralelo no thread principal.

Uma função síncrona longa, um laço custoso ou uma expressão regular problemática pode ocupar o event loop e atrasar outras tarefas. Mantenha pequeno o trabalho síncrono de cada callback e meça a latência sob cargas representativas. O event loop tem fases e regras de agendamento; esta unidade usa o modelo para raciocinar sobre espera e bloqueio sem exigir memorizar cada fase. [Node.js — event loop](https://nodejs.org/learn/asynchronous-work/event-loop-timers-and-nexttick) e [não bloquear o event loop](https://nodejs.org/en/learn/asynchronous-work/dont-block-the-event-loop).

### 3. Promises e async/await
Uma Promise representa um resultado que pode chegar no futuro. async/await facilita escrever a continuação desse trabalho, mas não cria thread nem torna código CPU-bound paralelo. Ao aguardar uma Promise, a função assíncrona suspende sua continuação; outras tarefas elegíveis podem progredir. Rejeições precisam ser tratadas com try/catch ou propagadas para quem chama.

Use Promise.all quando operações independentes puderem começar juntas e todas forem necessárias ao resultado. Isso não reduz automaticamente o custo de cada operação e pode aumentar a pressão sobre um serviço externo se usado sem limite. Operações dependentes devem aguardar a etapa anterior.

### 4. CPU-bound, I/O e workers
Uma transformação CPU-bound grande — por exemplo, comprimir ou processar matematicamente um conjunto extenso em JavaScript síncrono — bloqueia o thread principal. Primeiro meça e identifique o custo. Para trabalho que realmente precisa de paralelismo, worker_threads permite executar JavaScript em threads separados; há custo de inicialização, comunicação e memória, então workers não são solução automática. Workers ajudam em tarefas CPU-intensive e em geral não são necessários para I/O que as APIs assíncronas do Node já tratam eficientemente. [Node.js — Worker threads](https://nodejs.org/api/worker_threads.html).

### 5. Streams e backpressure
Uma stream representa dados que chegam ou são produzidos em partes. Streams legíveis, graváveis e de transformação podem ser encadeadas. Esse padrão evita manter o arquivo inteiro em memória. Quando a parte consumidora fica mais lenta que a produtora, backpressure regula o fluxo para limitar o buffer em trânsito; ignorá-la pode fazer a memória crescer.

A função pipeline conecta as etapas e ajuda a propagar erros e conclusão; a API de Promises de node:stream permite aguardá-la com await. Uma cópia em fluxo transfere bytes, mas não valida nem interpreta CSV. Ler chunks não equivale a receber linhas ou registros completos: uma linha pode atravessar dois chunks. CSV também permite aspas, delimitadores dentro de campos e quebras de linha em campos citados; use parser adequado em modo stream em vez de dividir ingenuamente por vírgula ou quebra de linha. [Node.js — Streams](https://nodejs.org/api/stream.html).

### 6. Módulos, package.json e scripts
Node.js oferece dois formatos comuns de módulo: ECMAScript Modules (ESM) e CommonJS. A forma de interpretar arquivos .js depende do campo type do package.json mais próximo; extensões .mjs e .cjs também identificam os formatos explicitamente. import/export pertencem ao ESM; require/module.exports são o padrão CommonJS. Um projeto deve declarar e usar seu formato de maneira consistente, especialmente ao integrar dependências.

O package.json registra metadados, dependências e scripts de automação. Scripts como npm run padronizam comandos de desenvolvimento, verificação e execução. Confirme a versão de Node adotada e não inclua tokens ou credenciais em scripts versionados. [Node.js — Packages](https://nodejs.org/api/packages.html).

## Resumo
- Node combina JavaScript no thread principal com APIs de I/O e workers internos; o caminho depende da API.
- I/O assíncrono permite concorrência; JavaScript síncrono longo bloqueia o event loop.
- async/await organiza Promises, mas não cria paralelismo.
- worker_threads são opção para CPU-bound medido; streams e backpressure controlam o volume de dados em trânsito.
- pipeline ajuda a compor etapas e propagar erros; CSV deve ser processado por parser consciente do formato.
- package.json e a configuração ESM/CommonJS tornam execução e scripts explícitos.

## Quiz

1. Uma rota aguarda uma consulta assíncrona ao banco. Enquanto aguarda, o que pode acontecer no processo?  
   **Resposta:** outras tarefas podem progredir enquanto a operação de I/O aguarda, se a API usada for não bloqueante.  
   **Feedback:** isso é concorrência de I/O; não significa que o JavaScript síncrono da rota está executando em paralelo no mesmo thread.

2. Uma função JavaScript síncrona leva vários segundos para processar um arquivo. O que pode ocorrer em um servidor Node?  
   **Resposta:** ela ocupa o thread principal e atrasa callbacks e outras requisições atendidas pelo event loop.  
   **Feedback:** trabalho longo precisa ser medido e, conforme o caso, dividido, otimizado ou transferido para workers.

3. await em uma Promise cria um novo thread?  
   **Resposta:** não. A continuação da função assíncrona espera o resultado; await não cria thread.  
   **Feedback:** Promises representam resultados assíncronos. Paralelismo de JavaScript exige mecanismo próprio, como worker threads.

4. Por que um pipeline de streams pode processar um arquivo grande usando menos memória que ler tudo e depois processar?  
   **Resposta:** porque as etapas trabalham com partes dos dados, e backpressure pode limitar os buffers entre produtor e consumidor.  
   **Feedback:** o benefício depende de não acumular os chunks em uma coleção ou string gigante depois.

5. Um programa lê CSV por chunks e separa cada chunk por vírgula para montar registros. Qual é o risco?  
   **Resposta:** um campo entre aspas pode conter vírgulas ou quebras de linha, e um registro pode estar dividido entre chunks; a divisão simples pode corromper a interpretação.  
   **Feedback:** use parser CSV que aceite streams e trate encoding, aspas, erros e limites de registro.

## Práticas

### Atividade 1 — Classificar caminhos de execução
Para cada operação, indique se tende a aguardar I/O, usar o thread principal para computação síncrona ou exige análise adicional: consulta assíncrona ao banco; cálculo síncrono longo em um array; leitura de arquivo pela API assíncrona; compressão com API assíncrona; interpretação síncrona de um JSON muito grande. Desenhe uma linha do tempo simples mostrando onde o event loop pode atender outra tarefa. Proponha uma ação para reduzir o risco da operação mais custosa.

**Dica:** não classifique apenas pela palavra “assíncrono”. Pergunte qual API foi chamada, que parte executa JavaScript e quanto trabalho síncrono ocorre por callback.

**Solução de referência:** consulta de banco não bloqueia o thread principal se o cliente usa I/O não bloqueante; cálculo síncrono e interpretação síncrona ocupam o thread principal enquanto rodam; APIs de arquivo e compressão assíncronas podem usar o pool conforme a API. Para o custo alto, medir primeiro e considerar otimização, limites de tamanho, streaming quando aplicável ou worker thread para computação CPU-bound.

**Rubrica:** distingue espera de I/O e execução síncrona; não afirma que async cria thread; reconhece o papel do pool sem generalizar todas as APIs; propõe mitigação coerente com a causa.

### Atividade 2 — Processar arquivo grande com stream
Implemente um programa que leia um arquivo de texto grande por stream, conte linhas sem guardar o arquivo completo e reporte erros de leitura. Defina o comportamento para arquivo vazio, linha final sem quebra de linha e finais de linha CRLF. Registre como verificou o resultado com um arquivo pequeno conhecido e como confirmou que a solução não acumula todo o conteúdo.

**Dica:** o byte LF pode ser contado mesmo quando chunks terminam em qualquer ponto; acrescente uma última linha somente se houver conteúdo após a última quebra. Para CSV real, use parser em stream e confira seus registros com um arquivo de exemplo pequeno.

**Solução de referência:** abrir uma stream de leitura e percorrer os chunks mantendo apenas o contador, se houve algum byte e o último byte; somar cada byte LF encontrado; ao final, somar uma linha se o arquivo não for vazio e o último byte não for LF. Usar tratamento de erro ou pipeline com uma etapa de transformação e destino de contagem. CRLF conta como uma quebra porque o par contém LF; uma linha final sem terminador conta uma vez.

**Rubrica:** memória não cresce proporcionalmente ao arquivo; erros são tratados; casos vazio/final sem LF/CRLF foram definidos; resultado confere com arquivo pequeno de referência; contagem de linhas não é confundida com parsing de CSV.

### Atividade 3 — Declarar módulos e scripts do projeto
Crie ou revise um package.json mínimo para um pequeno programa Node. Escolha ESM ou CommonJS, declare o formato explicitamente e configure um script para executar o programa. Escreva duas instruções de execução no README e explique como uma extensão .mjs ou .cjs se comporta caso o projeto precise misturar formatos.

**Dica:** o campo type afeta os arquivos .js dentro de seu pacote; não misture sintaxe ESM e CommonJS no mesmo arquivo.

**Solução de referência:** declarar type como module e usar import/export consistentemente, ou declarar commonjs e usar require/module.exports; registrar o comando em scripts e executá-lo via npm. Para misturar formatos, usar extensões explícitas e seguir a interoperabilidade documentada para a versão de Node em uso.

**Rubrica:** formato explícito e coerente; script pode ser explicado e reproduzido; README informa execução; credenciais não são colocadas no manifesto ou em scripts.

## Critério de conclusão
Explique por que I/O assíncrono não equivale a paralelismo, identifique um caso que bloquearia o event loop e processe um arquivo grande por stream com tratamento de erro e memória limitada. Configure também um formato de módulo explícito no projeto.
