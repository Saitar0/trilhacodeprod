# 24.3 — Projeto incremental da fase

- key: 24.3
- tipo: projeto
- carater: obrigatorio
- profundidade: alta
- estimativa_minutos: 600
- tags: [#qualidade, #infra]
- status: rascunho

## Objetivo
Evoluir o projeto principal do Trilho A para uma API autenticada e testada, persistida em PostgreSQL com migrations e cache coerente, executável localmente com Compose.

## Contexto e escopo
Continue a ideia escolhida no projeto 3.5 e o modelo/banco produzido em 16.2. Esta entrega transforma o modelo e as funcionalidades anteriores em uma fatia vertical utilizável: cliente → API autenticada → regra de domínio → PostgreSQL, com cache apenas onde já exista um caso justificado da Fase 4. Não é necessário reescrever o projeto nem adotar arquitetura distribuída.

Use o framework e ORM já escolhidos no projeto. Se o curso ainda não fixou uma stack, a trilha de referência pode usar NestJS com Prisma; mantenha a alternativa adotada consistente e registre a decisão. As migrations são a fonte versionada do schema. Nunca use dados, credenciais ou banco de produção nos testes; forneça valores de exemplo sem segredos reais.

## Entregas por marco

### Marco 1 — Escopo vertical, contrato e ambiente reproduzível
**Objetivo:** escolher uma capacidade pequena que atravesse API, domínio e persistência e definir como outra pessoa vai executá-la.

**Tarefas:** selecione uma operação principal já alinhada à ideia do Trilho A (por exemplo, criar e consultar uma tarefa, pedido ou artigo). Registre quem pode executá-la, entradas/saídas, erros esperados, modelo envolvido e dependências. Confirme que o modelo de 16.2 atende ao caso ou descreva uma migration necessária. Documente versões, variáveis de ambiente exigidas e comandos previstos para subir dependências e rodar testes.

**Evidência:** issue/ADR curto ou seção no README com escopo, contrato da rota, regra de acesso, desenho do fluxo, dependências e hipóteses.

**Aceite:** a operação é pequena e demonstrável; o contrato define sucesso e pelo menos os erros de validação e acesso; nenhum requisito depende de credenciais reais; a decisão de cache ou sua ausência está justificada.

**Dica:** escreva primeiro o caminho feliz e uma tentativa inválida. Evite incluir telas e funcionalidades que não ajudam a provar a competência da fase.

### Marco 2 — API autenticada e persistência migrável
**Objetivo:** entregar a operação principal com validação, autenticação/autorização e PostgreSQL real.

**Tarefas:** implemente controller/rota, serviço/regra de domínio e persistência; valide entrada na fronteira; obtenha a identidade do usuário a partir da sessão/token validado; aplique autorização no servidor; inclua migration e dados sintéticos de demonstração, se necessários. Retorne erros consistentes sem expor detalhes internos.

**Evidência:** código da rota e regra, migration aplicada a banco vazio, exemplos de requisição/resposta e teste ou demonstração reproduzível para sucesso, entrada inválida e acesso negado.

**Aceite:** após recriar o banco e aplicar migrations, a rota persiste e recupera o recurso; usuário não autorizado não lê nem modifica o recurso; não é possível selecionar outra identidade enviando `ownerId` livremente no corpo da requisição.

**Dica:** derive o proprietário da identidade autenticada e passe essa identidade para a consulta. Se o domínio for multiusuário, teste também um identificador de recurso que pertence a outra pessoa.

### Marco 3 — Testes de serviço/rota e coerência de cache
**Objetivo:** provar regras de negócio e integração crítica sem depender de dados externos.

**Tarefas:** crie testes unitários para regra de domínio e testes de rota ou integração que alcancem banco de teste isolado. Inclua sucesso, validação, não autenticado, acesso negado, recurso inexistente e persistência. Se houver cache no fluxo, demonstre hit, expiração/invalidação após escrita e fallback quando Redis estiver indisponível conforme a política definida. Se não houver cache adequado, registre por que não usar um é a decisão correta.

**Evidência:** suíte automatizada, configuração isolada, comandos, relatório de execução e nota explicando o que cada nível de teste cobre ou não cobre.

**Aceite:** teste reproduzível detecta regressão na regra principal e autorização; teste de integração comprova a persistência real; estado de cache antigo não é servido após a operação que deveria invalidá-lo; executar testes não toca dados de produção.

**Dica:** mock de repositório ajuda a isolar unidade, mas sozinho não demonstra que rota, ORM e PostgreSQL funcionam juntos. Nomeie claramente cada tipo de teste.

### Marco 4 — Compose, documentação e revisão de ponta a ponta
**Objetivo:** tornar a entrega fácil de executar e revisar do zero.

**Tarefas:** inclua Dockerfile da API e integre API, PostgreSQL e Redis usado pela aplicação ao Compose local; configure health/readiness e ordem por condição de saúde quando necessário. Mantenha segredo em variável local ignorada pelo Git e forneça `.env.example` sem valores sensíveis. Documente inicialização, migrations, seed sintético, testes, rotas, erros conhecidos e limpeza do ambiente.

**Evidência:** README, arquivos Docker/Compose, `.env.example`, logs de inicialização e resultados dos testes executados no ambiente documentado.

**Aceite:** uma pessoa que clonou o projeto consegue seguir o README, iniciar dependências e API, aplicar migrations e executar os testes; o fluxo autenticado persiste no banco; o acesso proibido falha; nenhuma credencial real está versionada.

**Dica:** faça o ensaio final como ambiente novo: remova somente os volumes descartáveis deste projeto, aplique migrations desde zero e siga as instruções sem comandos implícitos que existam apenas na sua máquina.

## Decisões que precisam ser demonstradas
- Identidade e autorização vêm de contexto validado no servidor; campos enviados pelo cliente não concedem acesso por si só.
- Testes com mocks validam regras isoladas, mas não substituem ao menos um teste de integração com banco descartável.
- Cache não é obrigatório por checklist: se foi usado, sua coerência tem teste; se não foi usado, a decisão e o motivo ficam documentados.

## Checklist de aceite final
- [ ] README permite iniciar, migrar e testar o projeto em ambiente local.
- [ ] API documenta operação, autenticação, respostas e erros principais.
- [ ] Autorização deriva da identidade autenticada e é testada para negação.
- [ ] PostgreSQL pode ser criado do zero com migrations versionadas.
- [ ] Testes cobrem serviço, rota, validação, persistência e acesso negado.
- [ ] Cache tem decisão registrada e, se usado, política testável de expiração/invalidação.
- [ ] Dockerfile e Compose executam os serviços necessários sem embutir segredos.
- [ ] Seeds e exemplos usam dados sintéticos; nenhum teste acessa produção.

## Rubrica por marco (0–4)
1. **Escopo e contrato:** operação delimitada e requisito de acesso claro (0–1).
2. **Correção e segurança:** fluxo persiste corretamente e protege recurso/identidade (0–1).
3. **Evidência e testes:** evidências reproduzíveis cobrem caminho feliz, falhas e integração (0–1).
4. **Operação e documentação:** execução do zero é descrita, configuração é segura e limitações estão declaradas (0–1).

Não some pontos de marcos como substituto dos gates: o aceite final exige todos os itens críticos de autorização, persistência e execução reproduzível.

## Critério de conclusão
Os quatro marcos são entregues; API autenticada persiste no PostgreSQL após migrations; testes de serviço e rota demonstram regra, validação, persistência e negação de acesso; cache tem política testada ou justificativa para ausência; o projeto pode ser iniciado e verificado com as instruções e o Compose documentados.

## Conexões
Continua a ideia do Trilho A (3.5), o modelo de dados (16.2) e aplicação/confiabilidade de testes (24.1–24.2). Reutiliza fundamentos de API, autenticação, migrations e Compose já apresentados nas fases anteriores.
