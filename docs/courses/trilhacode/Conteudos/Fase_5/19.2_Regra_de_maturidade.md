# 19.2 — Regra de maturidade

- profundidade: media

## Objetivo
Decidir, por operação, quando usar a API de um ORM, um construtor de consultas ou SQL explícito, justificando a escolha com requisitos, evidências e custos de manutenção.

## Microtópico 1 — Comece pela regra e pela consulta
A decisão não começa pela preferência por ferramenta. Começa pelo comportamento que a aplicação precisa garantir: quais dados entram e saem, quais invariantes devem permanecer verdadeiras, qual volume é esperado e quais condições de concorrência existem. Identifique também se a operação é CRUD comum, leitura relacional, relatório, atualização em lote ou fluxo transacional.

**Exemplo:** cadastrar um usuário com campos e relações comuns pode caber naturalmente na API do ORM. Um relatório com agregações, agrupamentos e recursos específicos do banco pode pedir um construtor de consultas ou SQL explícito. O nome da operação, sozinho, não determina a escolha.

**Erro comum:** adotar uma regra global como “todo acesso passa pelo ORM” ou “consulta séria sempre é SQL”. As duas regras ignoram o problema concreto e podem esconder custo ou duplicar complexidade.

**Checagem:** antes de escolher uma API, descreva o resultado, as invariantes e o volume esperado da operação.

## Microtópico 2 — Escolha a menor abstração que mantém clareza
Use a API do ORM quando ela expressa a operação de modo legível, preserva tipagem útil e deixa as relações e limites da transação claros. Um query builder pode ser um meio-termo quando a consulta exige composição, joins ou condições dinâmicas, mas ainda se beneficia da integração da ferramenta. SQL explícito é adequado quando a API não expressa bem a consulta, quando um recurso específico do banco é necessário ou quando evidência medida justifica controle mais direto.

A menor abstração não é necessariamente a menor quantidade de linhas. Considere quem vai revisar e manter o código, se os tipos representam o resultado corretamente, se a consulta continua parametrizada e se a lógica de domínio permanece entendível. Evite manter duas implementações equivalentes sem motivo, pois elas podem divergir.

**Exemplo:** um endpoint CRUD permanece na API do ORM; uma consulta de relatório específica pode ficar em SQL versionado e parametrizado, com nome e contrato claros no repositório de acesso a dados.

**Erro comum:** trocar uma consulta apenas porque “SQL parece mais rápido”. A linguagem usada não garante plano, índice, seletividade ou menor custo.

**Checagem:** a escolha reduz surpresa e deixa claro como validar o resultado? Se não, a fronteira ainda precisa de justificativa ou simplificação.

## Microtópico 3 — Exija evidência antes de otimizar
Quando houver problema de desempenho, reproduza-o com dados representativos e compare a mesma operação. Colete SQL emitido, parâmetros sem expor dados sensíveis, quantidade de consultas, linhas e campos retornados, latência e plano de execução do banco. No PostgreSQL, EXPLAIN mostra estimativas do plano; EXPLAIN ANALYZE executa a consulta e inclui medições reais, portanto deve ser usado com atenção em comandos que alteram dados.

Compare hipóteses verificáveis: projeção menor, índice adequado, estratégia de relação, paginação, query builder ou SQL explícito. Registre ambiente, conjunto de dados e limites da medição. Uma melhoria observada em um banco e volume não é prova universal de que a solução será mais rápida em qualquer cenário.

**Exemplo:** se uma consulta ORM está lenta, primeiro verifique se o gargalo é N+1, volume excessivo, plano inadequado ou contenção. Só então compare uma reescrita; confira que ela continua retornando os mesmos resultados e respeita as invariantes.

**Erro comum:** usar somente o tempo de uma execução local como benchmark. Cache, concorrência, estado do banco e volume alteram o resultado.

**Checagem:** que evidência sustenta a troca? Um caso reproduzível, uma métrica comparável e confirmação de correção funcional.

## Microtópico 4 — Mantenha fronteira, segurança e contrato
Concentre o acesso a dados em uma fronteira compreensível, como repositório ou módulo de persistência, sem esconder do restante do time as decisões importantes. Documente a razão para uma exceção ao caminho usual, a forma de executar a consulta, suas premissas e como detectar regressões. Use testes para confirmar resultados, cardinalidade importante e comportamento transacional; use medições para avaliar desempenho.

SQL explícito também precisa de parâmetros vinculados para valores externos. Não concatene entradas não confiáveis. Se uma ordenação ou identificador for dinâmico, valide-o por uma lista permitida, já que parâmetros de consulta representam valores, não nomes de coluna. Preserve constraints e migrations no banco, mesmo quando a aplicação valida os mesmos dados.

**Exemplo:** um módulo de relatórios expõe uma função com nome e retorno definidos, executa SQL parametrizado e tem teste para o caso sem resultados, o caso típico e um volume maior. A justificativa informa qual necessidade específica levou ao SQL.

**Erro comum:** chamar a consulta bruta diretamente de vários pontos da aplicação ou deixar sua assinatura sem contrato. Isso espalha conhecimento de persistência e torna mudanças mais arriscadas.

**Checagem:** outra pessoa consegue entender por que a exceção existe, testar seu resultado e alterar o banco sem procurar SQL escondido em vários módulos?

## Resumo
- Escolha por operação, começando pelo requisito, pelas invariantes e pelo volume esperado.
- API ORM, query builder e SQL explícito são opções; nenhuma é automaticamente mais correta ou rápida.
- Troque uma implementação com base em evidência repetível e verifique que o comportamento continua correto.
- Mantenha consultas específicas parametrizadas, documentadas e concentradas em uma fronteira de acesso a dados.

## Quiz
1. **Múltipla escolha —** um CRUD comum está claro na API do ORM e não há evidência de problema. Qual é o próximo passo mais maduro?  
   A) Reescrever tudo em SQL para evitar abstrações.  
   B) Manter a API atual e observar o comportamento relevante.  
   C) Criar uma segunda implementação e escolher em produção.  
   **Resposta:** B. A API já representa a operação; reescrita sem necessidade aumenta manutenção sem demonstrar benefício.

2. **Verdadeiro ou falso —** uma consulta em SQL explícito será mais rápida que a consulta equivalente do ORM.  
   **Resposta:** falso. O plano e o custo dependem da consulta, dos dados, dos índices, do banco e da execução; a sintaxe de origem não comprova desempenho.

3. **Cenário —** uma consulta ORM demora em ambiente com muitos registros. Cite duas evidências a coletar antes de reescrevê-la.  
   **Resposta esperada:** SQL emitido e parâmetros seguros; plano de execução; quantidade de consultas; volume de linhas/campos; latência medida em condições descritas. Duas evidências pertinentes com contexto bastam.

4. **Resposta curta —** quando um query builder pode ser uma escolha intermediária?  
   **Resposta esperada:** quando a consulta precisa de composição, joins ou filtros dinâmicos que ficam difíceis na API simples do ORM, mas a integração com a ferramenta ainda facilita composição, parâmetros ou manutenção.

5. **Identifique o risco —** a aplicação monta uma cláusula ORDER BY concatenando texto vindo da URL. Qual correção é necessária?  
   **Resposta:** não concatenar diretamente; mapear as opções aceitas para identificadores fixos por allowlist. Parâmetros vinculados protegem valores, mas não substituem validação de nomes de coluna/ordenação.

## Atividades práticas

### Atividade 1 — Registro de decisão por operação
**Objetivo:** aplicar critérios consistentes a duas consultas com necessidades diferentes.

**Passos:**
1. Escolha no projeto uma operação CRUD comum e uma leitura mais específica, como um relatório.
2. Para cada operação, registre resultado esperado, invariantes, volume aproximado e requisitos de consistência.
3. Escolha API do ORM, query builder ou SQL explícito para cada uma.
4. Escreva uma justificativa curta incluindo benefício, custo de manutenção e risco residual.
5. Faça uma revisão por pares: quem revisa deve conseguir explicar a decisão sem recorrer a “sempre” ou “nunca”.

**Dica:** se as duas operações receberem a mesma escolha, isso pode estar correto; a justificativa e as necessidades devem sustentar a decisão.

**Solução de referência:** CRUD comum fica na API ORM quando esta expressa bem o caso; a consulta específica usa query builder ou SQL apenas se a composição, recurso ou evidência justificar. O registro explicita contrato, custo e motivo, sem transformar preferência em regra universal.

**Rubrica:** 0 — escolhas sem relação com os requisitos; 1 — escolhas plausíveis, mas justificativa ou risco incompletos; 2 — requisitos, escolha, custo e risco explicados para ambas as operações.

### Atividade 2 — Diagnóstico antes da otimização
**Objetivo:** usar evidências para escolher se e como mudar uma leitura existente.

**Passos:**
1. Rode uma consulta do projeto com conjunto de dados conhecido e registre ambiente e condições.
2. Inspecione SQL emitido, parâmetros sem valores sensíveis, número de consultas e volume de dados retornado.
3. Se o banco for PostgreSQL, examine EXPLAIN; use EXPLAIN ANALYZE somente sabendo que a instrução será executada.
4. Formule uma hipótese concreta e implemente uma alternativa pequena, como reduzir projeção, corrigir N+1 ou ajustar a consulta.
5. Compare correção funcional e medições nas mesmas condições; anote o que a comparação não permite concluir.

**Dica:** não use dados de produção ou comandos mutáveis em EXPLAIN ANALYZE sem ambiente e procedimento apropriados.

**Solução de referência:** um registro antes/depois reproduzível apresenta consulta e dados de teste, explica a hipótese, comprova resultado equivalente e compara uma métrica pertinente sem declarar vitória universal.

**Rubrica:** 0 — troca baseada apenas em opinião ou tempo isolado; 1 — evidência coletada, mas comparação ou correção funcional ausente; 2 — hipótese, comparação controlada, resultado equivalente e limite da conclusão registrados.

### Atividade 3 — Exceção de persistência sustentável
**Objetivo:** criar uma consulta especializada sem espalhar fragilidade pelo projeto.

**Passos:**
1. Identifique uma consulta que a API escolhida não expressa bem ou um recurso específico que o projeto realmente exige.
2. Encapsule-a no módulo de acesso a dados com parâmetros vinculados e retorno/contrato explícitos.
3. Se a escolha for ORM ou query builder em vez de SQL, registre por que essa abstração é suficiente.
4. Adicione verificações para resultado típico, ausência de resultados e regra de integridade relevante.
5. Documente premissas, decisão, custo de manutenção e como perceber uma regressão.

**Dica:** não crie uma exceção apenas para cumprir a atividade; se não houver caso real, use um exemplo controlado e marque-o como demonstrativo.

**Solução de referência:** a consulta ou operação está concentrada, segura e testável; sua interface não vaza detalhes desnecessários; a decisão registra o motivo e não duplica implementação sem necessidade.

**Rubrica:** 0 — entrada concatenada ou lógica espalhada sem contrato; 1 — consulta segura, mas faltam teste, justificativa ou limite; 2 — fronteira clara, parâmetros corretos, comportamento verificado e decisão documentada.

## Critério de conclusão
Apresente duas decisões contextualizadas entre API ORM, query builder e SQL explícito; sustente pelo menos uma delas com evidência ou inspeção reproduzível; explique contrato, risco e custo de manutenção de cada escolha. A maturidade está na qualidade do raciocínio e da validação, não em maximizar o uso de uma ferramenta.
