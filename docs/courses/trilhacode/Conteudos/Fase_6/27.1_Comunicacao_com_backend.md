## Objetivo
Consumir a API REST do curso a partir da interface React, respeitando contratos de requisição, autenticação, paginação e segurança; tratar falhas de rede e HTTP e impedir que resposta obsoleta substitua dados atuais.

## Teoria

## Microtópico 1 — Requisição e resposta seguem o contrato da API

Antes de chamar o backend, confirme método, rota, parâmetros, headers, formato do corpo, autenticação e esquema da resposta. A interface não deve inventar nomes de campo nem pressupor que todos os endpoints respondem JSON. O contrato também define paginação, códigos de status e formato de erro.

fetch retorna uma Promise com Response quando recebe uma resposta HTTP, mesmo que o status seja 401, 404 ou 500. Verifique response.ok ou response.status antes de tratar o corpo como sucesso. Problemas de rede, bloqueio CORS e cancelamento podem rejeitar a Promise; esses casos não são a mesma coisa que uma resposta HTTP de erro.

Nem toda resposta tem corpo JSON: 204 No Content não deve ser processada com response.json(). Se o contrato retorna JSON, valide o resultado ao decodificar; se retorna erro estruturado, leia com cuidado e converta para uma mensagem/modelo adequado à UI. Evite mostrar stack trace, cabeçalho sensível ou conteúdo interno do servidor à pessoa usuária.

```js
async function loadOrders(url, signal, accessToken) {
  const headers = { Accept: "application/json" };

  if (accessToken) {
    headers.Authorization = "Bearer " + accessToken;
  }

  const response = await fetch(url, { headers, signal });

  if (!response.ok) {
    throw new Error("Falha HTTP: " + response.status);
  }

  if (response.status === 204) {
    return null;
  }

  return response.json();
}
```

O exemplo é um ponto de partida, não um cliente universal: a API pode não usar bearer, pode exigir Content-Type somente em requisições com corpo ou pode ter esquema de erro próprio. Evite esconder comportamentos diferentes numa função genérica antes de entender os endpoints usados.

## Microtópico 2 — Autenticação e credenciais exigem decisão explícita

Quando o contrato usar bearer token, envie-o no header Authorization: Bearer, nunca na URL. URLs podem aparecer em histórico, logs, métricas, captura de tela e Referer. Não exponha segredos de servidor no bundle do frontend: qualquer valor enviado ao navegador pode ser inspecionado por quem o utiliza.

Escolha de armazenamento depende do desenho de sessão e da ameaça:
- Manter um access token apenas em memória reduz persistência após recarga, mas a aplicação precisa lidar novamente com a sessão ao recarregar.
- localStorage é acessível a qualquer JavaScript executado na origem; uma falha XSS pode ler tokens. Não o trate como cofre para credenciais sensíveis.
- Cookie HttpOnly impede leitura direta pelo JavaScript da página, mas o navegador envia cookies automaticamente. Operações autenticadas por cookie precisam de defesa contra CSRF, configuração Secure/SameSite adequada ao fluxo e validação no servidor.

Não há uma escolha universal que o frontend possa tomar sem o backend. Siga o contrato da aplicação e documente o compromisso entre XSS, CSRF, persistência e experiência. Um bearer token no header criado por JavaScript não é enviado automaticamente pelo navegador como cookie, mas ainda pode ser roubado se o código da origem for comprometido.

Trate 401 como não autenticado ou credencial expirada conforme o contrato; 403 significa que a identidade não tem permissão para a operação. Não faça refresh ou novo login em loop para qualquer erro: limite tentativas, proteja ações não idempotentes e encerre/renove a sessão segundo política definida.

## Microtópico 3 — Integração React acompanha a requisição vigente

Ao iniciar uma requisição, a interface pode precisar indicar carregamento, resultado e erro. Mantenha esses estados coerentes com a intenção atual: se a pessoa muda o filtro de “abertas” para “concluídas”, uma resposta lenta do filtro anterior não deve substituir a nova lista.

Se a requisição é sincronização declarada a partir de props/estado, um Effect pode iniciar a chamada com AbortController e abortá-la na limpeza quando a dependência mudar ou o componente sair. A aplicação deve distinguir cancelamento esperado de falha visível. Também é possível ignorar o resultado antigo com um marcador; cancelar economiza trabalho quando o serviço suporta signal, mas não garante que o servidor não tenha processado a operação.

Se a chamada acontece por ação explícita de envio, o handler do formulário/botão normalmente inicia a operação; não use Effect apenas para reagir a um booleano de clique duplicado. Para fluxos com cache, deduplicação, invalidação ou muitas requisições concorrentes, siga a camada de dados já adotada pelo projeto em vez de improvisar outra.

Cuidado com mutações: cancelar uma requisição de leitura costuma ser seguro; cancelar no navegador não desfaz um POST que o servidor já recebeu. Para ações de escrita, previna envio duplicado com estado e contrato apropriados, e use idempotency key se a API oferecer suporte.

## Microtópico 4 — Paginação, filtros e ordem dos resultados

Siga o formato de paginação do backend. Paginação por página pode receber page e limit e retornar total; cursor pode retornar próximo cursor e hasMore. Cursor é opaco se o contrato o define assim: repasse o valor recebido sem inventar cálculo a partir dele.

A URL deve refletir filtros que precisam ser compartilhados ou restaurados ao voltar à página; codifique parâmetros corretamente. Defina limite máximo aceito pela API e trate lista vazia, primeira/última página e resultado que encolhe após exclusão. Se o total muda enquanto a pessoa navega, a página atual pode ficar fora do intervalo; ajuste com base nos metadados do servidor.

Filtro, ordenação, página e resultados são relacionados. Quando o filtro muda, normalmente recomece da primeira página e inicie requisição para o novo conjunto. Mantenha a resposta associada aos parâmetros que a produziram; descarte resultado atrasado de uma combinação anterior. Não derive número de páginas de uma estimativa quando o contrato fornece metadados oficiais.

## Microtópico 5 — CORS e erros são parte da integração

CORS é uma política aplicada pelo navegador com base nos headers da resposta do servidor. O frontend não concede a si mesmo permissão para acessar outra origem. Para uma requisição cross-origin, backend/gateway precisa autorizar a origem e os headers/métodos necessários. Se credenciais de cookie forem usadas, o servidor precisa configurar permissões compatíveis; credenciais não podem ser combinadas com uma origem curinga.

Não tente corrigir erro CORS com mode: no-cors, desativando segurança do navegador ou colando segredo em outro header aleatório. Uma resposta opaca não permite à aplicação ler o conteúdo como se a política tivesse sido resolvida. Confirme URL, origem, preflight, método, headers e resposta do servidor na aba de rede; em desenvolvimento, um proxy local pode simplificar a origem, mas a configuração do servidor continua necessária em produção.

Modele estados de forma útil: carregando, sucesso vazio, sucesso com dados, não autenticado, sem permissão, erro de validação, limite excedido, falha temporária do servidor e falha de rede podem exigir mensagens/ações distintas. Só tente novamente automaticamente quando a operação e a política permitirem. GET idempotente pode admitir retry limitado com espera progressiva; não repita automaticamente escrita que pode criar cobrança ou duplicidade sem suporte de idempotência.

## Resumo
- Confirme contrato de método, URL, headers, corpo, status e formato de resposta antes de integrar.
- fetch não rejeita automaticamente por status HTTP; diferencie erro HTTP, rede, CORS e cancelamento.
- Credenciais seguem arquitetura e threat model; token não vai na URL nem segredo de servidor no bundle.
- Trate 401 e 403 segundo seus significados e evite ciclos de renovação/retry ilimitados.
- Sincronize filtros, paginação e respostas; descarte resultado obsoleto sem presumir que abortar desfaz uma escrita.
- CORS exige configuração da origem servidora; o cliente não contorna a política.

## Quiz

1. **Interpretação de fetch:** fetch recebe status 500 e resolve Response. Isso significa que a operação foi bem-sucedida?  
   **Resposta esperada:** não. A Promise pode resolver para status HTTP de erro; a aplicação verifica response.ok/status e converte o corpo conforme o contrato.

2. **Segurança:** por que um bearer token não deve ser colocado como parâmetro da URL?  
   **Resposta esperada:** URLs podem ser registradas ou expostas em histórico, logs, telemetria e Referer; o contrato bearer prevê header Authorization.

3. **Autorização:** qual diferença prática entre 401 e 403?  
   **Resposta esperada:** 401 indica ausência ou invalidade de autenticação conforme o serviço; 403 indica que a identidade não tem permissão para aquele recurso/operação. O cliente responde conforme a política, sem refresh infinito.

4. **Concorrência:** filtro “abertas” inicia primeira requisição; em seguida a pessoa escolhe “concluídas”, cuja resposta chega antes. O que fazer com a primeira resposta?  
   **Resposta esperada:** cancelá-la quando possível ou ignorá-la; não pode substituir os resultados do filtro vigente.

5. **Diagnóstico:** a página funciona em desenvolvimento com proxy e falha no navegador ao chamar uma API em outra origem em produção. Desativar CORS no fetch resolve?  
   **Resposta esperada:** não. CORS é autorizada pela resposta/configuração do servidor. Verifique origem, preflight, método, headers e configuração do backend/gateway.

## Atividades práticas

### Atividade 1 — Construa um cliente de lista que modele erros

**Desafio:** implemente a busca paginada de pedidos obedecendo ao contrato da API e sem confundir erro HTTP com falha de rede.

**Passos:**
1. Registre método, URL, parâmetros, headers, autenticação e formato de resposta do endpoint de pedidos.
2. Envie Accept e o header de autenticação somente se o mecanismo e o contrato os exigirem.
3. Verifique response.ok/status antes de assumir sucesso; trate resposta sem corpo se o endpoint puder retornar 204.
4. Converta erros estruturados conhecidos em estados seguros para a UI e mantenha uma categoria separada para rede/CORS/JSON inválido.
5. Teste em ambiente local 200 com dados, 200 vazio, 401, 403, 500 e falha de rede; confira que URL não contém token.

**Dica:** não apresente texto técnico do backend sem filtragem e não tente interpretar como JSON toda resposta.

**Solução de referência:** função recebe page/filter/signal e credencial disponível; monta query conforme contrato; faz fetch; checa status; trata JSON de erro somente quando o corpo é parseável; converte 401 e 403 separadamente e retorna dados e metadados de sucesso. Falha de rede e abort são estados diferentes. Token só no header bearer se esse for o contrato.

**Rubrica:** request corresponde ao contrato; erro HTTP não passa como sucesso; 204 não é parseado como JSON; credencial não aparece em URL; rede e abort são reconhecidos; mensagem da UI não vaza detalhes internos.

### Atividade 2 — Impeça que resposta antiga substitua a atual

**Desafio:** conecte busca por filtro à tela React e simule que a primeira requisição demora mais que a segunda.

**Passos:**
1. Defina estado de resultado e parâmetro vigente (filtro/página) sem duplicar dados derivados.
2. Inicie a requisição para o parâmetro atual e passe signal de AbortController, ou implemente marcador que ignore resultado que perdeu validade.
3. Limpe/aborte a requisição anterior quando o parâmetro mudar ou a tela desmontar.
4. Não mostre erro comum para AbortError de requisição que ficou obsoleta; preserve estado de carregamento correto da nova busca.
5. Simule “abertas” lento e “concluídas” rápido; confirme que a lista final corresponde ao filtro atual.

**Dica:** abortar client-side economiza trabalho quando possível; use a checagem de validade também quando a operação subjacente não pode ser interrompida.

**Solução de referência:** Effect depende do filtro e da página, cria controller, inicia GET e só grava a resposta da execução atual; cleanup aborta ou marca como ignorada. A segunda busca representa os dados ativos; resposta atrasada não altera resultado nem estado de erro. Requisição de escrita acionada por usuário não deve ser tratada como leitura cancelável.

**Rubrica:** request relaciona-se aos parâmetros atuais; cleanup ocorre em troca/desmontagem; resposta antiga não altera UI; cancelamento não aparece como falha de usuário; limites de AbortController explicados.

### Atividade 3 — Escolha autenticação, paginação e CORS para um fluxo

**Desafio:** integre endpoint autenticado que usa paginação cursor-based e pode ser chamado em origem diferente em produção.

**Passos:**
1. Confirme contrato de autenticação: bearer no header ou cookie de sessão; não invente mecanismo.
2. Se for cookie, registre flags/configuração a confirmar com backend e defesa CSRF; se for bearer, determine como o frontend obtém token sem embutir segredo de servidor.
3. Leia e repasse cursor conforme contrato, respeitando hasMore e limit.
4. Liste configuração CORS do servidor para origem, método, Authorization ou credenciais que o navegador realmente enviará.
5. Faça uma chamada de primeira página, próxima página, sessão expirada e sem permissão; defina se retry é seguro e limitado.

**Dica:** um cursor não é necessariamente um número de página. E CORS não substitui autenticação nem autorização.

**Solução de referência:** usar exatamente o transporte de credencial definido pela arquitetura, tratar implicações de XSS ou CSRF do mecanismo, armazenar/gerar token conforme política acordada e nunca como segredo no bundle; encaminhar o cursor opaco recebido e parar quando hasMore for falso; configurar CORS no gateway/API para origem e headers reais; 401 segue renovação/logout controlado, 403 não faz login automático, retry limita-se a operação segura e política definida.

**Rubrica:** mecanismo de autenticação coincide com backend; ameaça de armazenamento declarada; cursor não é calculado pelo cliente; CORS é configurado no servidor para origens específicas; 401/403 e retry têm comportamento distinto e limitado.

## Critério de conclusão
Demonstre uma listagem paginada autenticada com status HTTP tratados, UI coerente durante carregamento/falhas e resposta obsoleta descartada; justifique credencial, CORS e política de retry conforme o contrato sem expor token.
