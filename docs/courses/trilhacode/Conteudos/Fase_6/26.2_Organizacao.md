## Objetivo
Organizar uma interface React por responsabilidades e fluxo de dados; escolher entre props, composição, levantamento de estado, custom Hooks e Context conforme o alcance e a finalidade do compartilhamento.

## Teoria

## Microtópico 1 — Organize pelo fluxo e pela responsabilidade

Uma árvore React descreve como componentes compõem a interface e trocam dados. Comece perguntando o que cada parte faz: apresentar uma informação, controlar uma interação, coordenar uma tela ou aplicar uma regra reutilizada. Dê nomes a componentes por seu papel no produto e mantenha juntos arquivos que mudam pelo mesmo motivo, conforme o tamanho e as convenções reais do projeto.

Uma divisão comum separa componentes visuais reutilizáveis, componentes de tela que coordenam estado e operações e funções de domínio que implementam regras sem conhecer detalhes visuais. Isso é uma heurística, não uma estrutura obrigatória. Uma aplicação pequena pode ser mais clara com poucos arquivos; uma área grande pode se beneficiar de pastas por funcionalidade. Pasta por componente ou camada só vale se torna navegação e mudanças mais simples.

Evite um componente gigante com muitos modos, várias responsabilidades e contratos difíceis de entender. Também evite fragmentar cada parágrafo em um componente. Extraia quando uma parte tem significado próprio, aparece em mais de um contexto, precisa de comportamento isolado ou mudou por motivos diferentes.

## Microtópico 2 — Composição e ownership deixam dados explícitos

Props são a forma explícita de o pai passar informação e funções ao filho. Se uma propriedade só atravessa um ou dois níveis e continua fazendo parte do contrato, passá-la é frequentemente mais simples do que introduzir Context.

Composição permite ao componente contêiner receber conteúdo por children. Assim, um componente de layout pode cuidar de borda e espaçamento sem conhecer o conteúdo interno. Use slots com props específicas quando o componente precisa organizar regiões como header, actions ou sidebar.

Se dois componentes precisam coordenar o mesmo valor, mantenha uma única fonte de verdade. Remova estado duplicado dos filhos, mova-o ao ancestral comum mais próximo e passe valor e callbacks por props. Não mova todo estado para o topo da aplicação: estado de um campo ou painel pode continuar próximo de quem o usa.

```jsx
function Panel({ title, children }) {
  return (
    <section className="panel">
      <h2>{title}</h2>
      {children}
    </section>
  );
}

<Panel title="Preferências">
  <ThemePicker />
</Panel>
```

O Panel conhece a estrutura compartilhada, enquanto ThemePicker fornece o conteúdo. Essa composição pode evitar passar props por um componente intermediário que não usa os dados.

## Microtópico 3 — Custom Hooks compartilham lógica

Um custom Hook extrai lógica que usa Hooks e pode ser reutilizada por mais de um componente. Seu nome começa com use seguido de um nome descritivo; ele pode receber parâmetros e retornar valores ou funções. Um custom Hook é uma função chamada no nível superior de um componente ou de outro Hook, respeitando as regras de Hooks.

Cada chamada do mesmo Hook executa sua própria lógica e mantém sua própria instância de estado. Duas chamadas de useField em campos diferentes não compartilham o texto digitado; elas reutilizam a forma de controlar o campo. Para compartilhar o mesmo valor, levante o estado ao pai ou conecte as partes a uma fonte compartilhada apropriada.

Extraia quando a lógica representa um conceito reutilizável — por exemplo, estado de formulário com validação comum, acompanhar online/offline ou assinar uma fonte externa. Não extraia apenas para esconder algumas linhas ou dar prefixo use a uma função pura que não chama Hooks. Para regra sem estado React, uma função JavaScript comum costuma ser mais clara.

## Microtópico 4 — Context alcança descendentes quando props viram ruído

Context disponibiliza um valor a componentes descendentes sem passá-lo explicitamente por todos os níveis intermediários. É útil quando muitos pontos da árvore precisam do mesmo dado de ambiente, como tema, idioma ou usuário autenticado. Antes de usar Context, avalie se props explícitas, children ou levantamento de estado já deixam o fluxo simples.

Crie o Context, forneça um valor num ancestral adequado e leia-o com useContext no componente consumidor. O provider deve envolver os consumidores; um componente não consegue ler com useContext um provider que ele próprio retorna abaixo de si. Quando não há provider correspondente, o valor padrão de createContext é usado, então escolha esse padrão conscientemente.

Context não é automaticamente estado global, store remota ou substituto de toda prop. O estado pode continuar local ao provider. Quando o valor fornecido muda, componentes que leem aquele Context são atualizados; Contexts muito amplos com dados que mudam por motivos distintos podem acoplar consumidores e trabalho desnecessários. Separe valores quando isso clarifica quem depende de quê e meça antes de introduzir otimizações.

```jsx
const ThemeContext = createContext("light");

function App() {
  return (
    <ThemeContext.Provider value="dark">
      <Page />
    </ThemeContext.Provider>
  );
}

function ThemeLabel() {
  const theme = useContext(ThemeContext);
  return <p>Tema atual: {theme}</p>;
}
```

O contexto percorre a árvore para consumidores; componentes intermediários não precisam encaminhar theme como prop se não o utilizam.

## Resumo
- Organize componentes conforme responsabilidade e fluxo de mudança, sem impor uma pasta por componente.
- Props mantêm fluxo explícito; children compõe conteúdo sem acoplar o contêiner a detalhes internos.
- Levante estado compartilhado ao ancestral comum mais próximo, mantendo cada fonte de verdade única.
- Custom Hooks reutilizam lógica com estado, não compartilham automaticamente a mesma instância.
- Context é útil para valores consumidos profundamente; mudanças atualizam consumidores e exigem escopo bem pensado.

## Quiz

1. **Escolha de fluxo:** uma prop passa por dois componentes que não a usam até chegar ao único consumidor. Qual alternativa pode manter o fluxo explícito com menos encaminhamento?  
   **Resposta esperada:** compor o consumidor como children do componente contêiner, quando a estrutura da tela permitir, ou usar Context se a passagem profunda for realmente recorrente. A escolha depende da árvore e do contrato.

2. **Estado compartilhado:** duas chamadas ao mesmo custom Hook useField controlam dois campos. Elas compartilham o valor por terem o mesmo nome de Hook?  
   **Resposta esperada:** não. Cada chamada mantém estado independente; para compartilhar um valor, ele precisa ter dono comum ou fonte compartilhada.

3. **Organização:** dois painéis precisam garantir que só um esteja aberto por vez. Onde deve ficar o estado isOpen?  
   **Resposta esperada:** no ancestral comum que coordena os painéis, passando valor e callbacks aos filhos, mantendo uma única fonte de verdade.

4. **Context:** tema é usado por componentes em níveis profundos e muitos elementos não o encaminham nem consomem. Que vantagem Context oferece?  
   **Resposta esperada:** disponibiliza o valor aos descendentes que precisam dele sem exigir que todos os intermediários repassem a prop.

5. **Custo de atualização:** o provider passa um objeto com autenticação, formulário e dados de busca para todos os consumidores. Qual risco de organização investigar?  
   **Resposta esperada:** responsabilidades e frequências de mudança diferentes estão acopladas em um Context amplo; mudanças podem atualizar consumidores que não precisam do dado. Separar Contexts por finalidade/consumidor pode clarear o desenho, validando o efeito no projeto.

## Atividades práticas

### Atividade 1 — Defina árvore e dono de cada dado

**Desafio:** organize uma tela de projetos com cabeçalho, filtro de busca, lista de cartões e painel de detalhes. Busca altera a lista e selecionar cartão altera o painel.

**Passos:**
1. Desenhe os componentes da tela e indique quais são de layout, apresentação e coordenação.
2. Marque quem é dono do texto de busca, da lista de projetos e do projeto selecionado.
3. Passe por props valores e callbacks até os consumidores reais.
4. Use children para uma região de conteúdo se um contêiner de layout não precisa conhecer seus detalhes.
5. Justifique uma decisão de manter estado local e outra de elevar estado.

**Dica:** filtro pertence perto da lista; seleção precisa estar em ancestral comum se lista e painel de detalhes a usam.

**Solução de referência:** uma página coordena a lista/projetos e projeto selecionado porque ambas as regiões dependem da seleção; o campo de busca pode ficar com a lista se nenhum outro componente precisa dele. Cartão recebe projeto e callback de seleção; painel de detalhes recebe seleção. O layout recebe conteúdo por children e não encaminha dados que não usa.

**Rubrica:** cada dado tem um dono claro; valores compartilhados têm uma fonte; callbacks seguem até o lugar da ação; composição reduz acoplamento; nenhuma abstração é justificada só por convenção.

### Atividade 2 — Extraia lógica em custom Hook sem compartilhar estado por engano

**Desafio:** dois formulários repetem estado de texto, alteração, limpeza e validação obrigatória. Extraia uma lógica comum chamada useRequiredField.

**Passos:**
1. Identifique o comportamento realmente igual nos dois campos e diferenças que devem ser parâmetros.
2. Escreva Hook que use state para valor e exponha value, onChange, reset e erro/validade.
3. Use o Hook uma vez para nome e outra para e-mail.
4. Mostre que limpar ou digitar em um campo não altera o outro.
5. Mantenha validação específica de formato de e-mail fora do Hook genérico, a menos que a interface aceite estratégia explícita para ela.

**Dica:** repetir o Hook cria duas instâncias independentes; o Hook organiza lógica, não funciona como store compartilhada.

**Solução de referência:** useRequiredField recebe valor inicial ou regra necessária e retorna estado e handlers para uma instância; nome e e-mail fazem chamadas independentes. A validação de presença pode ser reutilizada, enquanto a validação de formato pertence ao domínio do e-mail. Nenhum Context é necessário porque cada formulário controla seu campo localmente.

**Rubrica:** Hook começa com use e chama Hooks somente no nível superior; lógica comum foi extraída com parâmetros explícitos; estados permanecem independentes; regra específica não se perde; extração facilita reuso/compreensão.

### Atividade 3 — Decida entre props, composição e Context

**Desafio:** avalie três cenários: um aviso usado só dentro de uma tela; um tema lido em muitos componentes profundos; e uma prop de título encaminhada por quatro wrappers que não a utilizam.

**Passos:**
1. Para cada cenário, identifique produtores e consumidores e quantos níveis atravessa.
2. Escolha props, estado elevado, children/slots ou Context.
3. Selecione um Context para implementar com createContext, provider e useContext.
4. Separe Contexts quando valores têm consumidores ou frequências de mudança claramente distintas; explique o custo de fazê-lo.
5. Descreva como verificaria se a organização melhorou clareza sem criar complexidade desnecessária.

**Dica:** não mova o aviso de uma tela para uma store global. Para o título atravessando wrappers, composição pode remover a necessidade de encaminhá-lo.

**Solução de referência:** aviso local permanece em estado da tela; tema profundo pode ser Context de tema; título pode ser passado como children ou slot ao wrapper que o organiza, evitando repasse por intermediários. Separar dados de autenticação e busca pode reduzir acoplamento se os consumidores e ciclos de atualização forem diferentes, mas só se houver benefício prático.

**Rubrica:** escolha considera alcance e consumidores reais; estado fica no menor dono adequado; Context tem provider e consumidores corretos; composição é considerada; trade-off de manutenção e atualização foi explicado.

## Critério de conclusão
Apresente uma árvore de componentes com responsabilidade e dono dos dados, extraia lógica com custom Hook sem confundir lógica compartilhada com estado compartilhado e justifique quando props, composição ou Context dão o fluxo mais claro.
