# 31.4 — Projeto incremental da fase

- key: 31.4
- tipo: projeto
- carater: obrigatorio
- profundidade: alta
- estimativa_minutos: 600
- tags: [#web, #qualidade]
- status: rascunho

## Objetivo
Evoluir o projeto acumulado do Trilho A, iniciado em 3.5, com uma fatia frontend em React e TypeScript conectada à API real da Fase 5, cobrindo estados de interface, testes de comportamento e uma decisão de performance documentada.

## Escopo e relação com o Trilho B
Continue no mesmo projeto escolhido em 3.5 e use a API construída na Fase 5 como contrato e backend. Implemente uma fatia central e limitada do produto, sem reconstruir todas as funcionalidades. Este projeto forma a base comum do Trilho A.

A unidade 31.5 é uma entrega separada: nela, a pessoa escolhe uma ideia do Trilho B e demonstra o problema técnico específico desse tipo. Não copie toda a implementação desta unidade como se ela fosse a entrega especializada de 31.5. Reaproveite o que for realmente comum, mas mantenha requisitos e evidências próprios para cada projeto.

Antes de implementar, identifique quem usa a fatia, qual ação principal realizará, quais endpoints existentes atendem ao fluxo e que comportamento deve ocorrer em sucesso e falha. Não crie uma API fictícia para declarar integração concluída. Mocks são úteis para reproduzir estados, mas a etapa de integração deve também alcançar a API de teste da Fase 5.

## Princípios de implementação
- Use React com TypeScript e mantenha uma fronteira HTTP identificável entre interface e API.
- Tipos descrevem o contrato, mas não validam automaticamente respostas em runtime; trate respostas externas conforme o nível de validação adotado no curso.
- Mantenha estado de interface local separado do cache de dados remotos e evite cópias concorrentes sem sincronização.
- Exiba carregamento, erro, vazio e sucesso conforme o contrato da API; ofereça retry apenas quando a operação puder ser repetida com segurança.
- Preserve teclado, foco, labels e mensagens compreensíveis durante os fluxos principais.
- Use configuração de ambiente de exemplo sem credenciais reais ou valores secretos no bundle cliente.
- Registre comandos, condições de execução e limites de cada evidência para que outra pessoa consiga reproduzir a entrega.

## Entregas do projeto

### Marco 1 — Delimite uma fatia vertical e conecte a API
**Objetivo:** provar que uma jornada mínima do Trilho A usa o contrato real da Fase 5.

**Tarefas:**
1. Releia o brief e a ideia selecionada em 3.5; escolha uma tarefa central que caiba nesta fase.
2. Desenhe o fluxo curto entre pessoa, tela, cliente HTTP e endpoint existente. Registre método, rota, parâmetros, formato relevante e resposta esperada.
3. Configure a URL da API por ambiente de forma segura; forneça apenas um arquivo de exemplo com valores fictícios.
4. Implemente uma rota ou tela React tipada com uma leitura real e a ação principal mais representativa dessa fatia.
5. Gere build e percorra o fluxo no ambiente de integração da API, registrando resultado e qualquer limite conhecido.

**Evidências:** brief de escopo atualizado, mapa de requisição e resposta, código da tela e cliente HTTP, comandos/configuração de exemplo e registro reproduzível do fluxo contra a API de teste.

**Verificação:** outra pessoa consegue identificar qual endpoint alimenta a tela, iniciar frontend e API com as instruções e concluir a tarefa sem usar uma fixture como prova de integração.

**Aceite:** a fatia permanece dentro do projeto escolhido; pelo menos uma chamada real chega à API da Fase 5; dados e erros são tratados pelo cliente tipado; não há credenciais reais versionadas nem expostas no cliente.

### Marco 2 — Complete estados e acessibilidade do fluxo
**Objetivo:** tornar o comportamento da fatia compreensível em todos os estados relevantes.

**Tarefas:**
1. Implemente e documente como reproduzir carregamento, sucesso com dados, sucesso vazio, erro e nova tentativa.
2. Inclua retry manual ou automático somente quando o contrato tornar a repetição segura; não repita escrita não idempotente cegamente.
3. Defina o texto e a ação disponível em cada estado, distinguindo falta legítima de dados de falha da API.
4. Verifique teclado, ordem e visibilidade do foco, labels dos controles e anúncio compreensível das atualizações.
5. Confirme que filtros, seleção ou contexto necessários não desaparecem após uma atualização ou erro recuperável.

**Evidências:** matriz estado → causa → mensagem → ação, demonstração ou capturas dos cinco estados e roteiro de teclado/foco.

**Verificação:** provoque os cenários com handlers ou fixtures controladas; confirme separadamente o fluxo real feliz contra a API de teste. Cada evidência deve dizer se o servidor foi simulado ou real.

**Aceite:** cinco estados são reproduzíveis; vazio não mascara falha; retry respeita idempotência; controles e mensagens permanecem utilizáveis por teclado e tecnologia assistiva.

### Marco 3 — Cubra comportamento e fronteiras com testes
**Objetivo:** aumentar confiança no fluxo sem confundir testes mockados com validação do backend.

**Tarefas:**
1. Escreva testes de componente por comportamento observável para a ação principal e os estados relevantes.
2. Use MSW ou ferramenta equivalente para controlar respostas HTTP, incluindo ao menos sucesso, vazio e falha.
3. Acrescente um fluxo Playwright curto para o caminho central; declare se usa API de teste real ou se intercepta a rede.
4. Quando usar API real, prepare conta e dados isolados e descreva limpeza; nunca use produção.
5. Mostre que uma regressão visível plausível faz ao menos um teste falhar e restaure o comportamento correto.

**Evidências:** comandos e saída de testes, handlers ou fixtures, fluxo de navegador e tabela que enumera o que cada cenário simulou ou alcançou de verdade.

**Verificação:** execute os testes em isolamento e na ordem da suíte; confira que não dependem da rede pública, de dados de outro teste ou de uma conta pessoal.

**Aceite:** testes exercitam interação e resultado visível; mocks ficam na fronteira da API; o fluxo real não é descrito como real quando a rede foi interceptada; regressão simulada é detectada.

### Marco 4 — Meça, revise e entregue a fatia
**Objetivo:** comprovar a qualidade final e comunicar a decisão de performance.

**Tarefas:**
1. Escolha uma interação ou carregamento representativo e registre baseline, ferramenta, dispositivo/viewport, dados, rede e estado de cache.
2. Formule uma hipótese de otimização baseada no perfil ou numa medida relevante e altere uma coisa por vez.
3. Repita a medição em condições equivalentes, compare resultados e verifique funcionalidade, acessibilidade e bundle quando pertinente.
4. Mantenha a mudança somente se o ganho for reproduzível e compensar o custo. Se não houver gargalo ou benefício, reverta e documente a não adoção como resultado.
5. Atualize o README com objetivo da fatia, pré-requisitos, configuração de exemplo, comandos, cenários demonstrados, resultados de teste, método de medição e limitações.
6. Faça uma revisão final do diff e prepare uma demonstração curta do caminho central, incluindo pelo menos um estado de falha ou recuperação.

**Evidências:** perfil ou registro de medida antes/depois, decisão com limites, README reproduzível, revisão final e demonstração da fatia.

**Verificação:** outra pessoa segue o README, executa os cenários no ambiente de teste e consegue distinguir o que foi medido, mockado e conectado à API.

**Aceite:** medida é comparável e ligada à hipótese; otimização sem benefício não é mantida por obrigação; documentação corresponde ao projeto; nenhum estado crítico ou limite da evidência é ocultado.

## Rubrica comum dos marcos
Avalie cada marco de 0 a 4 usando sua evidência e verificação:

| Nota | Descrição |
|---:|---|
| 4 | Entrega completa, reproduzível e aceita; evidências respondem ao objetivo do marco. |
| 3 | Objetivo principal aceito; resta uma lacuna menor de clareza ou documentação que não bloqueia reprodução. |
| 2 | Há implementação parcial, mas falta uma evidência ou verificação importante; o aceite ainda não foi demonstrado. |
| 1 | Entrega difícil de reproduzir, não alcança a fronteira esperada ou contém regressão relevante. |
| 0 | Não há artefato ou evidência avaliável para o marco. |

Cada marco precisa obter ao menos 3 e não pode falhar em seu critério de aceite. Uma nota alta em um marco não compensa uma integração, segurança ou acessibilidade não demonstrada em outro. Credenciais reais, dados pessoais ou uso de produção invalidam o aceite até serem removidos e tratados conforme o procedimento apropriado.

## Resumo
- O projeto continua a ideia iniciada em 3.5 e usa a API real produzida na Fase 5.
- Quatro marcos conduzem da fatia vertical à documentação e evidência final.
- Fixtures/MSW demonstram estados previsíveis; integração real precisa alcançar a API de teste.
- Testes, acessibilidade, política de retry e medição fazem parte do aceite.
- 31.4 entrega a base comum do Trilho A; 31.5 demonstra o problema específico de uma ideia do Trilho B.

## Critério de conclusão
Os quatro marcos obtêm nota mínima 3 e cumprem seus critérios de aceite. A fatia React/TypeScript usa a API real de teste da Fase 5, demonstra cinco estados, possui testes de comportamento com fronteiras claras, preserva acessibilidade básica e apresenta uma decisão de performance fundamentada e documentada.
