# 28.1 — Ferramentas

- tipo: solo

## Objetivo
Escolher e combinar Vite, Zustand e TanStack Query de acordo com suas responsabilidades, sem duplicar estado ou instalar dependências sem necessidade.

## Microtópico 1 — Identifique o problema antes da ferramenta
Comece descrevendo o problema em termos observáveis: iniciar o projeto localmente, gerar arquivos para publicação, compartilhar uma preferência entre telas ou buscar e manter atualizada uma resposta da API. Uma ferramenta é adequada quando resolve esse problema com menos custo e complexidade do que as alternativas já disponíveis.

Não confunda “estado” como uma categoria única. Uma variável temporária de formulário, a preferência de tema escolhida pela pessoa e os dados de uma consulta ao servidor têm ciclos de vida diferentes. Antes de adicionar uma biblioteca, pergunte onde o dado nasce, quem é responsável por atualizá-lo, quanto tempo deve viver e quais componentes precisam observá-lo. Estado local do React pode ser suficiente para uma interação confinada a um componente.

## Microtópico 2 — Use Vite para desenvolvimento e build
Vite fornece o servidor de desenvolvimento e a etapa de build para aplicações web. O servidor ajuda a desenvolver e verificar mudanças; o comando de build gera os artefatos que podem ser publicados em uma hospedagem compatível. Isso não transforma Vite em servidor de produção da aplicação nem em gerenciador de estado.

Os scripts do `package.json` documentam as tarefas disponíveis, como iniciar o servidor e gerar o build. Variáveis de ambiente exigem atenção: valores com prefixo `VITE_` são disponibilizados no código do cliente e entram no bundle durante o build. Portanto, não coloque senhas, tokens privados ou credenciais de banco nessas variáveis. Um valor que precisa permanecer secreto deve ser mantido em um servidor ou serviço seguro, fora do bundle público. Variáveis expostas também são strings e podem precisar de conversão e validação.

O resultado da build precisa ser servido por uma hospedagem configurada para a aplicação. O destino e as regras de fallback para rotas dependem da plataforma de publicação; “o build terminou” não prova por si só que todas as rotas funcionarão em produção.

## Microtópico 3 — Separe estado de interface e estado remoto
**Zustand** mantém estado do cliente que vários componentes precisam compartilhar, como um painel aberto, uma seleção temporária ou uma preferência de interface. A store contém estado e ações; componentes podem selecionar somente o valor de que precisam. Evite transformar toda variável local em estado global: isso aumenta os acoplamentos e torna mais difícil descobrir quem pode alterar um valor.

**TanStack Query** organiza dados assíncronos que vêm de uma fonte externa: executa consultas, mantém cache por chave, acompanha atualizações e oferece mecanismos para sincronizar o cache depois de mutações. A chave deve identificar os dados consultados e incluir as variáveis que mudam a resposta, como identificador, página e filtro. Se a função da consulta usa um parâmetro que altera o resultado, ele precisa participar da identidade da consulta.

Uma regra prática: preferência de ordenação exclusivamente visual pode pertencer ao estado do cliente; uma ordenação que altera a consulta também faz parte dos parâmetros da consulta remota. O mesmo valor pode ter representação em mais de uma camada por motivos distintos, mas precisa haver uma fonte de verdade definida e uma regra de sincronização. Copiar a resposta da API para uma store sem essa política cria caches concorrentes e risco de dados divergentes.

| Necessidade | Onde começar | Motivo |
| --- | --- | --- |
| Campo de busca usado só neste formulário | Estado local do React | Escopo pequeno, sem compartilhamento necessário |
| Painel lateral aberto em várias telas | Store de cliente, se o compartilhamento for real | Estado de interface compartilhado |
| Lista carregada de uma API com cache e atualização | TanStack Query | Estado remoto tem ciclo de busca e sincronização próprio |
| Preferência que deve sobreviver à navegação e ser compartilhável | URL ou persistência deliberada | O requisito define o ciclo de vida e o compartilhamento |
| Projeto sem necessidade que as ferramentas resolvam | Ferramentas existentes | Dependência nova também tem custo de manutenção |

## Microtópico 4 — Combine com fronteiras claras
As ferramentas podem coexistir, desde que cada uma tenha uma responsabilidade clara: Vite prepara desenvolvimento e build; Zustand mantém estado de cliente que realmente precisa ser compartilhado; TanStack Query coordena dados remotos. A consulta pode usar um filtro selecionado na interface, mas a aplicação deve decidir se esse filtro vive na URL, na store ou localmente. Se o filtro altera os resultados, a chave da consulta precisa refletir seu valor atual.

Quando uma mutação altera dados do servidor, escolha como as consultas relacionadas serão atualizadas: invalidar e buscar novamente, atualizar o cache de forma explícita ou combinar estratégias. Faça isso de acordo com o contrato da API e com o comportamento desejado. Evite sincronização improvisada em que um componente altera uma cópia na store e outro continua lendo uma resposta antiga do cache.

Não transporte uma receita de arquitetura sem considerar o projeto. Um framework pode integrar build, rotas ou carregamento de dados com outras ferramentas. Em outro caso, `fetch` e estado local podem atender ao escopo. Aprenda a reconhecer a responsabilidade; a escolha da implementação vem depois do contexto.

## Resumo
- Vite cobre o fluxo de desenvolvimento e a geração do build; ele não mantém estado da interface nem serve automaticamente a aplicação em produção.
- Zustand é uma opção para estado de cliente compartilhado; use seletores e mantenha estado local local quando não houver necessidade de compartilhamento.
- TanStack Query administra consultas e cache de dados remotos; chaves devem refletir todos os parâmetros que mudam o resultado.
- Copiar dados remotos para outra store exige fonte de verdade e política explícitas de sincronização.
- Antes de instalar uma ferramenta, descreva a necessidade e compare com o que o projeto já oferece.

## Quiz
1. Vite invalida o cache de uma consulta à API quando um componente é atualizado? **Não. Vite cuida do desenvolvimento e do build; o ciclo da consulta é responsabilidade da camada de dados da aplicação.**
2. Uma store global deve conter todo estado de formulário? **Não. Mantenha local o que só é usado localmente; compartilhe apenas quando houver uma necessidade concreta.**
3. Qual informação deve participar da chave de uma consulta paginada por filtro? **Página e filtro, além de qualquer parâmetro que altere os dados retornados.**
4. É seguro colocar `VITE_API_SECRET` no `.env`? **Não. O prefixo `VITE_` expõe o valor ao código do cliente e ao bundle. Segredos devem ficar no servidor.**
5. Qual risco aparece ao copiar uma resposta remota para Zustand e também mantê-la no cache do TanStack Query? **As duas cópias podem divergir; sem uma fonte de verdade e uma política de sincronização, a interface pode mostrar dados inconsistentes.**

## Atividades

### Atividade 1 — Faça um mapa de responsabilidades
**Objetivo:** classificar dados por origem, escopo e ciclo de vida antes de escolher uma biblioteca.

**Passos:**
1. Descreva uma aplicação pequena de catálogo com busca, filtros, lista de produtos, favoritos temporários e tema visual.
2. Para cada dado, preencha: onde nasce, quem o altera, quais telas o usam, se vem do servidor e quando deve desaparecer.
3. Atribua cada dado a estado local, URL, store de cliente ou cache de consulta remota; justifique cada escolha em uma frase.
4. Marque casos em que a escolha depende de um requisito ainda desconhecido, como sobreviver ao recarregamento ou permitir compartilhar um link.
5. Desenhe as fronteiras entre componentes, store, URL e API, incluindo quem pode atualizar cada dado.

**Dica:** não escolha a ferramenta pelo número de componentes. Primeiro identifique a origem e o ciclo de vida do dado.

**Entrega:** tabela de classificação e diagrama simples das fontes de estado.

**Critérios de conclusão:** cada dado tem fonte definida; estado local não foi globalizado sem justificativa; decisões dependentes de requisitos estão identificadas.

### Atividade 2 — Integre uma lista remota e estado de interface
**Objetivo:** aplicar TanStack Query e Zustand em um fluxo pequeno com responsabilidades distintas.

**Passos:**
1. Em uma aplicação React com Vite, implemente ou localize uma tela de lista que consulte uma API ou mock.
2. Use TanStack Query para a consulta. Inclua na chave o filtro e a página usados pela função de busca.
3. Crie uma preferência de interface compartilhada, como painel de filtros aberto, em Zustand. Se essa preferência só for necessária em um componente, mantenha-a local e registre o motivo.
4. Faça uma alteração no servidor de teste e escolha uma política para atualizar a lista: invalidação ou atualização explícita do cache. Explique a escolha.
5. Registre a origem de cada dado e verifique que a resposta da consulta não foi duplicada em uma store sem sincronização.

**Dica:** uma variável só pertence à chave se mudar o conjunto de dados retornado; uma preferência puramente visual não precisa ser enviada à API.

**Entrega:** tela funcional, diagrama de responsabilidades e justificativa da política de atualização.

**Critérios de conclusão:** consulta e filtro permanecem coerentes; estado visual tem escopo justificado; a atualização não depende de duas cópias divergentes da resposta remota.

### Atividade 3 — Audite build e variáveis expostas
**Objetivo:** compreender o que o Vite entrega ao navegador e evitar colocar segredos no cliente.

**Passos:**
1. Examine os scripts de desenvolvimento e build do projeto e descreva o que cada um faz.
2. Liste as variáveis usadas pelo código do cliente e classifique cada uma como pública ou secreta, justificando a classificação.
3. Confira como o projeto escolhe a URL da API por ambiente e valide valores esperados, considerando que variáveis carregadas pelo Vite são strings.
4. Gere o build local e identifique a pasta de saída e o tipo de hospedagem necessário para servi-la.
5. Escolha uma rota interna da aplicação e descreva como verificaria o acesso direto a essa rota na hospedagem. Não publique segredos nem inclua credenciais no bundle.

**Dica:** tudo que o navegador precisa receber pode ser inspecionado por quem usa a aplicação. Não trate `.env` como cofre quando a variável é exposta ao cliente.

**Entrega:** mapa dos scripts, tabela de variáveis e nota curta sobre build e hospedagem.

**Critérios de conclusão:** scripts estão compreendidos; nenhuma credencial privada é exposta; saída e comportamento de rotas são verificáveis no ambiente de publicação previsto.

## Critério de conclusão
Conclua quando a pessoa consegue justificar a ferramenta a partir do problema, separar interface de dados remotos, montar uma chave que identifica a consulta, explicar como uma mutação atualiza os dados relacionados e reconhecer que variáveis expostas pelo Vite são públicas no cliente.
