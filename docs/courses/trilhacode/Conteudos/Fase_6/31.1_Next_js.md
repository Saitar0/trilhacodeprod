## Objetivo
Explicar a estrutura de rotas do App Router, separar responsabilidades de servidor e cliente, comparar formas de produzir e entregar conteúdo e criar um Route Handler seguro e adequado ao contrato.

## Microtópico 1 — Leia a estrutura de rotas do App Router
Next.js é um framework React que reúne convenções de roteamento, renderização e build. No **App Router**, pastas dentro de `app` representam segmentos de URL; arquivos convencionais definem o que cada segmento faz. `page.tsx` expõe uma página, `layout.tsx` compartilha uma estrutura entre páginas filhas e `route.ts` publica um handler HTTP. Segmentos dinâmicos como `[slug]` representam partes variáveis do caminho. Um grupo de rotas entre parênteses pode organizar arquivos sem adicionar um segmento à URL.

Layouts aninhados preservam a estrutura compartilhada durante a navegação. Também existem convenções para estados de carregamento, erros e páginas não encontradas, como `loading.tsx`, `error.tsx` e `not-found.tsx`. Entenda o papel de cada arquivo antes de inventar um mecanismo próprio para o mesmo comportamento.

O **Pages Router** é uma convenção anterior baseada em `pages`; nele, arquivos em `pages/api` implementam API Routes. O App Router usa Route Handlers em `app`. Os dois roteadores podem coexistir em um projeto durante uma migração, mas não defina uma página e um Route Handler para o mesmo segmento de rota. Ao estudar ou manter um projeto, identifique qual roteador contém cada URL.

## Microtópico 2 — Desenhe fronteiras pequenas entre servidor e cliente
No App Router, componentes de servidor são o padrão. Eles podem buscar dados próximos à fonte, usar credenciais de servidor e evitar enviar ao navegador JavaScript de interação que não é necessário. Um **Client Component** é necessário para estado interativo, event handlers e APIs do navegador. A diretiva `'use client'` marca uma entrada para a árvore cliente; os imports dessa entrada também participam do bundle cliente. Por isso, coloque a fronteira perto da interação em vez de marcar toda a aplicação como cliente.

Uma composição comum é um Server Component carregar dados e entregar apenas os valores necessários para um pequeno componente cliente, como um botão de favorito. Props que atravessam a fronteira precisam ser serializáveis conforme as regras do framework. A interface pode receber HTML inicial e o payload necessário para reconciliar a árvore; o JavaScript hidrata partes cliente para habilitar interações.

Código no servidor pode acessar segredos, mas valores passados ao cliente deixam de ser secretos. Em Next.js, variáveis com prefixo `NEXT_PUBLIC_` são incluídas no bundle cliente. Nunca envie tokens privados, credenciais de banco ou dados de autorização para um Client Component só para facilitar uma interação. A fronteira de componente também não substitui autenticação e autorização: proteja dados e ações no servidor.

## Microtópico 3 — Escolha quando e onde o conteúdo é produzido
Renderização descreve quando a interface ou parte dela é preparada; não trate SSR, prerenderização e client rendering como três caixas sempre excludentes. Uma página pode apresentar um shell previamente renderizado e carregar partes dinâmicas depois. A estratégia adequada depende de frescor, personalização, latência, custo de execução e capacidade do destino de deploy.

- **Prerenderização:** prepara HTML antes da solicitação do usuário quando os dados e a configuração permitem. Pode reduzir trabalho por visita e favorecer cache, mas precisa de uma política para atualizar conteúdo.
- **Renderização por solicitação:** usa dados ou contexto da requisição, como sessão e cookies, para compor conteúdo específico. Ajuda com personalização e frescor, mas depende de runtime e pode aumentar a latência.
- **Renderização no cliente:** o navegador executa JavaScript para produzir ou atualizar a interface. É útil para interações, mas pode exigir mais código e trabalho no cliente e não deve ser a escolha automática para todo conteúdo.

Streaming com limites de carregamento pode enviar partes da interface conforme ficam prontas. Cache e revalidação afetam se uma parte é calculada em build, em requisição ou reutilizada. As regras e padrões de cache do Next.js mudam entre versões e opções como Cache Components; confirme o comportamento da versão do projeto e teste o build de produção. Não deduza estratégia de renderização apenas pela aparência da página no servidor de desenvolvimento.

## Microtópico 4 — Trate Route Handlers como endpoints públicos
Um arquivo `route.ts` no App Router implementa métodos HTTP com as APIs `Request` e `Response`, como `GET`, `POST`, `PATCH` e `DELETE`. Route Handlers não são componentes de página e não participam dos layouts nem da navegação visual. Uma URL pode ser criada em qualquer segmento adequado dentro de `app`, respeitando o conflito entre `page` e `route` no mesmo nível.

Pense nesses handlers como endpoints de API expostos a requisições externas. Valide parâmetros e corpo, autentique a sessão, autorize a ação para aquele recurso, trate erros e retorne status apropriados. Esconder um link na interface não protege o endpoint. Dados personalizados não podem ser servidos de um cache compartilhado sem uma chave e política seguras. Os padrões de cache de Route Handlers também dependem da versão e da configuração; confira a documentação vigente antes de assumir que uma resposta `GET` é ou não armazenada.

Antes de publicar, verifique se a plataforma oferece o runtime e os recursos exigidos pelo projeto. Um site estático pode servir páginas já geradas, mas endpoints e conteúdo dinâmico precisam de uma plataforma que execute o código correspondente. Segredos devem ser configurados no ambiente de servidor da hospedagem, nunca inseridos no bundle do navegador.

## Resumo
- O App Router usa convenções de arquivo em `app`; `pages/api` pertence ao Pages Router e Route Handlers ficam em `app`.
- Server Components são padrão; Client Components são fronteiras de interação e seus imports entram na árvore cliente.
- Prerenderização, execução por requisição, streaming e trabalho no cliente podem coexistir; frescor e cache dependem da configuração e da versão.
- Route Handlers são endpoints públicos que precisam validar entrada, autenticar e autorizar operações.
- O destino de deploy deve suportar os runtimes e recursos usados, e variáveis expostas ao cliente não podem conter segredos.

## Quiz
1. **Múltipla escolha.** Onde fica um endpoint no App Router? A) Em `app/api/items/route.ts`. B) Em qualquer `page.tsx` com botão. C) Apenas em `pages/api`. **Resposta: A.** `pages/api` é a convenção do Pages Router.
2. **Verdadeiro ou falso, justifique.** “Um Server Component é privado porque não roda no navegador.” **Falso.** A resposta renderizada ou os dados que ele retorna ainda podem ser públicos; autorização precisa ser feita no servidor para cada recurso.
3. **Cenário.** Um botão requer clique e estado local, enquanto o restante da página lê dados com credencial privada. Como organizar? **Manter a busca e a credencial no servidor e criar um Client Component pequeno para o botão, recebendo apenas props serializáveis e necessárias.**
4. **Associe o contexto à decisão.** Página de marketing com conteúdo estável; painel personalizado por sessão; abrir menu lateral. **Resposta:** avaliar prerenderização; usar contexto de requisição no servidor e proteger os dados; interação cliente local.
5. **Diagnóstico.** Uma rota `GET` funciona em desenvolvimento, mas em produção entrega dados personalizados de uma conta a outra. Que áreas precisam ser revisadas? **Autorização e identidade da sessão, política/chave de cache e configuração de renderização; o funcionamento em desenvolvimento não comprova isolamento em produção.**

## Atividades

### Atividade 1 — Modele rotas, páginas e layouts
**Objetivo:** transformar uma estrutura de produto em rotas do App Router sem confundir URL, organização de pastas e convenções.

**Passos:**
1. Modele um catálogo com início, listagem, detalhe por slug e uma área de conta.
2. Desenhe a árvore `app` e marque quais segmentos viram URL, quais grupos apenas organizam arquivos e onde layouts compartilhados são necessários.
3. Defina onde entrariam estados de carregamento, erro e não encontrado usando as convenções do framework.
4. Identifique quais URLs são páginas e quais recursos são endpoints HTTP; garanta que `page.tsx` e `route.ts` não disputem o mesmo segmento.
5. Registre quais rotas podem ser pré-geradas e quais dependem de dados da solicitação ou sessão, justificando a escolha.

**Dica:** escreva primeiro as URLs desejadas e depois mapeie cada uma para arquivos. A estrutura de pastas é uma convenção para expressar rotas, não o requisito em si.

**Entrega:** árvore de arquivos anotada e tabela URL → página/handler → dados necessários.

**Critérios de conclusão:** URLs e arquivos correspondem; layouts têm escopo claro; páginas públicas e dependentes de sessão estão diferenciadas.

### Atividade 2 — Separe servidor e interação cliente
**Objetivo:** buscar dados protegidos no servidor e limitar o bundle cliente ao que precisa de interação.

**Passos:**
1. Implemente uma página de detalhe que leia um registro usando uma função de servidor ou API de teste.
2. Mantenha credenciais e acesso à fonte de dados fora do grafo cliente; identifique cada variável que atravessa a renderização.
3. Extraia uma interação real, como favoritar ou alternar um painel, para um Client Component pequeno.
4. Passe pela fronteira apenas valores necessários e serializáveis; documente o que acontece com sessão inválida e recurso não autorizado.
5. Examine o bundle ou a saída de build para confirmar que nenhum segredo foi exposto e confira a experiência com JavaScript habilitado e carregamento progressivo esperado.

**Dica:** `'use client'` define uma fronteira de módulos, não uma anotação isolada que deixa todos os imports no servidor.

**Entrega:** página com leitura no servidor e uma interação cliente, acompanhada de diagrama da fronteira e revisão das variáveis.

**Critérios de conclusão:** segredo permanece no servidor; a parte cliente é limitada à interação; estado não autorizado é tratado no servidor e na interface.

### Atividade 3 — Compare Route Handler e estratégia de renderização
**Objetivo:** publicar uma rota HTTP segura e explicar seu comportamento de produção.

**Passos:**
1. Crie `app/api/items/route.ts` com leitura de coleção de teste e, se fizer sentido, uma operação de escrita com validação de entrada.
2. Verifique método, parâmetros, formato da resposta e status de sucesso, entrada inválida, não autenticado e não autorizado.
3. Para a página que usa esses dados, decida se o conteúdo pode ser pré-gerado, se depende da requisição ou se combina shell e conteúdo dinâmico.
4. Documente a configuração de cache e revalidação para a versão utilizada; inclua identidade do usuário na decisão de isolamento e evite cache compartilhado de dados privados.
5. Gere e execute o build no runtime de teste previsto e confirme que páginas, handlers, variáveis de servidor e rotas funcionam conforme a configuração declarada.

**Dica:** não use o servidor de desenvolvimento como única evidência do modo de produção; o comportamento de cache e build pode ser diferente.

**Entrega:** Route Handler documentado, tabela de respostas e decisão de renderização/cache com evidência de build.

**Critérios de conclusão:** entrada validada; endpoint faz autenticação e autorização; cache não mistura usuários; plataforma atende ao runtime escolhido.

## Critério de conclusão
Conclua quando a pessoa desenha uma árvore válida do App Router, explica a fronteira servidor/cliente e o destino dos dados, compara uma página pré-gerada com conteúdo dependente de requisição, e implementa um Route Handler com validação, autenticação, autorização e cache coerente.
