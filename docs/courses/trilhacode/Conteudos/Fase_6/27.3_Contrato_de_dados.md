# 27.3 — Contrato de dados

## Objetivo
Definir e consumir contratos HTTP explícitos, validar JSON em tempo de execução e transformar respostas válidas em dados seguros para a interface.

## Teoria

### 1. Descrever a fronteira entre cliente e API
Um contrato de dados define quais operações existem, o que o cliente envia, o que recebe, quais campos são obrigatórios, que valores podem ser nulos e quais erros podem ocorrer. Também documenta parâmetros, paginação, formatos, autenticação e limites relevantes. Um exemplo de resposta é útil, mas sozinho não define se os campos são sempre presentes nem como o servidor responde a falhas.

OpenAPI descreve operações HTTP e seus esquemas em um formato legível por pessoas e ferramentas. Pode servir para gerar documentação, tipos ou clientes, mas a especificação precisa refletir o comportamento real do servidor. Defina uma fonte de verdade e um processo para revisar/versionar mudanças; compartilhar um tipo TypeScript não garante que o payload em rede esteja conforme.

Considere esta resposta de listagem:

```json
{
  "items": [{ "id": "t-17", "title": "Revisar contrato", "dueDate": null }],
  "page": 1,
  "pageSize": 20,
  "total": 1
}
```

O contrato deve dizer se `dueDate` pode ser `null`, se `items` pode estar vazio, quais limites aceitam `page` e `pageSize`, e o que acontece quando a página solicitada não existe.

### 2. Separar tipo estático de validação em runtime
TypeScript analisa o código durante compilação; ele não verifica automaticamente se o servidor remoto enviou os campos prometidos. `response.json()` deve ser tratado como dado externo. Uma afirmação como `await response.json() as Task` muda a interpretação do compilador, mas não examina o valor recebido.

Use `unknown` na fronteira. Valide tipo, campos e restrições com uma função de validação, schema runtime ou biblioteca escolhida; depois transforme o dado para um modelo de domínio/UI. Se inválido, devolva erro controlado, estado de indisponibilidade ou adaptação explicitamente documentada. Não deixe que payload malformado derrube a tela e não silencie a incerteza com `any` ou `as`.

Validação verifica forma e invariantes locais — por exemplo, `page` inteiro positivo e `title` string. Ela não substitui autorização, integridade do banco ou confirmação de que um dado é verdadeiro. Nunca registre payload sensível inteiro só para investigar erro; inclua contexto seguro, como rota, código de erro e identificador de correlação.

### 3. Modelar presença, nulidade e variações de resposta
Campo opcional e campo anulável expressam situações diferentes. `nickname?: string` permite que a propriedade esteja ausente; `nickname: string | null` exige a propriedade, mas admite valor nulo. A API e o cliente precisam concordar com o caso de cada campo. Não converta ausência em string vazia ou zero sem uma regra de produto.

Sucesso e erro também têm estruturas diferentes. Uma resposta HTTP de sucesso pode carregar um objeto de dados; falha pode incluir código estável, mensagem segura e detalhes de validação. O cliente deve considerar status HTTP e validar o corpo correspondente. Tipar só o caminho feliz deixa erros de rede, autenticação e contrato sem tratamento.

### 4. Evoluir contratos sem surpreender consumidores
Uma mudança aditiva — como incluir campo opcional que clientes antigos ignoram — tende a ser mais compatível do que remover ou alterar o tipo/significado de um campo usado. Ainda assim, clientes que rejeitam propriedades desconhecidas ou geradores específicos podem se comportar de modo diferente. Teste consumidores e servidor com exemplos versionados.

Para mudança incompatível, planeje migração: adicionar novo campo/rota, migrar consumidores, observar uso e só então remover o antigo quando a política permitir. Defina comportamento para cliente antigo, versão suportada, período de transição e aviso de descontinuação. Testes de contrato com exemplos válidos e inválidos ajudam a detectar divergência antes de chegar à UI.

## Resumo
- O contrato define formatos, presença, nulidade, erros e parâmetros HTTP.
- Tipos TypeScript não validam automaticamente dados recebidos pela rede.
- Trate JSON como `unknown` até validar e adaptar.
- Diferencie campo ausente de campo `null`.
- Avalie compatibilidade de mudanças com consumidores e testes de contrato.

## Quiz
1. `const task = await response.json() as Task` comprova que `title` existe e é string? **Não.** A asserção só orienta o compilador; é necessário validar o valor recebido em runtime.
2. Qual diferença entre `dueDate?: string` e `dueDate: string | null`? **No primeiro, a propriedade pode estar ausente; no segundo, ela precisa existir, mas seu valor pode ser nulo.**
3. Uma API adiciona `archived: boolean` à resposta. Isso sempre quebra clientes antigos? **Não necessariamente; consumidores que ignoram campos desconhecidos podem continuar. Porém, clientes/validadores estritos podem rejeitar; verifique comportamento e compatibilidade real.**
4. Por que a UI precisa checar o status HTTP além de validar JSON? **Porque resposta de erro e sucesso têm semântica diferente; um JSON bem-formado pode representar falha ou não autorização.**
5. O que um teste de contrato compartilhado ajuda a detectar? **Diferenças entre a resposta/documentação esperada e o formato real consumido, incluindo campos e formatos incompatíveis. Não prova autenticidade nem autorização dos dados.**

## Prática

### Atividade 1 — Especificar contrato de uma listagem paginada
**Contexto e objetivo:** transformar um exemplo de endpoint em contrato verificável para cliente e API.

**Dados iniciais:** endpoint `GET /api/tasks?page=1&pageSize=20`, resposta de exemplo:

```json
{
  "items": [{ "id": "t-17", "title": "Revisar contrato", "dueDate": null }],
  "page": 1,
  "pageSize": 20,
  "total": 1
}
```

**Instruções:** escreva os tipos TS e descreva o contrato HTTP: parâmetros e limites, campos obrigatórios/opcionais/anuláveis, caso sem resultados, comportamento para parâmetro inválido, status e formato de erro. Inclua um exemplo de resposta válida vazia e um exemplo de falha de validação. Não escolha limites silenciosamente: anote-os como decisões do contrato.

**Entrega:** definição TS, rascunho OpenAPI ou tabela de contrato com exemplos válidos e inválidos.

**Dica gradual:** determine primeiro se cada propriedade pode faltar, ser nula ou ambas as coisas. Depois defina faixa de `pageSize` e resposta para página fora da faixa.

**Feedback e erro comum:** a descrição precisa distinguir `items: []` de ausência de `items` e `dueDate: null` de campo omitido. Erro comum: usar um único formato de resposta para sucesso e erro sem definir status HTTP ou semântica.

### Atividade 2 — Validar JSON externo e adaptar para a UI
**Contexto e objetivo:** impedir que resposta inesperada chegue à interface como se fosse confiável.

**Dados iniciais válidos:** o exemplo da Atividade 1. Teste também estas respostas inválidas: `{"items":[{"id":12,"title":false}],"page":0,"pageSize":20,"total":1}` e `{"items":null,"page":1,"pageSize":20,"total":0}`.

**Instruções:** implemente, na linguagem/stack da unidade, uma função que receba `unknown` e retorne resultado discriminado (sucesso com dados validados ou erro controlado). Valide tipos, `page >= 1`, `pageSize` dentro do limite decidido, `total >= 0`, `id` e `title`; preserve `dueDate: null`. Converta o valor validado para modelo da UI, sem afirmação `as` na fronteira. Mostre tratamento distinto para falha HTTP, JSON inválido e payload com schema inválido.

**Entrega:** função/guard/schema, três testes com os dados indicados e um exemplo de como a UI representa erro sem crash.

**Dica gradual:** comece verificando que o valor é objeto não nulo; depois valide cada propriedade antes de usá-la. Um tipo de resultado como `{ ok: true, data } | { ok: false, reason }` ajuda o consumidor a tratar os dois caminhos.

**Feedback e erro comum:** resposta válida deve ser estreitada sem coerção insegura; ambas as inválidas devem ser rejeitadas com motivo seguro. Erro comum: validar só se o corpo é objeto e depois presumir que todos os campos internos estão corretos.

### Atividade 3 — Revisar evolução e compatibilidade de contrato
**Contexto e objetivo:** detectar mudança que quebra consumidores e planejar uma migração compatível.

**Situação:** versão atual usa `{ "id": "t-17", "title": "Revisar", "dueDate": null }`. A proposta quer remover `title`, trocar `dueDate` para Unix timestamp numérico e adicionar `status`.

**Instruções:** classifique cada mudança como potencialmente compatível ou incompatível e justifique; escreva uma alternativa de migração que mantenha cliente antigo funcional por um período; proponha exemplos/testes para contrato antigo e novo; defina como saber quando o campo antigo pode ser removido. Considere consumidor estrito que rejeita propriedades desconhecidas.

**Entrega:** matriz “mudança → consumidor afetado → risco → plano de migração” e conjunto mínimo de exemplos/testes de contrato.

**Dica gradual:** adicionar `status` opcional pode ser aditivo para muitos consumidores; remover `title` e alterar o tipo de `dueDate` mudam contrato existente. Uma transição pode adicionar campo novo antes de descontinuar o antigo.

**Feedback e erro comum:** o plano mantém compatibilidade durante transição, nomeia os consumidores e define evidência de uso/depreciação. Erro comum: chamar toda adição de campo de segura sem verificar validação estrita ou tipos gerados.

**Rubrica (0–4) por atividade:** contrato definido sem ambiguidade (0–1); validação/compatibilidade correta (0–1); exemplos e testes cobrem falhas relevantes (0–1); decisão e limites comunicados com clareza (0–1).

## Critério de conclusão
Definir contrato de sucesso e erro para uma rota paginada, validar resposta JSON como `unknown` antes do uso na interface e apresentar plano de migração para uma mudança incompatível, incluindo exemplos/testes de contrato.
