## Objetivo
Explicar como React descreve interfaces e transformar marcação repetida em componentes funcionais reutilizáveis com JSX e props, mantendo a renderização previsível.

## Teoria

## Microtópico 1 — React descreve a interface a partir dos dados

Em uma interface imperativa, o código pode localizar nós do DOM e alterar texto, classes e atributos em várias partes do programa. Conforme estados e telas aumentam, fica difícil saber qual código deve prevalecer e se todas as alterações foram aplicadas.

Com React, a aplicação descreve qual interface deve aparecer para os dados atuais. Componentes expressam partes da interface; o React executa essa descrição, compara a árvore resultante com a anterior e atualiza o DOM quando necessário. Em geral, quem desenvolve declara o resultado esperado, em vez de coordenar manualmente cada alteração no DOM.

A descrição segue entradas como props e estado. Nesta primeira unidade, concentre-se em dados recebidos por props; estado e resposta a eventos serão aprofundados em 25.2. React é uma biblioteca para interfaces; não substitui por si só todas as decisões de roteamento, chamadas de rede ou organização da aplicação.

## Microtópico 2 — Componentes são funções que compõem a UI

Um componente funcional é uma função JavaScript que recebe props e retorna elementos React, normalmente escritos com JSX. Nomes de componente começam com letra maiúscula para que JSX os reconheça como componentes; nomes de elementos HTML, como article e button, começam com letra minúscula.

Componentes podem ser compostos: um componente de página pode renderizar uma lista de cartões; cada cartão apresenta um item. A extração é útil quando uma parte tem significado e responsabilidade reconhecíveis, ou quando a mesma estrutura aparece em vários dados. Não é necessário criar um componente para cada tag ou linha isolada.

```jsx
function TaskCard({ title, owner, completed }) {
  return (
    <article>
      <h2>{title}</h2>
      <p>Responsável: {owner}</p>
      <p>{completed ? "Concluída" : "Pendente"}</p>
    </article>
  );
}

function TaskList() {
  const tasks = [
    { id: 1, title: "Revisar acessibilidade", owner: "Lia", completed: false },
    { id: 2, title: "Corrigir formulário", owner: "Caio", completed: true },
  ];

  return (
    <section>
      {tasks.map((task) => (
        <TaskCard
          key={task.id}
          title={task.title}
          owner={task.owner}
          completed={task.completed}
        />
      ))}
    </section>
  );
}
```

O exemplo mostra composição e dados variados. O atributo key identifica cada item entre irmãos quando uma coleção é renderizada; ele é usado pelo React para acompanhar itens e não funciona como uma prop comum que o cartão possa ler. A unidade não exige memorizar casos complexos de reconciliação; basta manter a identidade estável dos itens.

## Microtópico 3 — JSX é sintaxe para descrever elementos

JSX permite escrever uma estrutura semelhante a marcação dentro de JavaScript. As ferramentas de build transformam JSX para que o runtime React possa usá-lo; o navegador não recebe JSX como HTML puro. A sintaxe é parecida com HTML, mas segue regras próprias:

- Retorne uma única expressão que envolva a descrição; use um elemento pai ou fragmento quando houver irmãos.
- Feche tags e escreva elementos vazios com fechamento, como img ou input.
- Use convenções JavaScript para alguns atributos, como className.
- Insira valores ou expressões JavaScript entre chaves.
- Passe uma expressão de componente com letra maiúscula; texto literal pode ser escrito diretamente entre elementos.

```jsx
function Greeting({ name }) {
  return (
    <>
      <h1>Olá, {name}</h1>
      <img className="avatar" src="/avatar.png" alt="" />
    </>
  );
}
```

O fragmento reúne elementos sem adicionar um nó de contêiner à estrutura HTML. Aspas representam texto literal em atributos; chaves permitem valores e expressões. Se um título contém caracteres especiais como & ou <, escreva-o como texto vindo de uma prop: React o trata como texto e escapa conteúdo para a saída em vez de interpretar a entrada como JSX.

## Microtópico 4 — Props são entradas de leitura do componente

Props são informações que um componente pai passa ao filho. Podem ser texto, números, booleanos, objetos, arrays, funções ou elementos. O componente lê esses valores e escolhe o que descrever. Props devem ser tratadas como imutáveis durante a renderização: se o filho precisa de uma entrada diferente, o pai envia novos dados; o filho não altera o objeto recebido para forçar uma atualização.

```jsx
<TaskCard title="Revisar testes" owner="João" completed={false} />
```

Nesse uso, strings são passadas entre aspas, booleanos e expressões entre chaves. No componente, desestruturar o objeto de props nos parâmetros pode tornar as entradas explícitas. O nome e o formato das props são parte do contrato entre pai e filho; prefira nomes ligados ao significado do domínio e evite uma prop genérica sem propósito.

Uma condição pode alterar a descrição para os mesmos dados, como mostrar “Concluída” quando completed é true. Isso continua sendo uma renderização baseada em dados, não uma alteração imperativa no DOM. Uma prop não é automaticamente estado interno: o filho recebe uma fotografia das entradas daquela renderização.

## Microtópico 5 — Renderização precisa ser previsível

Renderizar é executar componentes para calcular a descrição da UI. Depois, React pode confirmar alterações necessárias no DOM. Uma renderização não significa que o navegador vai recriar tudo a cada chamada. Além disso, uma renderização pode ocorrer sem que haja mudança no DOM.

Mantenha a função de renderização pura: com as mesmas props, estado e contexto, calcule a mesma descrição e não altere valores que existiam antes da chamada nem faça efeitos externos. React pode chamar uma função de componente mais de uma vez, interromper um trabalho ou repetir cálculos em desenvolvimento para revelar problemas. Por isso, não envie requisições, escreva no DOM nem incremente variável global durante a renderização.

```jsx
function TaskCard({ task }) {
  // Leia task; não altere task.title nem task.completed aqui.
  return <h2>{task.title}</h2>;
}
```

Mais tarde, eventos de usuário serão tratados fora do cálculo da renderização, e estado será atualizado pela API própria do React. Por ora, lembre a separação: props descrevem entradas, o componente calcula a UI e React decide como aplicar a descrição.

## Resumo
- React permite descrever a UI a partir dos dados atuais; o React coordena a atualização do DOM.
- Componentes funcionais recebem props e compõem elementos maiores a partir de partes com significado.
- JSX é sintaxe transformada pelas ferramentas; expressões JavaScript usam chaves e atributos seguem convenções próprias.
- Props são entradas de leitura e não devem ser alteradas pelo filho.
- Renderização previsível não realiza efeitos externos nem manipula DOM diretamente.

## Quiz

1. **Conceito:** JSX é uma linguagem que o navegador interpreta diretamente como HTML?  
   **Resposta esperada:** não. JSX é uma extensão de sintaxe transformada pelas ferramentas do projeto para uso com React.

2. **Leitura de componente:** em um TaskCard que recebe title e completed, quem decide os valores de cada cartão quando a lista é renderizada?  
   **Resposta esperada:** o componente pai fornece props distintas para cada item; o filho usa essas entradas para descrever o cartão.

3. **Análise de código:** por que alterar task.completed dentro de TaskCard é um problema?  
   **Resposta esperada:** props e objetos recebidos são entradas de leitura; mutá-los pode afetar o pai e tornar o resultado imprevisível, especialmente se React repetir renderização.

4. **Classificação:** uma função altera diretamente o texto de um nó do DOM dentro do corpo do componente. Isso segue o modelo declarativo de React?  
   **Resposta esperada:** não. A função deveria retornar a descrição pretendida; React controla a atualização do DOM.

5. **Transferência:** uma tela contém quatro cartões com o mesmo formato e dados distintos. Que parte é apropriado reutilizar e que dados devem variar?  
   **Resposta esperada:** extrair um componente com responsabilidade clara para o formato do cartão e fornecer props distintas, como título, responsável e conclusão; não criar abstrações extras sem necessidade.

## Atividades práticas

### Atividade 1 — Converta marcação repetida em componente

**Desafio:** transforme três blocos de tarefa escritos manualmente em uma lista de dados e um componente TaskCard.

**Passos:**
1. Defina três tarefas com id, título, responsável e status concluído.
2. Escreva um componente que receba os campos necessários por props e retorne a estrutura comum.
3. Percorra a lista para renderizar um cartão por tarefa; use um identificador estável como key.
4. Inclua um título com acento e caracteres como &, < ou aspas.
5. Explique quais partes da marcação se repetem e quais dados diferem.

**Dica:** não passe o objeto inteiro se o contrato do componente ficar mais claro com as propriedades que ele realmente usa.

**Solução de referência:** uma lista de objetos mantém os dados; o pai usa map e passa title, owner e completed a TaskCard. O cartão mostra título e responsável como texto e escolhe “Concluída” ou “Pendente” conforme o booleano. A key vem do id, mas não é lida como prop pelo cartão.

**Rubrica:** componente reutilizado para três itens; props representam dados; markup não é duplicado; key estável; caracteres especiais aparecem como texto; explica composição com clareza.

### Atividade 2 — Corrija JSX e explique o resultado

**Desafio:** corrija uma descrição de perfil com erros comuns: dois elementos irmãos retornados sem contêiner, class em vez de className, tag sem fechamento e nome de componente iniciado em minúscula.

**Passos:**
1. Identifique cada problema sintático ou convenção incorreta.
2. Corrija a composição usando um contêiner ou fragmento.
3. Transforme nome e imagem em props.
4. Renderize duas pessoas diferentes com o mesmo componente.
5. Explique por que JSX precisa ser transformado e como as props diferenciam os resultados.

**Dica:** fragmento agrupa a expressão sem adicionar um elemento ao DOM.

**Solução de referência:** um componente Profile com P maiúsculo recebe name e imageUrl; retorna fragmento contendo título e imagem com alt, usando className e tags fechadas corretamente. O pai renderiza Profile duas vezes com valores distintos. As ferramentas transformam a sintaxe JSX antes do navegador executar o app.

**Rubrica:** JSX válido; semântica de componente preservada; dados vêm por props; conteúdo de acessibilidade não fica sem alt adequado; explica a transformação sem afirmar que JSX é HTML nativo.

### Atividade 3 — Detecte renderização impura

**Desafio:** um componente incrementa uma variável global para gerar número de cartão e modifica task.title para capitalizar o texto durante a renderização.

**Passos:**
1. Identifique os valores externos que estão sendo modificados.
2. Descreva por que repetir a chamada pode produzir outro resultado.
3. Faça o pai fornecer um número de ordem estável se ele for necessário na interface.
4. Calcule a versão capitalizada em uma variável local sem alterar task, ou faça a transformação antes de passar o dado se isso pertencer ao pai.
5. Compare a saída para as mesmas props em chamadas repetidas e explique por que ela deve permanecer igual.

**Dica:** mutação local de valor criado durante a própria renderização pode ser segura; alterar objeto que veio de fora não é.

**Solução de referência:** remover o contador global e a atribuição em task.title; derivar texto localmente sem alterar task; passar order como prop estável se a tela precisa exibi-la. Para as mesmas entradas, o componente deve calcular a mesma descrição e não deve depender da ordem em que React chama componentes.

**Rubrica:** identifica ambas as mutações externas; preserva os dados de entrada; resultado depende das props; alternativa mantém comportamento pretendido sem manipulação direta do DOM ou estado global.

## Critério de conclusão
Refatore uma interface repetida em componentes funcionais que recebem props distintas, explique as regras essenciais de JSX e demonstre que renderizar com as mesmas entradas não altera dados externos nem produz efeitos colaterais.
