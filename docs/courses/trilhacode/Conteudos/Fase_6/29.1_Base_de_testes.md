# 29.1 — Base de testes

- key: 29.1
- tipo: solo
- carater: obrigatorio
- profundidade: media
- estimativa_minutos: 90
- tags: [#qualidade, #web]
- status: rascunho

## Objetivo
Escrever testes de componentes React que verificam comportamento observável, interações acessíveis e respostas assíncronas, com configuração adequada ao projeto e sem acoplamento desnecessário à implementação.

## Microtópico 1 — Teste o contrato que a pessoa usa
Um teste de componente deve responder a uma pergunta sobre o comportamento: o formulário informa um campo obrigatório? O botão envia os dados válidos? A lista mostra erro quando a consulta falha? O teste renderiza a interface, interage com ela e verifica o resultado percebido. Ele não precisa conhecer o nome de um `useState`, chamar um handler privado ou depender de uma classe CSS que só organiza o visual.

Testing Library orienta a escrever testes que se aproximem de como o software é usado. Consultas por papel acessível e nome, label ou texto costumam exercitar a semântica da interface. Isso também torna problemas de acessibilidade mais visíveis: se não é possível localizar um botão pelo papel e nome que deveria ter, pode haver uma falha real no markup.

Não transforme cada detalhe de implementação em contrato. Um snapshot enorme pode mudar por alterações irrelevantes e ainda deixar passar um comportamento errado. Prefira assertions específicas: mensagem visível, ação disponível, resultado renderizado ou ausência de um conteúdo após a interação. Escolha cenários de acordo com risco e regra de negócio, não apenas para aumentar a quantidade de testes.

## Microtópico 2 — Configure runner e ambiente coerentes
Um runner executa os testes, oferece assertions, isolamento e recursos como mocks. Vitest integra-se ao ecossistema Vite; Jest é uma alternativa estabelecida em outros projetos. Normalmente basta escolher o que combina com a configuração existente. Usar os dois no mesmo projeto adiciona configuração e manutenção sem benefício automático.

Um teste de lógica sem DOM pode rodar em Node. Um teste de componente precisa de um ambiente com APIs de navegador: um DOM simulado como `jsdom` ou `happy-dom`, ou um modo de navegador real quando o projeto e o escopo justificarem. Esses ambientes têm diferenças. DOM simulado é rápido e suficiente para muitos comportamentos; não comprova layout, renderização real de CSS ou todos os detalhes de APIs do navegador.

Confira a versão e as instruções de configuração vigentes para o runner, o framework React e as bibliotecas auxiliares do projeto. O arquivo de setup pode registrar matchers ou configuração compartilhada. Um teste que só passa por causa de globals ou estado residual de outro teste não está isolado corretamente.

## Microtópico 3 — Consulte, interaja e aguarde corretamente
Escolha a consulta conforme a expectativa temporal:

- `getBy...` é apropriada quando o elemento já deve estar presente; falha imediatamente se não encontrar ou se a consulta for ambígua.
- `queryBy...` é útil para verificar ausência sem lançar erro quando nada é encontrado.
- `findBy...` espera até que um elemento apareça ou que o tempo limite seja atingido, sendo útil para atualizações assíncronas.

Para uma ação de usuário, use uma API de interação como `user-event` ou a API recomendada pelo ambiente de teste escolhido. Interagir pelo botão, teclado ou campo exercita mais do fluxo do que chamar diretamente uma função interna. Faça o teste assíncrono quando a interação ou o resultado depender de uma Promise. Use `waitFor` para uma expectativa que precisa ser repetida enquanto a interface atualiza; mantenha dentro dele uma assertion, sem colocar a ação de usuário ali, porque a função pode executar mais de uma vez.

Os testes devem verificar um resultado observável após o evento. Não basta confirmar que um mock foi chamado se o contrato importante também é a mensagem, navegação ou atualização que a pessoa vê. Assertions de chamadas são úteis quando a chamada é parte do contrato entre componentes, mas não substituem a verificação da resposta da interface.

## Microtópico 4 — Isole dependências sem esconder defeitos
Mock é útil para controlar uma dependência externa ou uma resposta imprevisível, como API, relógio ou serviço de terceiros. Use a menor fronteira necessária: teste a interface com sucesso e falha controlados, sem substituir justamente o comportamento que quer verificar. Se todo o componente, incluindo sua regra principal, foi mockado, o teste pode passar sem testar o produto.

Cada teste deve preparar seus próprios dados e não depender da ordem de execução. Limpe mocks e estado compartilhado conforme a ferramenta e o setup do projeto. Prefira fixtures pequenas e legíveis, com diferenças importantes explícitas. Para consultas assíncronas, resolva ou rejeite a Promise de forma controlada e aguarde a interface chegar ao estado esperado.

Cobertura informa quais partes foram executadas, mas não mede se as assertions detectariam um defeito. Uma suíte pode ter alta cobertura e apenas confirmar que elementos existem, sem testar a regra. Uma verificação útil é introduzir temporariamente uma falha plausível — por exemplo, remover uma validação — e observar se o teste relacionado falha. Depois restaure o código e mantenha a assertion que detecta o comportamento quebrado.

## Resumo
- Teste contratos e comportamentos visíveis por meio de interações parecidas com as de uma pessoa usuária.
- Use consultas semânticas: `getBy` para presença imediata, `queryBy` para ausência e `findBy` para aparecimento assíncrono.
- Escolha um runner e um ambiente compatíveis com o projeto; DOM simulado não equivale a navegador real.
- Controle dependências externas sem mockar a regra que o teste precisa verificar.
- Isolamento e assertions significativas importam mais que snapshots extensos ou percentual de cobertura isolado.

## Quiz
1. **Múltipla escolha.** Qual busca é mais apropriada para encontrar o botão de envio? A) `getByRole('button', { name: 'Enviar' })`. B) Buscar uma classe CSS gerada. C) Inspecionar o nome da variável do handler. **Resposta: A.** Ela procura pela semântica e pelo nome percebidos na interface.
2. **Associe a necessidade à consulta.** Verificar que um aviso está ausente; localizar um campo que já deve estar renderizado; esperar o resultado de uma busca assíncrona. **Resposta:** `queryBy...`; `getBy...`; `findBy...`, respectivamente.
3. **Verdadeiro ou falso, justifique.** “Se o teste passa e a cobertura é 100%, o comportamento está correto.” **Falso.** Código executado não garante assertions capazes de detectar resultados incorretos.
4. **Cenário.** Um teste coloca `await user.click(...)` dentro de uma callback de `waitFor`. Qual é o risco e como melhorar? **`waitFor` pode executar a callback várias vezes e repetir a ação; execute a interação uma vez fora dela e use `waitFor` apenas para aguardar a assertion quando `findBy` não for suficiente.**
5. **Resposta curta.** Por que usar `jsdom` não comprova que o layout funciona em navegadores reais? **Ele simula APIs e DOM, mas não reproduz completamente renderização visual, CSS e comportamento do navegador.**

## Atividades

### Atividade 1 — Teste o contrato de um formulário
**Objetivo:** verificar validação, interação e confirmação usando a interface pública.

**Passos:**
1. Escolha um formulário de cadastro ou perfil com pelo menos dois campos e uma regra de validação observável.
2. Renderize o componente no ambiente de teste já usado pelo projeto e localize controles por label e botões por papel e nome.
3. Tente enviar dados inválidos e verifique a mensagem e o foco ou orientação esperados.
4. Preencha dados válidos usando interação de usuário, envie e confira a confirmação visível.
5. Torne temporariamente uma regra de validação inoperante para confirmar que o teste falha; restaure a regra e mantenha a assertion que detecta o defeito.

**Dica:** não chame a função de submit diretamente. O objetivo é passar pelo mesmo controle que uma pessoa usaria.

**Entrega:** testes para validação, submissão válida e confirmação, com uma nota sobre a falha introduzida e detectada.

**Critérios de conclusão:** testes encontram controles semanticamente; cobrem resultado válido e inválido; falham quando a regra importante é removida.

### Atividade 2 — Cubra estados assíncronos de uma lista
**Objetivo:** verificar como a interface responde a carregamento, sucesso, vazio e erro de uma consulta.

**Passos:**
1. Escolha uma lista carregada por uma função de API ou serviço isolável.
2. Controle essa fronteira para fornecer uma resposta lenta e depois uma resposta com itens; confirme o indicador e o conteúdo final.
3. Forneça uma lista vazia e confira a mensagem contextual de estado vazio.
4. Rejeite a consulta e verifique a mensagem de erro e a ação de recuperação apresentada.
5. Aguarde mudanças assíncronas com `findBy...` ou uma espera explícita adequada; evite atrasos fixos sem relação com a condição esperada.

**Dica:** cada caso deve começar com estado independente e resultado controlado. Não dependa de uma API externa ou da rede real para decidir o resultado do teste.

**Entrega:** testes determinísticos para carregamento, sucesso, vazio e erro.

**Critérios de conclusão:** todos os estados são percebidos pelo usuário; a falha não é confundida com vazio; os casos podem rodar em qualquer ordem.

### Atividade 3 — Revise isolamento, mocks e valor das assertions
**Objetivo:** identificar uma suíte frágil e torná-la capaz de detectar uma regressão plausível.

**Passos:**
1. Selecione um teste existente que use muitas classes internas, snapshot amplo ou mock de comportamento central.
2. Escreva em linguagem simples qual contrato do componente o teste deveria garantir.
3. Substitua dependências externas por respostas controladas, mantendo intacto o componente e a regra sob teste.
4. Garanta que dados, mocks e estado sejam preparados e limpos por caso, sem depender de outra execução.
5. Introduza uma alteração temporária plausível, como esconder uma mensagem ou ignorar um filtro, e confirme que a assertion relevante falha; depois restaure o comportamento.

**Dica:** um teste pode afirmar chamadas de função como evidência auxiliar, mas deve verificar também o resultado visível quando esse resultado é o contrato.

**Entrega:** teste revisado, descrição do defeito simulado e breve justificativa do limite do mock.

**Critérios de conclusão:** o teste não depende de detalhes internos frágeis; controla somente a dependência necessária; detecta a regressão simulada e roda isoladamente.

## Critério de conclusão
Conclua quando uma suíte de componente verifica comportamentos válidos e inválidos por consultas semânticas, aguarda resultados assíncronos pela condição correta, controla dependências externas e demonstra que suas assertions detectam ao menos uma regressão plausível.
