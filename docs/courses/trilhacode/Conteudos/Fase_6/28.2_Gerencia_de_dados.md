# 28.2 — Gerência de dados

## Objetivo
Definir a fonte de verdade para dados locais, compartilhados e remotos; configurar identidade e frescor de consultas; e manter o cache coerente após leituras, mutações, falhas e troca de sessão.

## Microtópico 1 — Classifique a origem e a fonte de verdade
Antes de escolher onde guardar um valor, descubra quem o cria e quem pode alterá-lo. Estado **local de interface** atende uma interação limitada, como um modal aberto ou um rascunho de campo. Estado **compartilhado no cliente** atravessa componentes ou telas, como uma preferência de visualização. Dados **remotos** vêm de uma API e podem ser alterados por outras pessoas ou processos; o servidor é a fonte autoritativa.

Uma tela pode manter uma representação derivada para desenhar ou editar, mas deve saber de onde ela veio e como será reconciliada. Por exemplo, um formulário pode manter um rascunho local enquanto a pessoa digita e enviar uma mutação ao servidor ao salvar. Isso não transforma o rascunho na fonte autoritativa do perfil. Copiar toda resposta da API para uma store global cria duas versões potencialmente divergentes e exige que a aplicação sincronize ambas.

| Exemplo | Origem/fonte autoritativa | Estado adequado para começar |
| --- | --- | --- |
| Modal de confirmação aberto | Interface atual | Estado local do componente |
| Preferência de layout compartilhada entre telas | Escolha do usuário no cliente | Store de cliente ou preferência persistida, conforme o requisito |
| Lista de pedidos | API/servidor | Cache de consultas remotas |
| Texto ainda não salvo em um formulário | Edição atual da pessoa | Rascunho local, enviado como mutação |
| Página e filtro que devem ser compartilhados por link | URL | Parâmetros da URL e consulta remota derivada deles |

Persistir também é uma decisão de produto: sobreviver a navegação, fechar e abrir a aba, ou compartilhar por link são requisitos diferentes. Não persista dados por padrão sem avaliar privacidade, expiração e comportamento de logout.

## Microtópico 2 — Dê identidade estável às consultas
Uma consulta precisa de uma chave que identifique exatamente o resultado que está buscando. No TanStack Query, a query key é uma estrutura serializável, normalmente um array. Inclua os parâmetros que alteram a resposta: recurso, identificador, página, filtro, ordenação ou escopo de conta quando aplicável. Assim, resultados de consultas diferentes não são tratados como se fossem o mesmo dado.

Uma regra prática: se mudar uma variável usada pela função de consulta e isso puder mudar os dados retornados, essa variável deve fazer parte da chave. Não inclua valores voláteis sem necessidade, pois isso fragmenta o cache. Não use a chave como depósito de segredos: chaves podem aparecer em ferramentas de depuração, logs ou telemetria. Use identificadores não sensíveis e proteja o acesso à própria aplicação no servidor.

Chaves hierárquicas facilitam encontrar famílias de consultas para invalidar. Por exemplo, `['orders']` pode identificar a família e `['orders', { page, status }]` uma lista com parâmetros específicos. Mantenha uma convenção consistente e evite objetos ou funções não serializáveis como parte da identidade.

## Microtópico 3 — Entenda frescor e ciclo de vida do cache
Cache diminui buscas repetidas e pode manter a interface útil enquanto novos dados chegam. **Frescor** e **permanência no cache** são decisões distintas: `staleTime` define por quanto tempo uma resposta é considerada fresca para fins de revalidação; o tempo de coleta de consultas inativas governa por quanto tempo dados sem observadores permanecem guardados. Dados obsoletos ainda podem ser exibidos, mas podem motivar uma nova busca conforme as opções da consulta e eventos configurados.

Não existe um único prazo certo para todos os dados. Uma lista que muda com frequência pode precisar ser revalidada mais cedo que uma tabela de referência quase imutável. Configure o comportamento com base no custo de dados desatualizados, frequência de mudança e custo da rede. Se a tela precisa atualizar periodicamente, polling é uma política separada e deve ser avaliado conscientemente. Leia os padrões da biblioteca adotada, porque revalidação em montagem, foco da janela, reconexão e tentativas podem explicar buscas que parecem inesperadas.

Invalidar uma família de consultas marca o dado como precisando de atualização e permite que a biblioteca reconcilie as consultas relevantes com o servidor. A invalidação não é sinônimo de apagar todos os dados nem garante que toda consulta futura desapareça; entenda o filtro de chave usado e o comportamento da versão instalada.

## Microtópico 4 — Reconcilie mutações, falhas e identidade do usuário
Depois de uma mutação bem-sucedida, escolha uma estratégia para manter as leituras coerentes:

1. **Invalidar e buscar novamente:** simples e robusto quando a resposta do servidor é a autoridade e o custo de uma nova leitura é aceitável.
2. **Atualizar o cache com a resposta da mutação:** evita uma busca quando a API devolve o registro atualizado completo e a chave do cache é conhecida.
3. **Atualizar otimisticamente:** mostra o resultado antes da confirmação do servidor. Exige guardar o valor anterior ou uma ação de rollback, tratar falha e considerar atualizações simultâneas ou buscas que poderiam sobrescrever a previsão.

Prefira a estratégia mais simples que atenda à experiência. Uma atualização otimista não é apenas “mudar o cache antes”: é preciso prever como desfazer a mudança e reconciliar o estado final. Se o rollback de uma lista inteira puder apagar uma alteração concorrente mais nova, limite o escopo da atualização, use identificadores e considere invalidar e buscar novamente ao final.

Se a mutação falhar, comunique o resultado sem apagar o rascunho da pessoa quando for seguro preservá-lo. O erro do cliente não prova sempre que o servidor não aplicou a ação; uma queda durante a resposta pode deixar o resultado incerto. Operações de escrita precisam de contrato de repetição e resolução de ambiguidade apropriados.

Ao encerrar sessão ou trocar de conta, trate dados em cache ligados à identidade anterior. Remova ou isole esses dados conforme o modelo de sessão para que outra pessoa usando o mesmo navegador não veja conteúdo anterior. A proteção real continua no servidor: ocultar um botão ou limpar a interface não substitui autenticação e autorização por recurso.

## Resumo
- Classifique dados por origem, escopo e ciclo de vida; o servidor continua autoritativo para dados remotos.
- A chave da consulta deve conter os parâmetros que mudam a resposta, sem carregar segredos desnecessários.
- Frescor (`staleTime`) e permanência de dados inativos no cache controlam aspectos diferentes.
- Após mutações, escolha invalidação, atualização com resposta do servidor ou atualização otimista com reconciliação adequada.
- Falhas, mudanças de conta e logout exigem cuidado com dados obsoletos ou pertencentes a outra identidade.

## Quiz
1. “Modal aberto” costuma ser dado remoto? **Não. É estado local da interface, a menos que exista um requisito específico que o persista ou compartilhe.**
2. A função de uma consulta usa `page` e `status` para buscar pedidos. O que deve aparecer na query key? **Os dois parâmetros, porque ambos podem alterar o resultado e a identidade da resposta.**
3. `staleTime` determina por quanto tempo uma consulta inativa fica armazenada antes da coleta? **Não. Frescor e coleta de dados inativos são configurações diferentes.**
4. A API devolve o registro atualizado completo após uma edição. Cite duas estratégias válidas para atualizar a interface. **Atualizar a entrada de cache com a resposta ou invalidar a consulta relacionada para buscar novamente.**
5. Uma alteração otimista falhou enquanto outra atualização simultânea ocorreu. Por que restaurar cegamente um snapshot antigo pode ser perigoso? **Pode apagar a atualização concorrente mais recente; o rollback precisa considerar escopo e concorrência e reconciliar com o servidor.**

## Atividades

### Atividade 1 — Mapeie a fonte de verdade e os ciclos de vida
**Objetivo:** propor um desenho de estado coerente para uma aplicação com áreas públicas e autenticadas.

**Passos:**
1. Use um cenário com sessão, modal, filtro, lista paginada da API, formulário de edição, preferência de tema, indicador de erro e contador do servidor.
2. Para cada item, anote origem, fonte autoritativa, componentes consumidores, ciclo de vida e se deve sobreviver à navegação ou recarga.
3. Escolha estado local, URL, store de cliente ou cache remoto para cada item e explique a decisão.
4. Marque quais dados devem ser removidos ou isolados ao sair da conta e quais não podem ser protegidos apenas pelo cliente.
5. Desenhe o fluxo de edição do formulário desde o rascunho local até a resposta do servidor e a atualização da tela.

**Dica:** “global” descreve alcance entre componentes; “remoto” descreve origem e autoridade. Um dado não é remoto só porque muitos componentes o leem.

**Entrega:** matriz de classificação e diagrama do fluxo de leitura e edição.

**Critérios de conclusão:** cada item tem uma fonte autoritativa; persistência está ligada a um requisito; o desenho separa autenticação no servidor de apresentação no cliente.

### Atividade 2 — Construa chaves e política de frescor
**Objetivo:** impedir colisões entre resultados e decidir como cada consulta envelhece.

**Passos:**
1. Modele consultas para detalhe de pedido, lista paginada por status e perfil da conta autenticada.
2. Proponha chaves serializáveis que incluam identificadores e parâmetros capazes de alterar cada resposta.
3. Identifique quais parâmetros são sensíveis e não devem aparecer na chave; use identificadores não secretos para distinguir escopos quando necessário.
4. Para cada consulta, defina o que significa dado fresco para o produto e qual custo haveria se a tela mostrasse dado antigo.
5. Registre quando a consulta pode revalidar, quando dados inativos podem ser coletados e como verificaria uma mudança de status, reconexão ou retorno à tela.

**Dica:** não copie um mesmo prazo de frescor para todos os recursos. Use a necessidade de atualização e o comportamento observado para justificá-lo.

**Entrega:** catálogo de query keys e tabela de políticas de frescor e revalidação.

**Critérios de conclusão:** parâmetros variáveis estão representados; as chaves não incluem segredos; frescor e coleta estão documentados como decisões distintas.

### Atividade 3 — Implemente uma mutação com reconciliação
**Objetivo:** manter detalhe e lista coerentes após edição e falha.

**Passos:**
1. Implemente uma edição de item com rascunho de formulário local e uma resposta previsível de sucesso ou erro.
2. Escolha entre invalidar as consultas relacionadas e atualizar o cache com a resposta do servidor; documente o motivo.
3. Se implementar atualização otimista, salve informação suficiente para desfazer a previsão, impeça que uma busca antiga sobrescreva a alteração e descreva como tratar mutações concorrentes.
4. Simule sucesso, erro de validação, falha de rede após envio e duas atualizações próximas; observe mensagem, rascunho, detalhe e lista em cada caso.
5. Faça logout e entrada com outra conta de teste; confirme que dados privados da sessão anterior não aparecem e que a API continua verificando autorização.

**Dica:** se a atualização otimista não for necessária para a experiência, invalidar e aceitar o estado confirmado pelo servidor é uma solução válida e mais simples.

**Entrega:** fluxo de edição, estratégia de cache documentada e registro dos cenários de sucesso, falha e troca de sessão.

**Critérios de conclusão:** lista e detalhe convergem ao mesmo estado; falha não elimina entrada útil; rollback não descarta atualização concorrente conhecida; dados de outra sessão não ficam visíveis.

## Critério de conclusão
Conclua quando cada dado tem fonte e ciclo de vida justificados, chaves identificam os resultados sem expor segredos, a política separa frescor de coleta, e uma mutação mantém lista e detalhe coerentes em sucesso, falha e concorrência. O servidor deve continuar responsável por autorizar o acesso.
