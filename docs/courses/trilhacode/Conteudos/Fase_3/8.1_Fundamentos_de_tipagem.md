# 8.1 — Fundamentos de tipagem

## Objetivo
Descrever valores JavaScript com tipos primitivos, usar inferência e unions, estreitar tipos por verificações e nomear estruturas com aliases e interfaces.

## Teoria

### 1. Tipos primitivos e anotações
TypeScript acrescenta verificação estática de tipos ao JavaScript. Um tipo descreve quais valores e operações o compilador aceita em determinado ponto do programa. Para valores primitivos, use `string`, `number` e `boolean` em minúsculas; `String` e `Number` nomeiam objetos wrapper e normalmente não são os tipos desejados. Arrays podem ser escritos, por exemplo, como `string[]`.

Uma anotação explícita comunica um contrato:

```ts
let nome: string = "Lia";
let tentativas: number = 0;
const nomes: string[] = ["Lia", "Caio"];
```

O compilador usa essas informações para apontar usos incompatíveis durante a checagem. As anotações de tipo não transformam os valores nem validam automaticamente dados recebidos de usuário, arquivo ou API em tempo de execução.

**Erro comum:** supor que declarar `nome: string` converte um número em texto. A anotação só descreve o valor esperado e permite ao verificador encontrar incompatibilidades.

### 2. Inferência e contratos explícitos
Muitas vezes o TypeScript infere o tipo a partir do valor inicial ou do contexto. Se `const total = 12`, o compilador sabe que `total` é um número sem precisar repetir `: number`. Prefira inferência quando a intenção estiver evidente; anote parâmetros e contratos públicos quando isso ajudar a leitura ou quando a inferência não puder determinar o tipo.

```ts
const quantidade = 3; // inferido como number
const saudacao = (nome: string) => "Olá, " + nome;
// retorno inferido como string
```

Uma variável inicializada como `let estado = "aberto"` pode receber um tipo mais estreito do que `string`, de acordo com o contexto e as atribuições. Quando a intenção é aceitar várias alternativas, declare-as claramente em vez de depender de uma atribuição inicial ambígua.

**Erro comum:** anotar absolutamente toda variável ou, no extremo oposto, deixar parâmetros públicos sem tipo. Escolha anotações que clarificam o contrato; deixe a inferência cuidar do que já está claro.

### 3. Unions e narrowing
Uma union representa um valor que pode pertencer a mais de um tipo, como `string | number`. Antes de usar uma operação disponível somente em uma alternativa, faça uma checagem que permita ao TypeScript estreitar (narrow) o tipo naquele fluxo.

```ts
type Identificador = string | number;

function exibirId(id: Identificador): string {
  if (typeof id === "string") {
    return id.toUpperCase();
  }
  return id.toFixed(0);
}
```

Dentro do primeiro ramo, `id` é reconhecido como texto; no segundo, como número. Verificações como `typeof`, comparações com `null` e checagem de propriedades podem estreitar tipos. A union não significa que toda operação será aceita: fora dos ramos, só use propriedades e operações válidas para todas as alternativas.

**Erro comum:** chamar `toUpperCase()` diretamente em `string | number`. Faça a verificação primeiro; evitar a asserção de tipo indiscriminada deixa o código e sua condição de segurança explícitos.

### 4. Aliases, interfaces e forma dos objetos
Um `type alias` dá um nome a um tipo, seja primitivo, union ou estrutura de objeto. Uma `interface` nomeia principalmente a forma de um objeto e pode ser estendida; declarações compatíveis com o mesmo nome podem ser mescladas. Para muitos objetos simples, ambos podem descrever a mesma forma. Use alias quando precisar nomear uma union, e escolha interface ou alias de objeto conforme a intenção e convenção do projeto.

```ts
type StatusTarefa = "aberta" | "em-andamento" | "concluida";

interface Tarefa {
  id: number;
  titulo: string;
  status: StatusTarefa;
  descricao?: string;
}
```

O `?` indica que uma propriedade pode não existir. Ao lê-la, trate a ausência, por exemplo com `tarefa.descricao ?? "Sem descrição"`. A compatibilidade de objetos é estrutural: importa se o valor tem os campos requeridos com tipos compatíveis, não se foi criado usando exatamente o nome da interface.

**Erro comum:** achar que o nome da interface cria uma classe ou existe em tempo de execução. Interfaces e anotações são parte da checagem estática; não substituem objetos reais nem validação de dados externos.

## Resumo
- Use `string`, `number`, `boolean` e tipos de array em minúsculas.
- TypeScript verifica compatibilidade estática; anotações não convertem nem validam dados em tempo de execução.
- Use inferência quando a intenção estiver clara e anote contratos quando isso ajudar.
- Uma union descreve alternativas; faça narrowing antes de usar operações exclusivas de uma forma.
- Alias pode nomear unions e outros tipos; interface descreve principalmente formas de objeto e pode ser estendida/mesclada.
- Propriedades opcionais podem estar ausentes e devem ser tratadas; compatibilidade de objetos é estrutural.

## Verificação — quiz
1. Qual tipo descreve um valor textual primitivo? **A)** `String`. **B)** `string`. **C)** `Text`. **D)** `object`. **Resposta: B.** `string` é o tipo primitivo; `String` é o tipo do objeto wrapper.

2. Que tipo descreve um identificador que pode ser número ou texto? **A)** `number & string`. **B)** `number | string`. **C)** `number[]`. **D)** `any[]`. **Resposta: B.** A barra vertical representa alternativas; `&` exigiria um valor que satisfizesse ambos os tipos.

3. O que deve ocorrer antes de chamar um método exclusivo de string em um valor `string | number`? **A)** Fazer narrowing por uma checagem. **B)** Apagar todos os tipos. **C)** Converter o projeto para JavaScript. **D)** Criar uma interface vazia. **Resposta: A.** A checagem permite ao verificador reconhecer qual alternativa está presente naquele ramo.

4. Qual afirmação compara corretamente `type` e `interface`? **A)** Só interface pode nomear objeto. **B)** Alias pode nomear unions; interface descreve principalmente formas de objeto e admite extensão/mesclagem de declarações. **C)** Ambos existem em runtime como classes. **D)** São sempre incompatíveis. **Resposta: B.** Os dois podem descrever formas simples de objeto; alias também nomeia unions e interfaces não criam classes em execução.

5. Uma propriedade está declarada como `descricao?: string`. Como o código deve tratá-la? **A)** Como sempre presente. **B)** Como possivelmente ausente, verificando ou usando um valor padrão. **C)** Como número. **D)** Como valor automaticamente convertido para texto. **Resposta: B.** Ao ler propriedade opcional, considere que ela pode ser `undefined`; a anotação não cria o campo.

## Práticas

### 1. Guiada — corrija operações inválidas numa union
Analise o código:

```ts
type Identificador = string | number;

function formatar(id: Identificador): string {
  return id.toUpperCase();
}
```

O verificador aponta que `toUpperCase` não existe para todos os valores aceitos. Altere a função para formatar texto em maiúsculas e números como texto sem casas decimais.

**Dica:** use `typeof id === "string"` e trate o outro ramo como número.

**Solução esperada:**
```ts
function formatar(id: Identificador): string {
  if (typeof id === "string") {
    return id.toUpperCase();
  }
  return id.toFixed(0);
}
```

**Aceite:** a função cobre as duas alternativas, retorna string em ambas e não usa `any` nem asserção para silenciar o verificador.

### 2. Independente — modele tarefas com contratos claros
Modele uma tarefa usando `interface Tarefa` e `type StatusTarefa` como union de literais. Inclua `id`, `titulo`, `status` e uma `descricao` opcional. Escreva:
- `formatarTarefa(tarefa)`, que retorna uma linha descritiva e trata descrição ausente;
- `mudarStatus(tarefa, novoStatus)`, que devolve uma nova tarefa com status atualizado;
- um exemplo válido e um exemplo inválido de status que o verificador deve rejeitar.

Use inferência nas variáveis locais quando o tipo já estiver claro. Anote entradas e saídas das funções, justificando as anotações escolhidas.

**Dica:** combine `??` com a propriedade opcional; para atualizar sem alterar o objeto recebido, use uma cópia com spread e o novo status.

**Solução de referência:**
```ts
type StatusTarefa = "aberta" | "em-andamento" | "concluida";

interface Tarefa {
  id: number;
  titulo: string;
  status: StatusTarefa;
  descricao?: string;
}

function formatarTarefa(tarefa: Tarefa): string {
  const descricao = tarefa.descricao ?? "Sem descrição";
  return tarefa.titulo + " — " + tarefa.status + ": " + descricao;
}

function mudarStatus(tarefa: Tarefa, novoStatus: StatusTarefa): Tarefa {
  return { ...tarefa, status: novoStatus };
}

const tarefa = { id: 1, titulo: "Estudar", status: "aberta" as StatusTarefa };
const atualizada = mudarStatus(tarefa, "em-andamento");
// mudarStatus(tarefa, "pausada"); // erro: literal fora da union
```

A asserção no exemplo só fixa o tipo do literal para ilustrar a chamada; uma alternativa mais clara é declarar `const tarefa: Tarefa`. A atualização retorna outro objeto e mantém a entrada intacta.

**Rubrica (0–2 cada):** propriedades e tipos coerentes; union rejeita status não permitido; ausência da descrição tratada; atualização retorna novo objeto; anotações e inferência justificadas. **Domínio:** 8/10 pontos ou mais, incluindo pontuação máxima em union e propriedade opcional.

### 3. Integrada — tipagem de um resumo de tarefas
Escreva uma função `resumirTarefas(tarefas)` que receba uma lista de tarefas e devolva uma estrutura com:
- quantidade total;
- quantidade concluída;
- títulos das tarefas abertas;
- um rótulo para filtro que aceite `"todas"`, `"abertas"` ou `"concluidas"`.

Defina os contratos com interface e alias, use inferência para variáveis locais quando fizer sentido, e trate uma lista vazia e a descrição ausente. Inclua uma função que recebe um identificador `string | number` e devolve sua representação textual usando narrowing. Não altere a lista de entrada.

**Entregáveis:** tipos nomeados; funções tipadas; exemplos que exercitam lista vazia, campo opcional, status e ambos os formatos de identificador; breve explicação de como o verificador detecta um status inválido.

**Dica:** use `filter` para seleções; compare status com literal; teste o tipo do identificador antes de aplicar uma operação exclusiva.

**Solução de referência:** `StatusTarefa` é a union literal já proposta; `FiltroTarefas` pode ser `"todas" | "abertas" | "concluidas"`; `ResumoTarefas` pode ser uma interface com `total: number`, `concluidas: number` e `titulosAbertas: string[]`. A função usa `length` para contar a lista e `filter` para obter tarefas concluídas ou abertas. Para entrada vazia, as contagens e a lista resultam em zero e `[]`. O identificador é tratado com `typeof` antes de uma operação específica. São válidas implementações equivalentes que não mutem a entrada e atendam aos contratos.

**Rubrica (0–2 cada):** contratos expressivos; filtragem e contagens corretas; narrowing correto; casos vazios/opcionais; ausência de mutação e explicação da verificação. **Domínio:** pelo menos 8/10, sem erro em narrowing ou status union.

## Critério de conclusão
Explicar a diferença prática entre alias e interface, usar inferência com intenção, estreitar uma union antes de operações específicas e modelar objetos com propriedades opcionais tratadas corretamente.
