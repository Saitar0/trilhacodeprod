# 6.4 — Node.js e npm no dia a dia

## Objetivo
Usar Node.js para executar JavaScript fora do navegador e npm para configurar projetos, dependências, scripts e ferramentas básicas de qualidade.

## Teoria

### Node.js e execução fora do navegador
**Node.js** é um ambiente de execução de JavaScript fora do navegador. O comando `node arquivo.js` executa um arquivo. APIs do navegador, como `document` e `window`, não existem automaticamente no Node; use APIs próprias do runtime para arquivos, terminal e outros recursos do sistema. Um gerenciador de versões permite alternar entre versões quando projetos exigem versões distintas; consulte a documentação oficial no momento da instalação.

Node suporta módulos CommonJS (`require`, `module.exports`) e ECMAScript Modules (`import`, `export`). A interpretação depende da extensão e configuração do pacote, incluindo o campo `type` do `package.json`: `.mjs` e `.cjs` explicitam formatos; em arquivos `.js`, declare `"type": "module"` ou `"type": "commonjs"` no manifesto. Para este curso, escolha um formato por projeto e documente essa escolha.

### Manifesto e dependências
`npm init` cria um `package.json`, manifesto do projeto com nome, scripts, dependências e outras informações. `dependencies` são pacotes necessários à aplicação em execução; `devDependencies` apoiam o desenvolvimento, como lint, formatação e compilação. `npm install pacote` instala um pacote e atualiza o manifesto e o lockfile; `npm install --save-dev pacote` registra uma ferramenta de desenvolvimento. Inspecione o propósito do pacote antes de adicioná-lo.

### Lockfile e instalação reproduzível
`package-lock.json` registra a árvore resolvida de dependências e deve ser versionado junto do `package.json`. `npm install` pode atualizar o lockfile para conciliá-lo com o manifesto. `npm ci` exige um lockfile compatível, falha se manifesto e lock divergirem e instala a árvore registrada; antes da instalação, remove o `node_modules` existente. Use-o em um projeto ou cópia descartável.

`node_modules` contém pacotes instalados localmente e costuma ser recriado a partir do manifesto e do lockfile, por isso geralmente fica fora do Git. Um clone limpo com `npm ci` permite verificar se as dependências registradas bastam para executar os scripts.

### Scripts e ferramentas de qualidade
O campo `scripts` do `package.json` dá nomes a comandos do projeto. `npm run nome` executa um script declarado; `npm start` é uma forma abreviada convencional para o script `start`. Scripts registram como iniciar e verificar o projeto, em vez de depender de comandos memorizados.

**ESLint** analisa padrões configurados e aponta problemas ou inconsistências; **Prettier** formata código segundo regras definidas. Têm funções diferentes e podem ser usados juntos. Registre ferramentas locais em `devDependencies` e chame as versões instaladas pelo projeto. `npm audit` envia ao registry configurado informações sobre dependências para obter um relatório de vulnerabilidades conhecidas. O resultado depende dos avisos disponíveis e da árvore consultada: relatório sem avisos não prova que o aplicativo é seguro.

## Resumo
- Node executa JavaScript fora do navegador.
- `package.json` descreve projeto, scripts e dependências.
- `dependencies` servem ao runtime; `devDependencies`, às ferramentas de desenvolvimento.
- Versione `package-lock.json`; exclua `node_modules` do Git; `npm ci` remove a pasta de dependências existente antes de recriá-la.
- CommonJS e ESM são sistemas de módulos diferentes, influenciados pela extensão e pelo campo `type`.
- `npm run` executa scripts declarados no projeto.
- ESLint analisa código segundo regras configuradas; Prettier formata; `npm audit` relata vulnerabilidades conhecidas, sem certificar segurança.

## Verificação — quiz
1. Qual arquivo lista scripts e dependências do projeto npm? **A)** `package.json`. **B)** `.gitignore`. **C)** `index.html`. **D)** `node_modules.md`. **Resposta: A.** O manifesto registra essas informações; `.gitignore` define padrões ignorados pelo Git.
2. O que normalmente é versionado para reproduzir uma instalação npm? **A)** `node_modules` inteiro. **B)** `package-lock.json`. **C)** cache global. **D)** tokens do registry. **Resposta: B.** O lockfile registra a árvore resolvida; `node_modules` pode ser recriado, e cache/credenciais não substituem o manifesto versionado.
3. Qual é a função mais adequada de Prettier? **A)** Formatar código. **B)** Executar banco de dados. **C)** Substituir Node. **D)** Encontrar todas as vulnerabilidades. **Resposta: A.** Prettier formata; ESLint analisa padrões configurados. Nenhum deles substitui runtime ou detecta todas as vulnerabilidades.
4. `npm audit` sem alertas prova que o aplicativo é seguro? **A)** Sim. **B)** Não; informa vulnerabilidades conhecidas na árvore consultada, mas não prova segurança completa. **C)** Sim, se houver lockfile. **D)** Só depende do nome do pacote. **Resposta: B.** O relatório depende dos avisos disponíveis e do registry consultado; lockfile não comprova que o código esteja livre de riscos.
5. O manifesto declara `"type": "module"` e o arquivo chama-se `index.js`. Qual sintaxe de módulos deve ser usada nesse arquivo? **A)** `require` e `module.exports`. **B)** `import` e `export`. **C)** Apenas HTML. **D)** Nenhum formato. **Resposta: B.** O campo `type` com valor `module` indica ESM nos arquivos `.js` do pacote; `require` é CommonJS.

## Práticas

### 1. Guiada — leia um manifesto npm
Analise este trecho sem executar comandos:

```json
{
  "type": "module",
  "scripts": {
    "start": "node src/index.js",
    "lint": "eslint .",
    "format": "prettier . --write"
  },
  "dependencies": { "date-fns": "^4.0.0" },
  "devDependencies": { "eslint": "^9.0.0", "prettier": "^3.0.0" }
}
```

**Tarefa:** classifique cada pacote; escolha os comandos para iniciar, analisar e formatar; indique a sintaxe de módulos esperada em `src/index.js`; explique por que `node_modules` não substitui o lockfile no Git.

**Dicas graduais:** (1) associe o nome do script ao comando `npm run`; (2) diferencie uso da aplicação e ferramenta de desenvolvimento; (3) confira o campo `type`.

**Gabarito comentado:** `date-fns` é dependência de runtime neste exemplo; ESLint e Prettier são ferramentas de desenvolvimento. `npm start` chama `node src/index.js`; `npm run lint` executa a análise; `npm run format` altera arquivos por causa de `--write`. `"type": "module"` indica sintaxe ESM no `.js`. `node_modules` é a instalação local recriável; o lockfile registra a árvore destinada à instalação.

**Erro comum:** dizer que `npm run format` só verifica o estilo; no exemplo, `--write` modifica arquivos.

### 2. Independente — investigue uma instalação não reproduzível
Um projeto clonado contém `package.json` e `package-lock.json`, mas não `node_modules`. O manifesto foi editado sem atualizar o lock e `npm ci` falha.

Entregue uma sequência curta que explique por que o clone não precisa versionar `node_modules`, por que `npm ci` falhou, quando `npm install` deve reconciliar manifesto e lock e como testar em uma cópia limpa sem apagar dependências locais importantes. Inclua como analisar uma vulnerabilidade transitiva do `npm audit` sem aplicar uma correção automática às cegas.

**Dicas graduais:** (1) compare manifesto e lock; (2) `npm ci` não atualiza o lock e remove a instalação existente; (3) leia pacote, caminho transitivo, severidade e correção sugerida antes de decidir.

**Critérios de aceite:** diferença entre `npm install` e `npm ci` explicada; teste em cópia limpa; análise do relatório sem tratá-lo como certificado. Mais de uma sequência é válida se respeitar esses comportamentos.

### 3. Transferência — monte um pequeno projeto Node/npm
Crie um projeto com `npm init`, um `dados.json` fictício e um programa Node que leia o arquivo local e imprima um resumo. Declare explicitamente o formato de módulos. Configure scripts para iniciar o programa e executar ESLint e Prettier como ferramentas locais de desenvolvimento. Configure `.gitignore` para `node_modules`; versione manifesto e lockfile.

Use este dado inicial em `dados.json`:

```json
{
  "eventos": [
    { "titulo": "Aula aberta", "publicado": true },
    { "titulo": "Rascunho", "publicado": false }
  ]
}
```

No arquivo de entrada ESM, use a estrutura abaixo e complete o resumo:

```js
import { readFileSync } from "node:fs";

const caminho = new URL("../dados.json", import.meta.url);
try {
  const dados = JSON.parse(readFileSync(caminho, "utf8"));
  // TODO: imprimir quantos eventos estão publicados
} catch (erro) {
  console.error(`Não foi possível ler os dados: ${erro.message}`);
  process.exitCode = 1;
}
```

Com o JSON inicial, a saída esperada é `Eventos publicados: 1`. Altere temporariamente o JSON para um formato inválido e confirme a mensagem e o código de saída. Depois restaure o arquivo válido.

Organize o projeto com `src/index.js` como entrada e `dados.json` na raiz; o caminho relativo do exemplo já considera essa estrutura.

Instale e configure as ferramentas seguindo a documentação oficial atual. Execute `npm audit` e registre como interpretou o relatório. Em uma cópia limpa, use `npm ci` e execute os scripts documentados. **Atenção:** `npm ci` remove `node_modules` existente na pasta onde é executado; use a cópia limpa ou confirme que a pasta é descartável.


**Entregue:** árvore de arquivos, scripts do manifesto, leitor JSON completo, `.gitignore`, lockfile e nota sobre o audit. Demonstre JSON válido e inválido conforme o cenário acima. Não é necessário publicar o projeto.


**Dicas graduais:** (1) complete o contador com `dados.eventos.filter((evento) => evento.publicado).length`; (2) converta o texto com `JSON.parse` e preserve o tratamento de erro; (3) instale ferramentas com `--save-dev` e chame-as por scripts npm; (4) valide em cópia limpa com `npm ci`.

**Aceite:** cópia limpa instala pelo lockfile e executa os scripts; JSON inválido gera mensagem clara e falha; `node_modules` fica fora do Git; formato de módulos explícito; ESLint analisa e Prettier formata em comandos separados; audit é interpretado como sinal, não certificado.

**Rubrica (0–2 por critério):** (1) execução e leitura JSON reproduzíveis; (2) manifesto, scripts e dependências classificados; (3) lockfile e instalação limpa tratados com segurança; (4) ferramentas e audit interpretados com limites. `0` = ausente/incorreto, `1` = parcial, `2` = claro e demonstrado. Pronto com pelo menos 6/8 e sem passos manuais não documentados.

## Critério de conclusão
Em outra cópia do repositório, instalar dependências e executar o script sem passos manuais não documentados; explicar o papel do `package-lock.json`, `node_modules` e scripts.
