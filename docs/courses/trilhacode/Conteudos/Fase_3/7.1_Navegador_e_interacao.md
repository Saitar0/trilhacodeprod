# 7.1 — Navegador e interação

## Objetivo
Manipular o DOM com JavaScript, responder a eventos e validar um formulário preservando os comportamentos nativos e acessíveis do navegador.

## Teoria

### DOM e seleção de elementos
O **DOM** (Document Object Model) representa o documento carregado como uma árvore de nós e objetos. É uma API da plataforma web, não uma parte exclusiva da linguagem JavaScript. O navegador cria essa representação a partir do HTML; scripts podem localizar elementos e atualizar conteúdo, atributos ou estrutura.

`document.querySelector()` localiza o primeiro elemento que corresponde a um seletor CSS. Se nenhum elemento corresponder, retorna `null`; confira o resultado antes de acessar suas propriedades. O seletor precisa ser CSS válido, então um seletor malformado também pode gerar erro.

### Texto e marcação no DOM
Para texto visível, `textContent` escreve texto sem interpretá-lo como HTML. `innerHTML` interpreta a string como marcação e substitui os descendentes do elemento; não use conteúdo não confiável com `innerHTML` sem um processo adequado de sanitização. Para mostrar o que alguém digitou como texto, prefira `textContent`.

### Eventos e comportamento padrão
**Eventos** representam acontecimentos como clique, envio de formulário e digitação. `addEventListener()` associa uma função ao evento. O objeto recebido pelo handler oferece contexto, como o alvo do evento. Em formulários, ouça `submit` no próprio `<form>` para cobrir envio pelo botão e envio por teclado.

`preventDefault()` cancela o comportamento padrão do evento. Use-o somente quando a aplicação vai tratar a ação no lugar do navegador, como mostrar uma confirmação local sem navegar ou recarregar. Não impede a execução dos outros handlers e não valida dados por si só.

### Formulários e validação nativa
HTML oferece restrições nativas, como `required`, `type="email"` e `minlength`. Quando os dados não passam pela validação nativa, o navegador normalmente não dispara `submit` e informa o campo inválido. Para dados válidos, o handler de `submit` pode impedir o envio tradicional e atualizar a página. Controles precisam de `name` para aparecer em `FormData`; labels associados ajudam a identificar os campos.

Mensagens adicionais devem explicar o problema em texto e ser associadas ao campo quando necessário; não dependa apenas de cor. Um status de confirmação pode usar uma região `aria-live` para ser anunciado por tecnologias assistivas. Validação no navegador melhora a experiência, mas não estabelece confiança nos dados.

### Limites da validação no cliente
JavaScript executado no navegador pode ser alterado ou contornado. A interface pode sinalizar erros cedo, mas o servidor precisa validar novamente todos os dados recebidos e aplicar as regras de segurança. Uma validação no cliente não autoriza nem protege a persistência por conta própria.

```js
const formulario = document.querySelector("#contato");
const resultado = document.querySelector("#resultado");

if (formulario && resultado) {
  formulario.addEventListener("submit", (event) => {
    event.preventDefault();
    const dados = new FormData(formulario);
    resultado.textContent = `Recebido: ${dados.get("email")}`;
  });
}
```

O navegador verifica as restrições nativas antes de disparar `submit`. O código acima então intercepta o envio válido e apresenta o e-mail como texto. O atributo `name="email"` deve existir no controle; neste exemplo, o handler não envia dados para um servidor.

## Resumo
- DOM é a representação manipulável do documento em memória.
- `querySelector` seleciona elementos; confirme existência antes de acessar.
- Eventos conectam ações da pessoa a funções.
- `preventDefault()` cancela comportamento padrão e deve ser usado intencionalmente.
- Validação nativa ajuda; regras específicas podem ser acrescentadas com mensagens claras.
- Validação no cliente não substitui validação no servidor.
- Prefira `textContent` para texto e trate com cuidado conteúdo inserido como HTML.

## Verificação — quiz
1. O que o DOM representa? **A)** Árvore de nós/objetos que modela o documento. **B)** Banco de dados obrigatório. **C)** Um framework. **D)** Apenas CSS. **Resposta: A.** O DOM modela o documento carregado e pode ser consultado por APIs da plataforma; não é banco de dados, framework nem somente estilo.
2. Para que serve `addEventListener("submit", handler)`? **A)** Registrar resposta ao envio do formulário. **B)** Criar o HTML. **C)** Enviar sempre ao banco. **D)** Instalar uma biblioteca. **Resposta: A.** O listener chama o handler quando o evento ocorre. Ele não cria a estrutura, não envia automaticamente ao banco e não instala dependências.
3. Validação no navegador garante que dados enviados ao servidor são confiáveis? **A)** Sim. **B)** Não; cliente pode ser contornado e servidor deve validar. **C)** Só com `required`. **D)** Sim, se usar TypeScript. **Resposta: B.** A pessoa pode contornar o JavaScript e enviar requisições próprias; validação no servidor continua necessária. `required` e TypeScript não mudam essa fronteira de confiança.
4. Ao mostrar texto digitado pela pessoa, qual opção evita interpretar o valor como marcação HTML? **A)** `textContent`. **B)** `innerHTML` sem revisão. **C)** `eval`. **D)** `style`. **Resposta: A.** `textContent` insere texto. `innerHTML` interpreta marcação, `eval` executa código e `style` não é um mecanismo de saída de texto.
5. Um script registra `submit` e chama `event.preventDefault()` depois de apresentar uma confirmação local. Qual é o efeito dessa chamada? **A)** Cancela o comportamento padrão de envio/navegação associado ao evento. **B)** Valida automaticamente os dados no servidor. **C)** Remove todos os listeners. **D)** Impede que o navegador crie o DOM. **Resposta: A.** `preventDefault()` cancela a ação padrão daquele evento; não substitui validação, não remove listeners e não controla a criação do DOM.

## Práticas

### 1. Guiada — selecione e escreva conteúdo com segurança
Considere:

```html
<p id="resultado"></p>
```

```js
const resultado = document.querySelector("#resultdo");
const entrada = "<strong>Olá</strong>";
resultado.innerHTML = entrada;
```

**Tarefa:** identifique os dois problemas, preveja o que aconteceria se o seletor fosse corrigido e reescreva para exibir a entrada literalmente como texto. Inclua uma proteção para o caso de o seletor não encontrar elemento.

**Dicas graduais:** (1) compare o `id` do HTML ao seletor; (2) lembre-se de que `querySelector` pode retornar `null`; (3) escolha a API que não interpreta a string como marcação.

**Solução comentada:** o seletor contém erro de digitação e retorna `null`; acessar `resultado.innerHTML` então gera erro. Corrija para `#resultado`, verifique `if (resultado)` e use `resultado.textContent = entrada`. A página exibirá os caracteres `<strong>Olá</strong>` como texto, sem criar um elemento em negrito. Não é necessário sanitizar uma string se a intenção é exibi-la como texto.

**Erro comum:** corrigir o seletor e manter `innerHTML`; isso transforma texto fornecido pela pessoa em marcação interpretável.

### 2. Independente — implemente um contador acionado por evento
Parta deste HTML:

```html
<button id="adicionar" type="button">Adicionar</button>
<p id="total" aria-live="polite">Itens: 0</p>
```

Implemente o JavaScript para que cada clique incremente o número e atualize o parágrafo. Confira se os elementos existem antes de registrar o listener. Teste também com teclado e explique por que um `<button>` nativo é adequado para essa ação.

**Dicas graduais:** (1) o estado numérico muda, então use `let`; (2) registre `click` com `addEventListener`; (3) atualize o texto com `textContent` e não recrie o parágrafo.

**Critérios de aceite:** cada ativação aumenta exatamente uma unidade; o valor inicial é zero; teclado ativa o botão; a região de status anuncia atualizações; se o seletor estiver ausente, o script não lança erro ao acessar o elemento.

### 3. Transferência — formulário interativo acessível
Construa um formulário de contato sem framework com nome, e-mail e mensagem. Use labels associados, `name` nos controles, `required`, `type="email"` e uma restrição mínima razoável para mensagem. Adicione um handler de `submit` que processe apenas o envio válido e mostre uma confirmação sem recarregar a página. Associe o status a uma região `aria-live="polite"`; mantenha mensagens compreensíveis e não dependa apenas de cor.

Teste campos vazios, e-mail malformado, mensagem abaixo do mínimo e envio válido com teclado. Use `FormData` para ler os valores. Mostre o conteúdo recebido com `textContent`; não envie HTML digitado para `innerHTML`. Como não há servidor nesta atividade, indique que validação real e persistência ainda precisariam ocorrer no servidor.

**Entregue:** HTML e JavaScript, evidência dos quatro cenários de validação, comportamento do formulário sem JavaScript e nota sobre o limite de confiança do cliente. Na submissão válida interceptada, explique por que `preventDefault()` é necessário.

**Dicas graduais:** (1) deixe a validação nativa impedir `submit` inválido; (2) só no evento válido, chame `preventDefault()` para manter a pessoa na página; (3) construa `FormData` com controles que tenham `name`; (4) atualize a confirmação com texto e região anunciável.

**Aceite:** formulário mantém estrutura útil sem JavaScript; erros nativos e restrições são claros; envio inválido não produz confirmação; envio válido mostra o resultado sem recarga; controles funcionam por teclado e possuem labels; dados são tratados como texto; limite de validação no cliente está documentado.

**Rubrica (0–2 por critério):** (1) seleção segura e tratamento de elemento ausente; (2) evento e comportamento padrão explicados; (3) formulário semântico e validação observável; (4) saída acessível e limite cliente/servidor reconhecido. `0` = ausente/incorreto, `1` = parcial, `2` = claro e demonstrado. Pronto com pelo menos 6/8 e sem saída de texto interpretada como HTML.

## Critério de conclusão
Explicar a relação entre HTML e DOM e demonstrar uma validação que impede envio inválido sem remover a semântica ou acessibilidade do formulário.
