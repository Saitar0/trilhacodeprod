# 7.3 — Dados e comunicação

## Objetivo
Consumir dados HTTP com `fetch`, interpretar JSON, usar promises e `async/await`, e distinguir falhas de rede, respostas HTTP malsucedidas, dados inválidos e bloqueios de CORS.

## Teoria

### 1. Dados JSON e contrato da API
JSON é um formato textual de intercâmbio de dados. Embora objetos e arrays JSON se pareçam com literais JavaScript, JSON tem sintaxe própria: chaves e strings usam aspas duplas, não há funções nem valores como `undefined`, e uma vírgula final torna o texto inválido. `JSON.parse(texto)` converte texto JSON válido em valores JavaScript; `JSON.stringify(valor)` cria texto JSON a partir de valores compatíveis.

Uma API também define um **contrato**: quais campos envia, quais campos espera e que tipo de resultado representa sucesso ou falha. Receber JSON válido não garante que a estrutura é a esperada. Se o código precisa de `produto.nome`, confirme que cada item contém esse campo antes de usá-lo ou mostrá-lo.

```js
const texto = '[{"nome":"Caderno","preco":18}]';
const produtos = JSON.parse(texto);
console.log(produtos[0].nome); // "Caderno"
```

**Erro comum:** tratar “o corpo foi convertido em JSON” como prova de que os dados têm os campos e tipos necessários. Sintaxe válida e formato esperado são verificações diferentes.

### 2. Requisição HTTP e fluxo assíncrono
Métodos HTTP comunicam a intenção da operação. `GET` costuma consultar; `POST` costuma enviar dados para criação ou processamento; `PUT` substitui uma representação; `PATCH` pede uma alteração parcial; `DELETE` solicita remoção. O comportamento concreto depende do contrato da API. Headers carregam metadados: `Accept` indica formatos que o cliente pode receber; `Content-Type` descreve o formato do corpo enviado.

Uma Promise representa um resultado futuro que pode ser cumprido ou rejeitado. Uma função `async` sempre devolve uma Promise. `await` permite esperar por uma Promise e continuar o fluxo da função quando ela se resolver; não bloqueia toda a interface. Uma rejeição esperada deve ser tratada com `try/catch` ou com `.catch()`.

```js
async function buscarProdutos(url) {
  const resposta = await fetch(url, {
    headers: { Accept: "application/json" },
  });
  return resposta;
}
```

A chamada `fetch` inicia uma operação assíncrona. O `await` anterior a ela pausa essa função até que haja uma resposta disponível, enquanto o navegador pode continuar processando outras interações.

**Erro comum:** esquecer `await` e tentar ler `response.ok` do próprio objeto Promise, antes de receber o objeto Response.

### 3. Resposta HTTP, corpo e parsing
`fetch` normalmente resolve sua Promise quando recebe uma resposta HTTP, mesmo que o status seja `404` ou `500`. Por isso, verifique `response.ok` (verdadeiro para status de sucesso 2xx) ou `response.status` explicitamente. Só depois leia o corpo. `response.json()` também é assíncrono e rejeita se o corpo não puder ser interpretado como JSON.

```js
async function carregarProdutos() {
  const resposta = await fetch("/api/produtos", {
    headers: { Accept: "application/json" },
  });

  if (!resposta.ok) {
    throw new Error(`HTTP ${resposta.status}`);
  }

  return await resposta.json();
}
```

Neste exemplo, falha ao obter a resposta e resposta HTTP não bem-sucedida são situações distintas. Uma resposta 404 não dispara sozinha o `catch`: o código a converte em erro ao verificar `ok`. Se o servidor responder com HTML de erro ou JSON malformado, a leitura com `json()` também pode falhar.

**Erro comum:** mostrar “erro de rede” para todo problema. Registre status quando uma resposta HTTP existe; diferencie a falha de transporte da falha de status e da falha de parsing.

### 4. Estados da interface, rede e CORS
Uma interface que carrega dados deve representar os estados relevantes: carregando, sucesso (inclusive resultado vazio, se a API o permitir) e falha. Garanta que o estado de carregamento termine tanto no sucesso quanto no erro; `finally` é útil para uma limpeza comum. Exiba dados externos como texto, por exemplo com `textContent`, e não como HTML interpretável sem necessidade.

Uma falha de rede pode ocorrer antes que o JavaScript receba uma resposta, por exemplo quando a conexão falha. Já HTTP 500 significa que uma resposta chegou com status de erro. Um erro de parsing significa que o corpo não corresponde ao formato JSON esperado pelo leitor.

CORS (Cross-Origin Resource Sharing) controla, por meio de headers HTTP, se o navegador permite que uma página leia uma resposta de outra origem. A origem inclui esquema, host e porta. Para certas requisições, o navegador envia um preflight `OPTIONS` para verificar permissões antes da operação. A autorização necessária é configurada no servidor/API. `mode: "no-cors"` não é solução para obter dados: a resposta se torna opaca e o JavaScript não consegue ler seu corpo ou status.

**Erro comum:** tentar contornar CORS desligando proteções do navegador ou usar `no-cors` esperando receber JSON legível. Verifique a mensagem do console e, quando for CORS, ajuste a configuração do servidor que controla a API.

## Resumo
- JSON é texto com regras de sintaxe próprias; parsing válido não confirma que o formato dos dados atende ao contrato esperado.
- `fetch` e `response.json()` são assíncronos; `async/await` organiza o fluxo sem bloquear toda a interface.
- Uma resposta HTTP 404/500 geralmente resolve `fetch`; confira `response.ok` ou `status`.
- Diferencie falha de rede, status HTTP malsucedido, erro de parsing e forma inesperada dos dados.
- Modele carregamento, sucesso e falha na interface e finalize o estado de carregamento em todos os caminhos.
- CORS depende de headers e da configuração do servidor; `no-cors` torna a resposta opaca, não legível.

## Verificação — quiz
1. `fetch` recebeu uma resposta HTTP 404. O que geralmente acontece? **A)** A Promise de `fetch` é rejeitada automaticamente. **B)** Ela resolve com um `Response` cujo `ok` é falso. **C)** O navegador transforma o corpo em JSON. **D)** A política CORS é desligada. **Resposta: B.** Status HTTP de erro não rejeita, por si só, a Promise de `fetch`; o código deve verificar `ok` ou `status`.

2. O que `await` faz numa função `async`? **A)** Espera a Promise e deixa a função continuar com o resultado ou tratar a rejeição. **B)** Bloqueia toda a interface até a rede responder. **C)** Converte a resposta automaticamente para JSON válido. **D)** Altera o status HTTP para sucesso. **Resposta: A.** A pausa afeta a continuação da função assíncrona, não o navegador inteiro; conversão e status precisam ser tratados separadamente.

3. Qual é a ordem apropriada para obter uma lista JSON e identificar uma resposta HTTP malsucedida? **A)** verificar `response.ok`, depois ler o corpo com `response.json()`. **B)** chamar `response.json()` antes de aguardar `fetch`. **C)** assumir que todo `Response` tem status 200. **D)** chamar `JSON.stringify(response)`. **Resposta: A.** Primeiro confira o status HTTP; a leitura do corpo é outra operação assíncrona e também pode falhar.

4. O servidor respondeu HTTP 200, mas `response.json()` falhou. Qual hipótese descreve melhor o problema? **A)** O corpo não pôde ser interpretado como JSON. **B)** O servidor não respondeu. **C)** O status 200 significa que o conteúdo é sempre JSON válido. **D)** É obrigatoriamente erro de CORS. **Resposta: A.** A resposta chegou com sucesso HTTP, mas o corpo pode estar vazio, malformado ou em outro formato.

5. Uma aplicação não consegue ler uma resposta de outra origem por CORS. Onde deve ser configurada a permissão necessária? **A)** No servidor/API que responde, usando os headers adequados. **B)** Em `JSON.parse` no cliente. **C)** Em uma regra CSS. **D)** Em `mode: "no-cors"` para manter o corpo legível. **Resposta: A.** O servidor autoriza origens; `no-cors` não dá acesso ao corpo ou status da resposta opaca.

## Práticas

### 1. Guiada — rastreie quatro resultados diferentes
Leia cada cenário e classifique o resultado como: (a) falha de rede/CORS antes de obter resposta legível; (b) HTTP não bem-sucedido; (c) erro ao interpretar JSON; ou (d) JSON válido, porém fora do formato esperado. Depois escreva uma mensagem útil ao usuário para cada um.

- **Cenário A:** a conexão é interrompida e o navegador não disponibiliza um objeto `Response`.
- **Cenário B:** `fetch` recebe status 503 e `response.ok` é falso.
- **Cenário C:** status 200, mas o corpo recebido é `{ "produtos": [`.
- **Cenário D:** status 200, JSON válido `{"items":[]}`; o código procura `data.products`.

**Dica:** primeiro pergunte se existe um `Response`; depois confira status, parsing e estrutura do objeto em ordem.

**Solução esperada:** A = falha antes de resposta legível (a causa pode exigir olhar o console e distinguir rede de CORS); B = HTTP malsucedido (b); C = parsing (c); D = estrutura/contrato (d). Mensagens devem orientar a próxima ação sem afirmar causa não comprovada: “Não foi possível conectar”; “Serviço indisponível (503)”; “O serviço enviou dados inválidos”; “Resposta recebida em formato inesperado”.

**Aceite:** quatro categorias corretamente diferenciadas; mensagens não confundem HTTP com rede ou parsing e não afirmam “CORS” sem evidência.

### 2. Independente — implemente uma função de leitura robusta
Implemente `carregarCatalogo(url)` com `fetch` e `async/await`. A função deve solicitar JSON, verificar o status, interpretar o corpo e validar que o resultado contém `items` como array. Ela deve retornar esse array. Em falha HTTP, parsing ou contrato inválido, lance erro com uma mensagem que identifique a etapa, sem esconder o status quando disponível.

**Dica:** resolva em camadas: aguarde a resposta; verifique `ok`; leia JSON; cheque `Array.isArray(dados.items)`.

**Solução de referência:**
```js
async function carregarCatalogo(url) {
  const resposta = await fetch(url, {
    headers: { Accept: "application/json" },
  });

  if (!resposta.ok) {
    throw new Error(`HTTP ${resposta.status}`);
  }

  let dados;
  try {
    dados = await resposta.json();
  } catch {
    throw new Error("Corpo da resposta não é JSON válido");
  }

  if (dados === null || typeof dados !== "object" || !Array.isArray(dados.items)) {
    throw new Error("Formato inesperado: items deve ser um array");
  }

  return dados.items;
}
```

A chamada pode tratar falha de rede/CORS no componente que a utiliza, pois essas falhas rejeitam a operação antes de uma resposta legível. Aceite mensagens equivalentes que indiquem a etapa e preservem o status HTTP.

**Rubrica (0–2 cada):** aguarda a resposta e verifica status; trata leitura/parsing; valida estrutura; mantém as categorias de erro compreensíveis. **Domínio:** pelo menos 6/8, sem confundir status HTTP com falha de rede.

### 3. Integrada — catálogo remoto com estados de interface
Consuma uma API de demonstração apropriada e apresente uma lista de itens. A interface deve mostrar carregamento, sucesso com itens, resultado vazio quando permitido e mensagens de falha. Inclua uma busca local ou filtro. Registre método, URL, status (quando houver resposta) e headers relevantes para depuração; não registre tokens nem dados pessoais.

Classifique os erros de rede, HTTP não bem-sucedido, parsing e formato inesperado separadamente. Garanta que o indicador de carregamento seja removido em qualquer resultado. Mostre conteúdo externo como texto e explique o que CORS protege, como reconhecer um possível bloqueio e por que a permissão precisa ser definida no servidor.

**Entregáveis:** código executável; instruções para configurar a URL da API e iniciar o projeto; tabela curta de estados e mensagens; nota descrevendo um cenário de falha testado.

**Dicas:** reutilize `carregarCatalogo`; coloque a mudança do indicador de carregamento num `finally`; não conclua que todo erro sem status é CORS — consulte console e aba de rede para investigar.

**Rubrica (0–2 cada):** fluxo de requisição e status; parsing/contrato; estados da interface inclusive encerramento de loading; busca local; diagnóstico e comunicação de erros. **Domínio:** pelo menos 8/10, incluindo pontuação máxima em status e categorias de erro.

## Critério de conclusão
Descrever o caminho da requisição ao dado exibido, explicar por que `fetch` pode resolver com status 404, distinguir falhas de rede, HTTP, parsing e contrato, e apresentar uma interface que finaliza o loading em sucesso e erro.
