# 8.2 — Estrutura e modelagem

## Objetivo
Modelar dados e funções com tipos compostos, unions discriminadas e generics, e validar valores externos em runtime antes de tratá-los como confiáveis.

## Teoria

### 1. Formas de dados e ausência
Uma interface ou alias de objeto descreve propriedades e seus tipos. Uma propriedade opcional pode não existir; um campo que aceita `null` existe, mas pode conter esse valor. Com `strictNullChecks`, trate explicitamente as possibilidades.

```ts
interface Produto {
  id: number;
  nome: string;
  preco: number;
  descricao?: string;
}

function rotulo(produto: Produto): string {
  return produto.descricao ?? produto.nome;
}
```

`?` não cria valor padrão nem garante presença em runtime. Modele apenas os campos que o contrato realmente permite.

**Erro comum:** usar `as Produto` para eliminar um aviso de campo opcional. A asserção não cria o campo nem comprova que o dado o contém.

### 2. Unions discriminadas e narrowing
Quando um valor pode representar alternativas com dados diferentes, modele cada alternativa como objeto e use um campo literal comum para distingui-las. A checagem desse discriminante estreita a union e permite acessar os campos daquela forma.

```ts
type Resultado<T> =
  | { estado: "sucesso"; dados: T }
  | { estado: "erro"; mensagem: string };

function descrever<T>(resultado: Resultado<T>): string {
  if (resultado.estado === "sucesso") {
    return "Dados recebidos";
  }
  return resultado.mensagem;
}
```

Antes da checagem, não é seguro acessar `mensagem` ou `dados`: cada campo pertence a uma alternativa. Esse padrão evita combinações contraditórias de propriedades opcionais.

**Erro comum:** representar carregamento, sucesso e erro por campos opcionais independentes, permitindo um estado de erro sem mensagem.

### 3. Generics preservam relações
Um generic permite criar uma operação reutilizável que mantém uma relação entre o tipo de entrada e o resultado. Em `primeiro<T>(itens: T[]): T | undefined`, uma coleção de `Produto` resulta em `Produto | undefined`; uma de strings resulta em `string | undefined`.

```ts
function primeiro<T>(itens: T[]): T | undefined {
  return itens[0];
}

const codigo = primeiro([10, 20]); // number | undefined
const nome = primeiro(["Lia", "Caio"]); // string | undefined
```

Use um parâmetro de tipo quando ele conecta posições do contrato. Uma restrição, como `T extends { id: number }`, expressa uma capacidade necessária sem perder o tipo concreto de `T`.

**Erro comum:** adicionar `<T>` sem preservar nenhuma relação entre entrada, saída ou propriedades. A abstração só ajuda se comunica algo útil.

### 4. unknown e validação em runtime
TypeScript remove os tipos ao gerar JavaScript. Portanto, o tipo estático `Produto` não verifica JSON recebido em runtime. Comece dados externos como `unknown`, confira sua forma e só então os aceite como dados do domínio. `unknown` exige verificações antes do uso; `any` permite quase qualquer operação sem essa proteção.

```ts
function ehProduto(valor: unknown): valor is Produto {
  if (typeof valor !== "object" || valor === null) return false;

  const candidato = valor as {
    id?: unknown;
    nome?: unknown;
    preco?: unknown;
  };

  return typeof candidato.id === "number"
    && typeof candidato.nome === "string"
    && typeof candidato.preco === "number";
}
```

A asserção que dá forma a `candidato` não valida o valor por si só: as verificações `typeof` são que conferem os campos. Em um sistema real, defina também regras de domínio, como preço não negativo.

**Erro comum:** confiar em `resposta.json() as Produto`. JSON sintaticamente válido ainda pode conter campos ausentes ou tipos errados.

### 5. Composição de contratos
Tipos compostos podem reutilizar contratos sem duplicar cada alternativa. `Resultado<T>` descreve sucesso e erro para operações diferentes, preservando o tipo concreto dos dados no ramo de sucesso. Não crie uma camada genérica antes que exista uma relação real para representar.

```ts
function buscarProduto(id: number): Resultado<Produto> {
  // implementação omitida
  return { estado: "erro", mensagem: "Não encontrado" };
}
```

O discriminante `estado` distingue os casos; `T` conecta os dados de sucesso ao produto procurado. O compilador ajuda a conferir essa estrutura no código, enquanto dados externos ainda precisam de validação.

## Resumo
- Modele formas de objeto e distinga campo opcional de campo que aceita `null`.
- Unions discriminadas tornam estados explícitos e permitem narrowing.
- Generics são úteis quando mantêm relação de tipo entre partes do contrato.
- `unknown` exige inspeção; `any` remove essa proteção.
- Tipos e asserções não validam valores em runtime; dados externos precisam de checagem real.
- Componha contratos reutilizáveis sem abstrair antes de haver necessidade.

## Verificação — quiz
1. O que `T` preserva em `primeiro<T>(itens: T[]): T | undefined`? **A)** Relação entre o tipo dos itens e o retorno. **B)** Uma variável JavaScript chamada T. **C)** Conexão com banco. **D)** Validação dos elementos. **Resposta: A.** O tipo concreto da coleção é reaproveitado no retorno, que também pode não ter item.

2. Quando é seguro acessar `mensagem` numa union sucesso/erro? **A)** Depois de verificar `estado === "erro"`. **B)** Em qualquer ramo sem checagem. **C)** Depois de serializar com `JSON.stringify`. **D)** Só se houver interface. **Resposta: A.** O discriminante identifica qual forma está presente naquele ramo.

3. `JSON.parse(texto) as Produto` garante que `nome` existe e é string? **A)** Sim. **B)** Não; a asserção só orienta a checagem estática, então é necessária validação runtime. **C)** Sim, se o JSON for válido. **D)** Só com generics. **Resposta: B.** JSON válido pode descrever qualquer forma de dados; a asserção não verifica campos.

4. Por que preferir `unknown` a `any` para dados não verificados? **A)** Exige narrowing antes de operações específicas. **B)** Converte para texto. **C)** Valida automaticamente. **D)** Impede a execução. **Resposta: A.** `unknown` obriga a conferir; `any` permite operações sem verificação.

5. Por que usar `T extends { id: number }` num generic? **A)** A função precisa usar `id` e quer manter o tipo concreto dos valores compatíveis. **B)** Para permitir qualquer propriedade sem checagem. **C)** Para validar JSON automaticamente. **D)** Para converter objeto em classe. **Resposta: A.** A restrição descreve a capacidade requerida e mantém informação específica de `T`.

## Práticas

### 1. Guiada — estreite o resultado
Complete a função para retornar o nome em caso de sucesso ou a mensagem no caso de erro:

```ts
function mensagemDoResultado(resultado: Resultado<Produto>): string {
  // completar
}
```

Explique por que acessar `resultado.dados.nome` antes de verificar `estado` não é seguro.

**Dica:** `estado` tem um literal que identifica cada forma.

**Solução esperada:**
```ts
function mensagemDoResultado(resultado: Resultado<Produto>): string {
  if (resultado.estado === "sucesso") {
    return resultado.dados.nome;
  }
  return resultado.mensagem;
}
```

**Aceite:** ambos os ramos retornam string e cada campo é acessado somente após narrowing.

### 2. Independente — componha uma coleção genérica
Implemente `Repositorio<T>` com `listar(): T[]`, `buscarPorId(id: number): T | undefined` e `adicionar(item: T): void`. Restrinja `T` para exigir `id: number`. Use a implementação com dois modelos, como Produto e Usuario, sem recorrer a `any`.

**Dica:** uma interface `ComId { id: number }` pode ser usada como restrição. Preserve `T` nos itens armazenados e retornados.

**Solução de referência:** a coleção interna é `T[]`; `listar` devolve essa lista, `buscarPorId` localiza pelo identificador e `adicionar` inclui um elemento `T`. Instâncias `Repositorio<Produto>` e `Repositorio<Usuario>` mantêm seus tipos; um objeto sem id numérico é rejeitado pelo verificador.

**Rubrica (0–2 cada):** restrição clara; tipo específico preservado; ausência representada com `undefined`; dois modelos aceitos sem `any`; exemplo incompatível rejeitado. **Domínio:** 8/10 ou mais, com nota máxima nos dois primeiros critérios.

### 3. Integrada — valide resposta de catálogo
Receba um valor `unknown` de fonte externa, valide se ele representa um produto e devolva `Resultado<Produto>`. Inclua três casos: produto válido, preço com tipo incorreto e `null`. Depois use `primeiro<T>` com uma coleção e explique o tipo retornado quando ela está vazia.

**Dica:** crie uma guarda `ehProduto(valor): valor is Produto` e use-a antes de montar o resultado discriminado.

**Solução de referência:** se `ehProduto(valor)` for verdadeiro, retorne `{ estado: "sucesso", dados: valor }`; caso contrário, `{ estado: "erro", mensagem: "Dados do produto inválidos" }`. Um produto com preço string e `null` devem ser rejeitados. `primeiro<Produto>([])` resulta em `undefined`; o tipo de retorno é `Produto | undefined`.

**Entregáveis:** tipos nomeados, guarda, função que produz o resultado, três exemplos e explicação da diferença entre verificação estática e validação runtime.

**Rubrica (0–2 cada):** validação rejeita forma incorreta e null; union coerente; `unknown` só usado após checagem; generic representa a lista vazia; casos e limites explicados. **Domínio:** 8/10 ou mais, com nota máxima em validação e union.

## Critério de conclusão
Modelar uma resposta com tipos compostos e generic, estreitar unions, criar uma guarda para validar dados externos e explicar por que tipagem estática não garante a forma recebida em runtime.
