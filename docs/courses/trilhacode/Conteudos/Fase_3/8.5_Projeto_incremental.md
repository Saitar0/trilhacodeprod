# 8.5 — Projeto incremental da fase

## Objetivo
Entregar uma primeira interface estática para a ideia do Trilho A escolhida na Fase 1, usando HTML, CSS, JavaScript, módulos TypeScript e dados locais em JSON, sem framework frontend e sem alegar persistência real.

## Escopo do projeto
Este projeto acrescenta uma camada de interface ao problema escolhido na Fase 1. A meta é demonstrar estrutura semântica, interação, organização do código, modelagem TypeScript e publicação de arquivos estáticos — não construir um produto completo.

Uma página estática é composta por arquivos servidos ao navegador. TypeScript precisa ser verificado e transformado em JavaScript pelo build; o navegador normalmente recebe HTML, CSS, JavaScript e arquivos de dados. Um JSON local serve como fonte demonstrativa, mas não oferece persistência compartilhada nem substitui uma API.

A entrega mínima tem uma página com uma listagem e um formulário. O formulário pode atualizar estado apenas em memória ou apresentar uma confirmação demonstrativa. Explique o que acontece com os dados quando a página é recarregada. Hospedagem estática publica os arquivos de saída; ela não executa backend, guarda segredos nem implementa autorização.

## Marcos de entrega

### Marco 1 — recorte, cenário e contrato de dados
Escolha a ideia do Trilho A já definida na Fase 1 e delimite uma fatia que caiba nesta etapa. Registre quem usaria a página, a tarefa principal, os campos que aparecem na listagem e o que o formulário demonstra. Crie um JSON inicial com pelo menos três registros representativos e descreva a forma dos dados. Liste o que fica fora do escopo, incluindo persistência/backend.

**Evidências:** breve descrição do problema e da fatia escolhida; amostra de dados; desenho simples ou lista da estrutura da página; critérios de aceite para fluxo principal e casos de entrada inválida/vazia.

**Checagem:** outra pessoa consegue identificar a tarefa principal e prever o que a interface fará com dados válidos, inválidos ou vazios?

**Aceite:** o escopo é uma única fatia demonstrável da ideia principal; dados têm campos consistentes e exemplos variados; limites da simulação estão explícitos; requisitos não descrevem recursos de backend.

### Marco 2 — estrutura semântica e interface adaptável
Implemente o esqueleto em HTML e CSS: título e regiões compreensíveis, listagem com dados de exemplo, formulário com rótulos associados e mensagens em local previsível. Use elementos adequados a cada função e preserve navegação por teclado. Ajuste a apresentação para larguras pequenas, médias e grandes sem esconder informação ou exigir rolagem horizontal da página.

**Evidências:** página executada localmente; captura ou registro das três larguras; lista de checagem de teclado, foco visível, rótulos, hierarquia de títulos e texto alternativo quando houver imagem informativa.

**Checagem:** percorra os controles apenas com teclado e confira em larguras aproximadas de 360 px, 768 px e 1280 px.

**Aceite:** listagem e formulário são distinguíveis; controles têm nomes/rótulos compreensíveis; todos os controles operáveis funcionam por teclado; foco é visível; conteúdo permanece legível e sem quebra relevante nas três larguras. Imagens decorativas não recebem descrição redundante; imagens informativas têm alternativa adequada.

### Marco 3 — dados e interação com TypeScript
Carregue o JSON local e apresente os itens na listagem. Organize o código em módulos TypeScript com responsabilidades identificáveis e modele os dados usados. O formulário deve validar os campos definidos no Marco 1 e responder com mensagem clara. Pode atualizar a lista em memória ou apenas confirmar o envio simulado, desde que a interface explique que os dados não são salvos após recarregar.

**Cenários de verificação manual:**
1. Abrir a página com o JSON válido e conferir os registros.
2. Usar o formulário com dados válidos e conferir a resposta visual.
3. Enviar com campo obrigatório vazio e verificar mensagem que identifica o campo.
4. Usar uma lista vazia e verificar que a interface explica que não há registros.
5. Simular um arquivo ausente ou inválido, se o fluxo carregado o permite, e confirmar uma mensagem compreensível sem travar a página.

**Evidências:** módulos e modelos de dados; saída da checagem/build; tabela com cenário, ação, resultado esperado e resultado observado.

**Aceite:** fluxo principal funciona; dados seguem o contrato modelado; validação cobre casos definidos; estados de sucesso, vazio e falha aplicáveis são claros; mudanças de estado e mensagens podem ser localizadas nos módulos correspondentes; nada sugere persistência inexistente.

### Marco 4 — build, publicação e documentação
Execute o processo de build e confira os arquivos finais, garantindo que a saída fica separada das fontes. Publique o resultado em GitHub Pages ou outro provedor de arquivos estáticos compatível com o projeto. Abra o endereço publicado, repita os cenários principais e confira que JSON, JavaScript, CSS e imagens são encontrados no endereço implantado. No README, registre objetivo, limites, pré-requisitos, passos de desenvolvimento, comando de build e configuração de publicação.

**Evidências:** comando de build e resultado; diretório publicado e sua página de entrada; URL pública; README com instruções; resultado dos cenários conferidos após a publicação.

**Aceite:** saída estática abre sem depender da máquina local; caminhos e arquivos carregam no endereço publicado; instruções permitem repetir o processo; persistência e limitações estão documentadas; não há tokens, segredos ou dados pessoais no repositório ou nas evidências.

## Checklist final de entrega
- [ ] A interface representa a ideia do Trilho A e a fatia escolhida está delimitada.
- [ ] Uma listagem carrega pelo menos três registros de JSON local.
- [ ] Formulário tem rótulos, validação e confirmação compreensível.
- [ ] HTML semântico, navegação por teclado, foco visível e alternativas de imagem foram revisados.
- [ ] Interface foi conferida em três larguras e não apresenta quebra relevante.
- [ ] Código está organizado em módulos TypeScript com responsabilidades identificáveis.
- [ ] A checagem/build gera ou valida a saída correta sem sobrescrever as fontes.
- [ ] Cenários válidos, inválidos, vazios e de falha aplicáveis foram registrados e conferidos.
- [ ] README informa objetivo, limites, instruções de desenvolvimento, build e publicação.
- [ ] Site publicado abre no endereço documentado sem depender da máquina local.
- [ ] Repositório e capturas não expõem segredo, token ou dado pessoal.

## Rubrica de avaliação
Pontue cada dimensão de 0 a 4:

- **Recorte e contrato:** problema coerente com o Trilho A, escopo limitado, dados exemplificados e limites declarados.
- **Interface e acessibilidade:** HTML adequado, controles identificados, teclado/foco e layouts legíveis nas larguras previstas.
- **Comportamento e TypeScript:** fluxo demonstrável, validação e estados corretos, módulos compreensíveis e build/checagem registrados.
- **Reprodução e publicação:** cenários repetíveis, instruções completas, URL pública funcional e saída independente da fonte.

**Referência da escala:** 4 = claro, completo e reproduzível; 3 = atende com pequena lacuna; 2 = parcialmente funcional ou documentado; 1 = evidência mínima; 0 = ausente. A pontuação orienta feedback; para concluir o projeto, os quatro marcos precisam atender aos próprios critérios de aceite e a publicação precisa estar acessível.

## Critério de conclusão
Publicar uma página acessível, responsiva e organizada, sem framework frontend, com dados JSON locais, build reproduzível, cenários conferidos e instruções suficientes para repetir a entrega. A documentação deve esclarecer que ainda não há persistência compartilhada.
