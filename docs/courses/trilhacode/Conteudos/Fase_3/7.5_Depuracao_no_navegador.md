# 7.5 — Depuração no navegador

## Objetivo
Usar Console, Elements, Sources e Network para reproduzir falhas, inspecionar estado e fluxo de JavaScript, localizar problemas de interação e analisar requisições com evidência.

## Teoria

### 1. Reproduzir e formular uma hipótese
Comece reproduzindo o problema com passos consistentes e anotando o resultado esperado e o observado. Formule uma hipótese verificável, como “o handler recebe uma string vazia” ou “a API respondeu com status 404”. Mude uma coisa por vez e repita o mesmo cenário para confirmar se a correção resolveu o sintoma.

**Evidência** é algo observável; **hipótese** é uma explicação possível para essa evidência. Uma mensagem ajuda a localizar a investigação, mas não prova sozinha a causa raiz.

**Erro comum:** fazer várias alterações antes de reproduzir de novo. Sem repetir o cenário, fica difícil saber qual mudança corrigiu o comportamento.

### 2. Console e Elements: mensagens, DOM e estado visível
O **Console** mostra logs, avisos e erros e permite avaliar expressões no contexto disponível. Leia o tipo da mensagem, o arquivo e a linha indicados. Um stack trace lista chamadas relacionadas ao erro; procure o primeiro frame do seu código e reconstrua como o fluxo chegou até ele.

**Elements** permite inspecionar o DOM atual e os estilos calculados. Compare o elemento real com o que o seletor espera: um seletor sem correspondência retorna `null`; tentar registrar um evento nesse valor produz um erro. Confirme IDs, classes, hierarquia e mudanças da interação.

**Erro comum:** editar o DOM pelo painel Elements e achar que corrigiu o código-fonte. A edição serve para investigar o estado atual; recarregar a página descarta mudanças temporárias.

### 3. Sources: breakpoint, escopo e pilha de chamadas
**Sources** é o painel de depuração de JavaScript. Um breakpoint pausa a execução na linha marcada. Durante a pausa, inspecione variáveis locais e valores em Scope ou Console, veja a linha atual e a pilha de chamadas (Call Stack). Use **Step over** para executar uma chamada sem entrar nela, **Step into** para acompanhar uma função relevante e **Step out** para terminar a função atual e voltar ao chamador.

Compare o valor que entra numa linha com o valor esperado. Para um handler de formulário, siga o evento desde a ação da pessoa até a leitura do campo e a atualização da página. Sourcemaps, quando disponíveis, relacionam código gerado ao fonte original; sem eles, arquivos compactados podem dificultar a leitura.

**Erro comum:** avançar linha a linha sem uma pergunta de depuração. Escolha antes qual valor ou transição sua hipótese prevê; no breakpoint, compare previsão e evidência.

### 4. Network: investigar requisições
**Network** registra requisições enquanto o painel está aberto. Reproduza a ação e filtre por Fetch/XHR; selecione a requisição para conferir URL, método, status, headers, payload, resposta e timing. A coluna Initiator e a pilha do iniciador ajudam a localizar o código que disparou a solicitação.

Um status HTTP como 404 ou 500 indica que uma resposta chegou com status malsucedido. Uma requisição marcada como falha/bloqueada pode não apresentar status HTTP legível; investigue Console e detalhes de rede, especialmente se suspeitar de CORS. Não conclua que todo erro sem status é CORS. Ao compartilhar evidências, oculte tokens, cookies, dados pessoais e conteúdo sensível.

**Erro comum:** interpretar “há uma linha vermelha na Network” como diagnóstico completo. Registre o detalhe observável, URL e comportamento esperado; só então formule a causa provável.

## Resumo
- Reproduza com passos estáveis e separe evidência observada de hipótese.
- Console mostra mensagens e stack traces; Elements confirma o DOM atual.
- Sources pausa em breakpoints e permite inspecionar valores, fluxo e chamadas.
- Network mostra URL, método, status, headers, corpo, timing e iniciador.
- Status HTTP de erro é uma resposta; falha de rede/bloqueio pode não oferecer status legível.
- Corrija uma causa por vez, repita o cenário e compartilhe evidências sem dados sensíveis.

## Verificação — quiz
1. Qual painel ajuda a conferir URL, método, status e headers de uma requisição? **A)** Network. **B)** Elements. **C)** Application. **D)** Sources somente. **Resposta: A.** Network registra solicitações e abre seus detalhes; os outros painéis apoiam outras investigações.

2. O que acontece quando o código atinge um breakpoint? **A)** A execução pausa para inspeção. **B)** O navegador corrige a causa. **C)** A requisição é reenviada. **D)** O código é publicado. **Resposta: A.** A pausa permite inspecionar estado e fluxo, mas não altera nem corrige o programa.

3. Um stack trace indica `app.js:18` após um clique. Qual é o próximo passo mais útil? **A)** Apagar a função. **B)** Reproduzir o clique, inspecionar a linha e os valores e acompanhar chamadas relevantes. **C)** Escolher uma linha aleatória. **D)** Desativar o Console. **Resposta: B.** O trace orienta onde investigar; reprodução e inspeção ajudam a testar a hipótese.

4. Network mostra status 404 para uma chamada. O que a evidência permite concluir? **A)** Houve uma resposta HTTP 404; verifique URL e contrato do endpoint. **B)** Não houve conexão. **C)** O CSS é inválido. **D)** O JavaScript foi corrigido. **Resposta: A.** 404 é resposta HTTP; não prova, por si só, por que o recurso não foi encontrado.

5. Qual afirmação sobre uma requisição marcada como falha sem status é mais precisa? **A)** É sempre CORS. **B)** Não há status HTTP legível; examine mensagem e detalhes para distinguir causas. **C)** A API respondeu 200. **D)** O JSON está necessariamente malformado. **Resposta: B.** Uma falha sem status pode ter causas diferentes; Console e Network fornecem mais evidências.

## Práticas

### 1. Guiada — localize um seletor sem correspondência
A página contém:

```html
<input id="nome" />
<button id="enviar">Enviar</button>
<p id="mensagem"></p>
```

O módulo contém:

```js
const entrada = document.querySelector("#nomes");
const botao = document.querySelector("#enviar");

botao.addEventListener("click", () => {
  document.querySelector("#mensagem").textContent = entrada.value;
});
```

Ao carregar, o Console mostra erro ao ler `addEventListener`. Use Elements e Console para verificar a hipótese. Corrija a causa e valide o clique com um breakpoint no handler.

**Dica:** compare o seletor com o `id` real; veja qual variável vale `null` antes de registrar o evento.

**Solução esperada:** `#nomes` não corresponde a nenhum elemento; o input tem `id="nome"`. Corrija o seletor, recarregue, confirme que o handler foi registrado e pause no clique para inspecionar `entrada.value`.

**Aceite:** evidência, causa, correção e resultado da nova reprodução estão registrados.

### 2. Independente — classifique evidências da Network
Investigue estes registros de uma aplicação didática. Para cada um, anote o que foi observado, o que ainda é hipótese e qual é o próximo passo.

- A: `GET /api/livros` retorna status 404.
- B: `GET /api/livros` aparece como `(failed)` sem status.
- C: `GET /api/livros` retorna 200, mas o corpo contém uma lista vazia.
- D: `GET /api/livros` retorna 500 com uma resposta de erro.

**Dica:** status HTTP e ausência de status não são equivalentes; uma lista vazia também pode ser válida conforme o contrato.

**Solução de referência:** A: resposta recebida; verifique caminho e disponibilidade da rota. B: sem status legível; consulte Console e detalhes para investigar rede ou bloqueio, sem afirmar CORS sem evidência. C: sucesso HTTP com resultado vazio; confirme se o contrato permite esse resultado e como a interface o representa. D: resposta HTTP malsucedida; registre status e corpo seguro e investigue o endpoint. Em cada caso, o próximo passo deve testar uma hipótese.

**Rubrica (0–2 cada):** observação fiel; hipótese separada do fato; próximo passo informativo; não confunde 404, falha sem status e lista vazia. **Domínio:** 6/8 ou mais, sem confundir resposta HTTP com ausência de status.

### 3. Integrada — corrija interação e requisição com evidência
Use a página e o módulo da prática guiada como base. Acrescente uma chamada a um endpoint de demonstração existente ou a uma rota fixture que possa responder 404 de forma previsível. Mantenha dois defeitos controlados: o seletor incorreto do input e o caminho incorreto da requisição. Corrija um de cada vez.

**Procedimento:** abra Console, Elements, Sources e Network; reproduza e registre a primeira evidência; pause no handler e inspecione o valor; corrija apenas o seletor e repita; então selecione a requisição na Network, confira método, URL, status e resposta, corrija o caminho e repita.

**Entregáveis:** tabela com sintoma, evidência, hipótese, causa confirmada, correção e resultado; captura opcional sem credenciais/dados pessoais; passos para reproduzir em outra máquina.

**Dicas:** abra Network antes de recarregar; use breakpoint perto da leitura do campo; compare o caminho solicitado com a rota real; faça uma mudança por vez. Se o endpoint não estiver disponível, registre a limitação e use uma fixture local com resposta previsível.

**Rubrica (0–2 cada):** reprodução consistente; evidência adequada em Console/Elements/Sources; diagnóstico HTTP apoiado pela Network; correções isoladas e revalidadas; relatório claro e sem dados sensíveis. **Domínio:** 8/10 ou mais, incluindo pontuação máxima em evidência de breakpoint e requisição.

## Critério de conclusão
Reproduzir e explicar uma falha de interação com evidência do DOM e breakpoint; diagnosticar uma chamada pela Network; distinguir observação de hipótese; corrigir uma causa por vez e confirmar o resultado repetindo o cenário.
