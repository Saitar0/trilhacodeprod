# 7.2 — Organização do código

## Objetivo
Organizar JavaScript em módulos com responsabilidades compreensíveis, tornar dependências explícitas e separar transformação de dados da interação com a página.

## Teoria

### 1. Módulo, escopo e interface
Um módulo ECMAScript (ESM) é um arquivo que pode expor parte de seu trabalho por `export` e consumir declarações de outros arquivos por `import`. As exportações formam a interface pública: quem usa o módulo conhece o que ele oferece, sem depender dos detalhes internos. Declarações de um módulo têm escopo próprio; importar uma função não a transforma em variável global.

```js
// tarefas.js
export function filtrarAtivas(tarefas) {
  return tarefas.filter((tarefa) => tarefa.ativa);
}

// app.js
import { filtrarAtivas } from "./tarefas.js";
```

**Erro comum:** esperar que uma função exportada fique automaticamente disponível em todos os arquivos. Cada consumidor precisa importá-la explicitamente.

### 2. Exportações e imports
Uma exportação nomeada associa um nome à declaração. O import nomeado usa chaves e precisa corresponder ao nome exportado:

```js
// formatos.js
export function formatarNome(nome) {
  return nome.trim();
}

// perfil.js
import { formatarNome } from "./formatos.js";
```

O caminho identifica o módulo de origem; `./` significa “a partir da pasta deste arquivo”. No navegador, sem um import map, use um caminho relativo ou URL resolvível, normalmente com a extensão, como `./formatos.js`. Também existe `export default`, importado sem chaves. Nesta unidade, priorize exportações nomeadas para deixar evidente o nome consumido nos dois arquivos.

**Erro comum:** renomear uma exportação sem atualizar seu import. Confira o nome e o caminho quando o carregamento falhar.

### 3. Carregamento e diagnóstico no navegador
O HTML carrega o ponto de entrada como módulo:

```html
<script type="module" src="./app.js"></script>
```

O navegador resolve as dependências importadas pelo ponto de entrada. Módulos são deferidos automaticamente até que o documento seja analisado e usam modo estrito. Durante o desenvolvimento, sirva a página por um servidor local compatível: abrir o HTML diretamente com `file://` pode impedir o carregamento por restrições do navegador.

Ao diagnosticar uma falha, confira: (1) se o script tem `type="module"`; (2) se o caminho é relativo ao arquivo que contém aquele import; (3) se o nome importado existe entre as exportações; (4) se o servidor encontrou e serviu os arquivos corretamente.

**Erro comum:** calcular o caminho do import a partir do HTML. O caminho é resolvido em relação ao módulo que declara o import.

### 4. Responsabilidades, coesão e dependências
Divida por responsabilidade coesa, não por uma regra automática de quantidade de linhas. Em uma lista de tarefas, por exemplo, `tarefas.js` pode transformar dados sem acessar o DOM; `interface-tarefas.js` pode registrar eventos e atualizar a página; `app.js` conecta e inicia as partes. O ponto de entrada coordena, mas não precisa conter toda a lógica.

Uma dependência aponta do consumidor para o módulo que fornece a função. Se dois módulos precisam importar um ao outro, há um ciclo; reavalie as responsabilidades e considere extrair a função compartilhada para um módulo menor. Evite também arquivos “utilitários” que acumulam funções sem relação.

**Erro comum:** criar um arquivo para cada função sem considerar o uso. Isso aumenta a navegação sem necessariamente tornar responsabilidades mais claras.

## Resumo
- `export` define a interface consumível; `import` declara a dependência.
- Imports nomeados usam chaves e precisam corresponder ao nome exportado.
- No navegador, carregue o ponto de entrada com `type="module"` e use caminhos resolvíveis.
- O caminho de import é relativo ao arquivo que declara esse import, não ao HTML.
- Separe por responsabilidades coesas; mantenha a transformação de dados independente do DOM quando isso clarificar o código.
- O ponto de entrada conecta módulos; ciclos e arquivos sem coesão indicam que a divisão merece revisão.

## Verificação — quiz
1. O que uma exportação nomeada permite? **A)** Disponibilizar uma declaração para importação por seu nome. **B)** Tornar todo o arquivo global. **C)** Executar o arquivo em qualquer ambiente. **D)** Copiar os dados automaticamente. **Resposta: A.** A exportação torna a declaração parte da interface; não globaliza o módulo nem garante execução em qualquer ambiente.

2. Qual marcação carrega um arquivo como módulo no navegador? **A)** `<script type="module" src="./app.js"></script>`. **B)** `<script class="module" src="./app.js"></script>`. **C)** `<module src="./app.js"></module>`. **D)** `<script async="module" src="./app.js"></script>`. **Resposta: A.** O valor `module` pertence ao atributo `type`.

3. `app.js` fica em `src/` e importa `"./calculos.js"`. Qual arquivo corresponde ao caminho? **A)** `src/calculos.js`. **B)** `calculos.js` ao lado do HTML, sempre. **C)** `src/app/calculos.js`. **D)** Um pacote chamado `calculos`. **Resposta: A.** A resolução parte da localização de `app.js`, não do documento HTML.

4. Uma função calcula o total de uma lista e outra parte atualiza a página. Qual divisão tende a ser mais coesa? **A)** Manter o cálculo sem DOM e conectá-lo à interface pelo ponto de entrada. **B)** Colocar tudo em `geral.js`. **C)** Criar um arquivo para cada variável. **D)** Fazer o cálculo consultar elementos HTML. **Resposta: A.** O cálculo pode ser compreendido e reutilizado sem acoplamento ao navegador.

5. `formatos.js` exporta `formatarNome`, mas `perfil.js` importa `formatarPessoa`. Qual diagnóstico é mais provável? **A)** O nome importado não corresponde à exportação nomeada. **B)** Imports nomeados não funcionam entre arquivos. **C)** É obrigatório renomear o HTML. **D)** O navegador converte os nomes automaticamente. **Resposta: A.** Corrija o nome no import ou exponha deliberadamente a declaração esperada.

## Práticas

### 1. Guiada — corrija a ligação entre módulos
Considere:

```js
// calculos.js
export function calcularMedia(valores) {
  const total = valores.reduce((soma, valor) => soma + valor, 0);
  return valores.length === 0 ? 0 : total / valores.length;
}
```

```js
// app.js
import { calcularMediaNotas } from "./calculos.js";

const media = calcularMediaNotas([7, 9, 8]);
console.log(media);
```

**Tarefa:** encontre as divergências, corrija o import e explique por que a função não precisa ser uma variável global.

**Dica:** compare o nome entre chaves ao nome declarado depois de `export function`; depois confira o caminho.

**Solução esperada:** importar `calcularMedia` de `./calculos.js` e chamar `calcularMedia([7, 9, 8])`. O resultado é `8`. A função fica disponível em `app.js` pelo import explícito, sem ser anexada ao escopo global.

**Aceite:** nome, caminho e chamada são compatíveis; a explicação distingue importação de variável global.

### 2. Independente — desenhe o mapa de módulos
Uma lista de leitura permite adicionar um livro, marcar como lido e contar os livros concluídos. Proponha de dois a quatro arquivos. Para cada um, descreva responsabilidade, funções que exporta e dependências que importa. Desenhe setas de quem importa para quem.

Revise seu desenho: o cálculo pode ser entendido sem HTML? A interface evita duplicar regras de dados? O ponto de entrada inicia a aplicação sem absorver detalhes? Há dependência circular?

**Dica:** comece pela operação mais independente, como contar livros lidos; depois identifique interface e ponto de entrada.

**Solução de referência:** `livros.js` exporta `adicionarLivro`, `marcarComoLido` e `contarLidos`; `interface-livros.js` importa as funções necessárias, registra eventos e atualiza a página; `app.js` importa e chama a inicialização. Direção: `app.js → interface-livros.js → livros.js`. Outras divisões são válidas se mantiverem responsabilidades claras e evitarem ciclos.

**Rubrica (0–2 cada):** responsabilidades distintas; interface pública identificada; setas consumidor → fornecedor; ausência de ciclo ou revisão justificada. **Domínio:** pelo menos 6/8 pontos, sem ciclo não explicado.

### 3. Transferência — modularize uma página de tarefas
Use uma página simples com campo de texto, botão “Adicionar” e lista (ou crie uma). Separe em um módulo de dados, outro de interação com o DOM e um ponto de entrada. Preserve a adição e a atualização visual da lista. Use exportações nomeadas para funções compartilhadas.

**Entregáveis:** arquivos, mapa de imports, instrução de execução por servidor local e uma nota justificando uma decisão de separação e uma mudança que agora ficaria localizada em um módulo.

**Dicas:** faça a transformação de dados funcionar sem DOM; na interface, selecione elementos e registre eventos; deixe `app.js` iniciar a aplicação; confira cada caminho a partir do arquivo que o declara.

**Estrutura sugerida:**
```text
projeto/
  index.html
  app.js
  tarefas.js
  interface-tarefas.js
```

**Rubrica (0–2 cada):** comportamento preservado; responsabilidades coesas; imports/exports compatíveis; execução documentada e decisão explicada. **Domínio:** pelo menos 6/8 pontos, incluindo nota máxima em compatibilidade. Se falhar, aplique a lista de diagnóstico do microtópico 3 e registre a causa corrigida.

## Critério de conclusão
Explicar o que cada módulo expõe e por quê, rastrear uma dependência até sua origem, corrigir um import incompatível e apresentar uma pequena aplicação modular com comportamento preservado.
