# 8.3 — Configuração e uso de TypeScript

## Objetivo
Configurar o compilador com tsconfig.json, verificar e emitir JavaScript conforme o ambiente, e migrar um módulo JavaScript em etapas sem alterar seu comportamento.

## Teoria

### 1. Escopo do projeto e seleção de arquivos
A presença de tsconfig.json identifica a raiz de um projeto TypeScript e registra os arquivos de entrada e as opções do compilador. include, exclude e files ajudam a definir o escopo. rootDir e outDir organizam caminhos de entrada e saída; rootDir não seleciona quais arquivos serão compilados.

Ao executar tsc sem nomes de arquivo, o compilador usa a configuração encontrada para o projeto. Se você chamar tsc src/index.ts, os arquivos informados são compilados com opções padrão e os tsconfig.json são ignorados. Para usar uma configuração específica, execute tsc -p caminho/para/tsconfig.json ou rode tsc na raiz configurada.

**Erro comum:** achar que include está funcionando quando a linha de comando passou nomes de arquivos diretamente. Confira como o compilador foi iniciado e quais arquivos incluiu.

### 2. Opções de acordo com runtime e build
As opções devem refletir onde o JavaScript vai rodar e quem resolve os módulos. target escolhe o nível de JavaScript emitido; module descreve o formato de módulos esperado no resultado; moduleResolution define como o TypeScript encontra imports; rootDir e outDir organizam fontes e saídas. Não copie opções de Node para navegador ou bundler sem verificar se representam o mesmo ambiente.

Uma saída separada evita misturar arquivos gerados às fontes:

```text
projeto/
  src/
    index.ts
  dist/       # saída gerada
  tsconfig.json
```

strict ativa verificações mais rigorosas, incluindo noImplicitAny e strictNullChecks. Entenda quais diagnósticos essas opções habilitam antes de desligá-las ao primeiro erro.

**Erro comum:** escolher module e moduleResolution isoladamente. As opções precisam combinar com runtime e ferramentas que executam ou empacotam o código.

### 3. Checagem, emissão e diagnósticos
O compilador pode verificar tipos e emitir JavaScript. noEmit desativa a emissão quando outra ferramenta, como um bundler, gera os arquivos finais. noEmitOnError controla se a emissão para quando a checagem encontra erros. Confira o script de build do projeto para saber qual fluxo está em uso.

Leia nos diagnósticos a mensagem, o arquivo, a linha e o tipo esperado/recebido. Resolva a causa no contrato ou no fluxo; não acrescente any ou asserções só para silenciar o erro. Uma checagem limpa significa que as regras configuradas passaram nos arquivos incluídos. Não prova que todos os arquivos relevantes entraram na checagem, que a aplicação funciona em runtime ou que dados externos são válidos.

**Erro comum:** declarar “sem erros” sem confirmar o comando, os arquivos incluídos e se a build real foi executada.

### 4. Migração gradual de JavaScript
allowJs permite que arquivos JavaScript sejam entradas do projeto; checkJs ativa diagnósticos neles. Isso possibilita uma evolução por etapas: delimite a pasta de entrada, separe saída, escolha um módulo de baixo risco, registre o comportamento atual, adicione tipos, ajuste consumidores e repita checagem e execução.

Mantenha a aplicação executável e limite o escopo de cada etapa. Registre exceções temporárias com contexto e plano de remoção. Não transforme cada aviso em any; resolva um contrato de cada vez.

**Erro comum:** renomear todos os arquivos de uma vez e interpretar uma avalanche de erros como um único problema. A migração incremental ajuda a localizar cada origem.

## Resumo
- tsconfig.json define o escopo e as opções; rootDir não seleciona arquivos de entrada.
- tsc sem lista de arquivos usa a configuração; passar arquivos diretamente pode ignorá-la.
- target, module e moduleResolution devem corresponder ao runtime e ao build.
- noEmit transfere a emissão para outra ferramenta; mantenha saída fora das fontes.
- Checagem limpa cobre somente arquivos e regras configuradas, não prova funcionamento em runtime.
- allowJs e checkJs ajudam na migração gradual; converta um módulo por vez e valide o comportamento.

## Verificação — quiz
1. Para que serve tsconfig.json? **A)** Definir o projeto, o escopo e opções do compilador. **B)** Guardar dados da API. **C)** Substituir package.json. **D)** Criar o DOM. **Resposta: A.** O arquivo indica a configuração da raiz TypeScript; não exerce as funções das outras opções.

2. O que ocorre ao executar tsc src/index.ts? **A)** O TypeScript sempre combina esse argumento com include. **B)** Os arquivos são compilados usando opções padrão e tsconfig.json é ignorado. **C)** O arquivo é executado no navegador. **D)** package.json é reescrito. **Resposta: B.** Para usar uma configuração de projeto, execute tsc -p ... ou tsc sem informar arquivos.

3. Qual afirmação sobre rootDir é correta? **A)** Organiza o caminho dos arquivos de entrada na saída; não substitui include. **B)** Garante que todos os arquivos serão compilados. **C)** Ativa validação de JSON. **D)** Escolhe o navegador. **Resposta: A.** Seleção de arquivos e organização da emissão são coisas distintas.

4. Quando noEmit pode fazer sentido? **A)** Quando outra ferramenta é responsável por gerar a saída JavaScript. **B)** Para converter automaticamente JS em TS. **C)** Para impedir toda checagem. **D)** Para corrigir erros de runtime. **Resposta: A.** noEmit desativa a emissão do compilador, mas a checagem estática ainda pode ocorrer.

5. Qual estratégia reduz o risco na migração de JS para TS? **A)** Renomear tudo sem verificar a aplicação. **B)** Migrar um módulo delimitado e validar cada etapa. **C)** Silenciar diagnósticos com any. **D)** Apagar tsconfig. **Resposta: B.** Etapas menores ajudam a manter o projeto utilizável e localizar regressões.

## Práticas

### 1. Guiada — descubra por que a configuração não se aplica
Um projeto possui tsconfig.json com strict: true, include: ["src/**/*.ts"] e outDir: "dist". Alguém executa tsc src/index.ts e observa que as opções parecem ignoradas.

Explique o comportamento e indique um comando que use a configuração. Diga também o que include e outDir controlam.

**Dica:** compare tsc sem nomes de arquivo com uma chamada que lista arquivos explicitamente.

**Solução esperada:** passar src/index.ts diretamente faz o compilador ignorar tsconfig.json e usar opções padrão para os arquivos indicados. Execute tsc -p . na raiz (ou tsc sem lista de arquivos nessa raiz). include seleciona arquivos; outDir define onde colocar a saída emitida.

**Aceite:** diferencia os comandos e explica seleção versus destino de saída.

### 2. Independente — proponha uma configuração de migração
Considere um projeto com JavaScript em src/, um processo de build existente e arquivos gerados que não devem ficar junto às fontes. Escreva um plano de três etapas: delimite os arquivos abrangidos, decida onde ficam as saídas quando o compilador as emitir, use allowJs/checkJs adequadamente e explique como verificará que cada etapa preservou o comportamento.

Registre o runtime real — Node, navegador com bundler ou outro — e explique como ele orienta target, module e moduleResolution. Não há uma combinação universal para todos os ambientes.

**Dica:** desenhe primeiro as pastas fonte/saída; escolha depois um módulo de baixo risco e defina como observar o comportamento antes e depois.

**Solução de referência:** delimitar src no escopo; separar fonte e saída; usar allowJs para aceitar JS e checkJs conforme a equipe passe a corrigir diagnósticos; migrar um módulo por etapa, mantendo build e comparação do comportamento. Opções de módulo devem corresponder ao runtime/ferramenta. Soluções equivalentes são válidas se justificadas.

**Rubrica (0–2 cada):** escopo definido; saída separada; allowJs/checkJs usados com propósito; opções ligadas ao ambiente; comparação de comportamento por etapa. **Domínio:** pelo menos 8/10, sem confundir escopo com pasta de saída.

### 3. Integrada — migre um módulo e documente o fluxo
Escolha um módulo JavaScript pequeno com um consumidor. Registre uma entrada representativa e a saída esperada. Converta o módulo para TypeScript, tipando contratos públicos; ajuste consumidores; configure checagem/emissão para o ambiente e execute o processo real do projeto. Se outra ferramenta gerar o JavaScript, explique como TypeScript participa da checagem sem duplicar a emissão.

**Entregáveis:** lista de arquivos alterados; opções explicadas; comando de verificação/build; exemplo de comportamento antes/depois; diagnósticos resolvidos e exceções temporárias justificadas.

**Dicas:** escolha um módulo de baixo risco; confirme se entrou no projeto; não passe o caminho do arquivo ao tsc se espera usar tsconfig; mantenha saída fora das fontes; compare o mesmo cenário antes e depois.

**Rubrica (0–2 cada):** módulo e consumidor coerentes; escopo e comando confirmados; opções de runtime justificadas; saída organizada; comportamento comparado e exceções documentadas. **Domínio:** 8/10 ou mais, incluindo nota máxima em escopo/build e comparação de comportamento.

## Critério de conclusão
Explicar opções essenciais e escopo de tsconfig, distinguir checagem de emissão, identificar quando a configuração é ignorada e migrar um módulo mantendo comportamento verificado.
