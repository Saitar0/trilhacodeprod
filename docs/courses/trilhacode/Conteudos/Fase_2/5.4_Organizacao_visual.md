# 5.4 — Organização visual

## Objetivo
Organizar estilos com separação de responsabilidades e uma convenção explícita, tornando alterações localizadas, compreensíveis e de baixo risco; reconhecer Tailwind CSS como abordagem utility-first de repertório.

## Teoria

### Organizar CSS para manutenção
CSS sem organização tende a acumular regras duplicadas, seletores globais difíceis de prever e exceções de alta especificidade. Separe estilos por responsabilidade e mantenha estilos relacionados próximos para facilitar localização e revisão.

Agrupe regras globais (tipografia base, cores, reset pequeno) separadamente de componentes e páginas quando isso ajudar a localizar mudanças. Use custom properties para valores repetidos, como cores ou espaçamentos, quando houver benefício real. Remova duplicação com cuidado e verifique quais elementos dependem da regra antes de alterá-la.

### Convenções de nomes e escopo
Use nomes que indiquem a função do componente, como `.card` ou `.nav-link`, e prefira seletores que não dependam de uma cadeia longa de ancestrais. Uma convenção como BEM (`.card__title`, `.card--featured`) pode ajudar a explicitar partes e variações, mas não é obrigatória. O acordo existente do projeto deve prevalecer; documentação e consistência importam mais que escolher uma sigla.

### Responsabilidade e risco da alteração
Uma regra muito ampla, como `div { ... }`, afeta muitos lugares. Uma classe de componente tende a limitar o efeito. Antes de refatorar, identifique os elementos afetados; faça uma mudança por vez e compare a interface nos contextos relevantes. Comentários devem explicar decisões ou restrições, não repetir literalmente o que a propriedade já diz.

### Repertório: utility-first e Tailwind
Tailwind CSS é um framework utility-first: classes pequenas aplicam propriedades diretamente no markup, e variantes podem condicionar estilos a breakpoints ou estados. Isso muda onde os estilos ficam e como a equipe organiza a interface; não elimina a necessidade de entender CSS, cascata, layout e responsividade. Para este tópico, basta reconhecer a abordagem e comparar legibilidade, repetição e manutenção em um exemplo curto.

## Resumo
- CSS deve ser organizado para localizar e compreender regras.
- Separe estilos globais e componentes conforme a escala do projeto.
- Convenções de nomes ajudam quando usadas com consistência; não existe uma convenção universal obrigatória.
- Regras amplas e especificidade excessiva aumentam o risco de efeitos colaterais.
- Faça refatorações pequenas e inspecione todos os contextos afetados.
- Tailwind é uma abordagem utility-first; entender CSS continua essencial.

## Verificação — quiz
1. Qual regra tende a ter maior risco de efeitos em cascata? **A)** Classe específica de componente. **B)** Regra global para `div`. **C)** Custom property local. **D)** Comentário. **Resposta: B.** Ela alcança todas as `div` que correspondem no documento; uma classe de componente restringe melhor o alcance. Comentários não aplicam estilos.
2. Uma equipe usa BEM. Isso significa que: **A)** toda equipe precisa usar BEM. **B)** escolheu uma convenção de nomes que deve aplicar consistentemente. **C)** não precisa entender cascata. **D)** está usando Tailwind obrigatoriamente. **Resposta: B.** BEM é uma convenção possível, não uma exigência universal nem uma substituição dos fundamentos de CSS.
3. O que significa utility-first? **A)** Escrever toda regra em um arquivo único. **B)** Compor estilos por classes utilitárias aplicadas no markup. **C)** Não usar classes. **D)** Gerar HTML sem CSS. **Resposta: B.** Cada utilitário aplica uma finalidade de estilo e pode ser combinado no elemento; isso não elimina CSS, e as outras opções descrevem conceitos diferentes.
4. Como reduzir risco ao reorganizar CSS? **A)** Alterar várias regras globais ao mesmo tempo. **B)** Fazer mudanças localizadas, entender os elementos afetados e revisar cada contexto. **C)** Apagar todas as classes. **D)** Usar `!important` em tudo. **Resposta: B.** Mudanças pequenas tornam mais fácil perceber regressões e preservar intenção; `!important` não substitui compreensão do alcance das regras.
5. Dois componentes usam o mesmo espaçamento e a equipe quer ajustá-lo de forma coerente. Qual opção tende a facilitar a manutenção? **A)** Copiar valores diferentes em cada seletor. **B)** Criar uma custom property compartilhada se o valor realmente representa uma decisão comum. **C)** Adicionar um seletor global `div`. **D)** Colocar o valor em um comentário. **Resposta: B.** Uma variável compartilhada pode tornar a decisão explícita e facilitar mudanças coordenadas. Se os valores só coincidem por acaso ou devem variar independentemente, mantê-los separados pode ser melhor.

## Práticas

### 1. Guiada — localize o alcance de cada regra
Leia este HTML e CSS. Antes de reorganizar, anote qual regra afeta cada elemento e quais alterações poderiam afetar mais de um componente.

```html
<article class="card"><h2>Curso</h2><p class="muted">Em andamento</p></article>
<section class="profile"><h2>Perfil</h2><p class="muted">Pessoa estudante</p></section>
```

```css
div { padding: 1rem; }
.card p { color: #555; }
.profile p { color: #555; }
.card { padding: 1rem; }
.muted { color: #777; }
```

**Tarefa:** identifique a regra que não alcança esses elementos, a duplicação aparente e a regra compartilhada que já expressa uma intenção comum. Proponha uma versão mais simples e diga como confirmaria que o resultado não mudou.

**Dicas graduais:** (1) confira as tags do HTML contra o seletor `div`; (2) compare as declarações de cor e o seletor `.muted`; (3) altere uma regra por vez e verifique ambos os componentes.

**Solução comentada:** `div` não corresponde ao `article` nem ao `section`, então sua declaração de padding não tem efeito nesses elementos. `.card p` e `.profile p` têm mais especificidade que `.muted` e, por isso, a cor calculada nos dois parágrafos é `#555`. Para preservar esse resultado e reduzir duplicação, remova as duas regras específicas e altere `.muted` para `color: #555`; mantenha `.card { padding: 1rem; }`. Compare cor e espaçamento nos dois componentes antes e depois. A solução é deliberadamente localizada; não é necessário criar uma arquitetura de arquivos para este exemplo.

**Erros comuns:** supor que todo seletor escrito afeta algo; remover uma regra sem conferir a aparência calculada; confundir repetição de valor com prova de que dois componentes terão sempre a mesma intenção.

### 2. Independente — defina uma convenção pequena
Escolha dois componentes da página que você já criou (por exemplo, navegação e cartão). Escreva uma convenção curta para nomes, organização de regras e valores repetidos. Aplique-a a pelo menos quatro seletores e registre onde cada estilo deve ser encontrado.

Entregue `Decisão | Exemplo aplicado | Motivo` para: padrão de nomes; escopo dos seletores; divisão entre estilos globais e componentes; uso ou não de custom properties para um valor repetido. Não precisa adotar BEM: pode usar o padrão existente ou justificar outro.

**Dicas graduais:** (1) use nomes que expressem papel, não aparência passageira; (2) evite encadear elementos e ancestrais sem necessidade; (3) centralize somente decisões que devem mudar juntas.

**Critérios de aceite:** convenção compreensível por outra pessoa; quatro seletores coerentes; nenhum seletor amplo incluído sem justificativa; valor repetido tratado conforme sua intenção. Existem várias soluções válidas; a justificativa e a consistência são a referência de avaliação.

### 3. Transferência — reorganize uma folha real
Receba ou crie um CSS com regras duplicadas, seletores amplos e nomes inconsistentes. Defina uma convenção simples, separe regras globais das específicas, reduza duplicação e documente decisões que não forem óbvias. Compare a página antes e depois e faça uma alteração pequena de baixo risco.

**Repertório opcional:** escolha um componente e reproduza uma parte com classes utilitárias do Tailwind em um ambiente já configurado ou em um exemplo estático. Compare onde ficam as decisões de estilo e como uma mudança é localizada; não instale ferramenta durante a atividade principal.

**Entregue:** trecho antes/depois, convenção adotada, componentes revisados e registro de uma mudança pequena feita após a reorganização. Se fizer o repertório opcional, inclua também um exemplo equivalente em utility-first e compare concisão, localização e leitura.

**Aceite:** convenção descrita; seletores com escopo adequado; duplicações removidas sem alterar intenção; funcionamento comparado antes/depois; comparação utility-first identifica ao menos um benefício e uma troca, se a opção for realizada.

**Rubrica (0–2 por critério):** (1) convenção aplicada com consistência; (2) escopo e efeitos das regras compreendidos; (3) duplicações removidas sem perda de comportamento; (4) comparação antes/depois e justificativa da mudança. `0` = ausente/incorreto, `1` = parcial, `2` = claro e demonstrado. Pronto com pelo menos 6/8 e sem regressão visual conhecida sem plano de correção.

## Critério de conclusão
Explicar a convenção adotada, localizar estilos de um componente e realizar uma alteração de baixo risco sem quebrar outros elementos da página.
