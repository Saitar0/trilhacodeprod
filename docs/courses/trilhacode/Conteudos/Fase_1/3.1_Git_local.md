# 3.1 — Git local

## Objetivo
Criar um repositório Git, registrar alterações em commits, trabalhar com branches e inspecionar ou desfazer mudanças com segurança.

## Teoria

### Repositório, working tree e staging area
Git é um sistema distribuído de controle de versão. Um **repositório** contém o histórico de commits e metadados que permitem comparar e recuperar estados registrados. A **working tree** é o conjunto de arquivos que você está vendo e editando. A **staging area** (índice) reúne as mudanças escolhidas para o próximo commit.

O ciclo comum é: editar arquivos, verificar `git status`, examinar `git diff`, selecionar mudanças com `git add` e registrar com `git commit`. O commit guarda um snapshot do conteúdo selecionado no staging. Alterações que não foram adicionadas não entram automaticamente no commit.

```bash
git init
git status
git add README.md
git diff --staged
git commit -m "docs: add study repository overview"
```

### Inspecionar o histórico
`git log` mostra commits; opções como `--oneline --graph --decorate` ajudam a visualizar o histórico. `git show` apresenta um commit e suas alterações. `git diff` compara estados: sem opções, costuma mostrar mudanças ainda fora do staging; `git diff --staged` mostra o que está preparado para o commit.

### Branches
Uma branch é uma referência móvel para uma linha de desenvolvimento; criar uma branch não duplica todo o projeto. Ela permite experimentar mudanças separadas. Confira a branch atual com `git branch --show-current`, crie uma com `git switch -c nome` e alterne com `git switch nome`. Termine um trabalho integrando-o por merge ou pelo fluxo definido no projeto.

### Desfazer com intenção
`git restore arquivo` pode descartar alterações locais daquele arquivo; isso pode apagar trabalho não salvo em commit. `git restore --staged arquivo` tira o arquivo do staging sem necessariamente apagar as alterações da working tree. `git reset` altera o estado do índice e, em certas formas, também referências; `git reset --hard` pode descartar mudanças e não deve ser usado como tentativa genérica de corrigir problemas. Antes de desfazer, execute `git status` e `git diff`; se estiver em dúvida, faça uma cópia ou salve o trabalho em uma branch/commit.

### `.gitignore`
Um arquivo `.gitignore` indica padrões de arquivos ainda não rastreados que o Git deve ignorar, como artefatos gerados e arquivos locais. Ele não remove do histórico um arquivo que já está sendo rastreado. Não use `.gitignore` como substituto para remover segredos já commitados; credenciais expostas devem ser revogadas/rotacionadas e o histórico tratado com cuidado.

## Resumo
- `git init` inicia um repositório; `git status` apresenta o estado atual.
- Working tree é onde se edita; staging area seleciona mudanças; commit registra um snapshot.
- Revise `git diff` e `git diff --staged` antes de registrar.
- `git log` e `git show` ajudam a entender o histórico.
- Branches isolam linhas de trabalho sem duplicar o repositório inteiro.
- `git restore` e `git reset` têm efeitos diferentes; `--hard` pode descartar trabalho.
- `.gitignore` evita rastrear certos arquivos novos, mas não apaga arquivos já rastreados.
- Nunca inclua credenciais no histórico; se expostas, revogue-as primeiro.

## Verificação — quiz
1. Qual sequência registra apenas `README.md` no próximo commit? **A)** `git commit README.md` sem preparação. **B)** `git add README.md`, revisar staging, `git commit`. **C)** `git reset README.md`. **D)** `git ignore README.md`. **Resposta: B.**
2. Você adicionou um arquivo ao staging por engano, mas quer manter as edições. Qual ação é apropriada? **A)** `git restore --staged arquivo`. **B)** `git restore arquivo`. **C)** `git reset --hard`. **D)** Apagar o repositório. **Resposta: A.** Remove do staging sem descartar a edição local.
3. O que `git diff --staged` ajuda a revisar? **A)** Mudanças selecionadas para o próximo commit. **B)** Arquivos remotos. **C)** Permissões do sistema. **D)** Apenas arquivos ignorados. **Resposta: A.**
4. Um token já foi commitado e depois o arquivo foi adicionado ao `.gitignore`. O que é correto? **A)** O segredo deixou de existir no histórico. **B)** Deve-se revogar/rotacionar o token e tratar a exposição; `.gitignore` não remove commits anteriores. **C)** Basta apagar a working tree. **D)** O repositório se corrige sozinho. **Resposta: B.**
5. `git status --short` mostra ` M README.md` e `M  plano.md`. O que isso indica? **A)** Ambos estão somente no staging. **B)** `README.md` tem mudança não preparada; `plano.md` tem mudança preparada no staging. **C)** Ambos foram commitados. **D)** O primeiro está ignorado e o segundo foi apagado. **Resposta: B.** No formato curto, a primeira coluna representa o índice/staging e a segunda, a working tree.

## Prática — três níveis

Faça as atividades em uma pasta temporária e use somente conteúdo fictício. Antes de qualquer operação de recuperação, confira `git status` e os diffs. Não use arquivos de ambiente ou credenciais reais.

### 1. Guiada — interprete o estado do repositório

Considere esta saída de `git status --short`:

```text
 M README.md
M  plano.md
?? rascunho.md
```

No formato curto, a primeira coluna indica o estado no índice (staging) e a segunda indica o estado da working tree.

**Tarefa:** responda o que está preparado para o próximo commit, o que ainda não foi preparado e o que ainda não é rastreado. Depois, imagine que você quer incluir apenas a mudança de `README.md` no próximo commit, mantendo as outras edições. Escreva a sequência de inspeção e preparação.

**Gabarito comentado:** `README.md` tem alteração somente na working tree; `plano.md` tem alteração no índice; `rascunho.md` é não rastreado. Como o commit registra tudo que já está no índice, primeiro inspecione `git diff --staged -- plano.md` e retire essa mudança do staging com `git restore --staged -- plano.md`. Isso mantém a edição na working tree. Em seguida, revise `git diff -- README.md`, prepare somente `README.md` com `git add README.md` e confirme com `git diff --staged`. A saída pode mostrar ` M plano.md`, `M  README.md` e `?? rascunho.md`. Só então faça o commit; arquivos fora do staging ficam de fora.

### 2. Independente — escolha como recuperar cada estado

Para cada situação, complete uma tabela com: estado atual, resultado desejado, inspeção anterior, operação apropriada e risco a comunicar.

1. Um arquivo foi preparado por engano; você quer mantê-lo editado, mas não incluí-lo no próximo commit.
2. Um arquivo rastreado tem uma edição local descartável; você quer voltar ao conteúdo registrado em `HEAD`.
3. Um segredo real foi incluído em um commit e enviado ao remoto; depois alguém adicionou o caminho ao `.gitignore`.
4. Você considera executar `git reset --hard` para “limpar” um repositório cujo estado ainda não inspecionou.

**Dicas progressivas**

- Diferencie remover do staging de descartar o conteúdo na working tree. São objetivos distintos.
- `.gitignore` afeta arquivos não rastreados; uma credencial já exposta exige revogação/rotação e tratamento cuidadoso do histórico e dos sistemas que receberam o commit.

**Gabarito comentado:** (1) conferir `git status` e `git diff --staged -- arquivo`; usar `git restore --staged -- arquivo` para tirar do índice preservando a edição local. (2) conferir `git diff -- arquivo` e, somente se a edição puder ser perdida, usar `git restore -- arquivo`; essa operação substitui o conteúdo da working tree pelo conteúdo do índice. (3) revogar/rotacionar a credencial imediatamente e seguir o processo de resposta a segredo exposto; `.gitignore` não remove o commit nem desfaz o acesso já ocorrido. A reescrita do histórico precisa considerar clones e colaboradores. (4) não executar ainda: `git reset --hard` pode descartar mudanças no índice e na working tree; primeiro identificar e preservar qualquer trabalho que precise ser mantido.

**Critérios de autocorreção (0–2 pontos cada; total 8)**

- Diferencia retirar do staging de descartar uma edição local.
- Reconhece que `git restore -- arquivo` pode substituir a edição local e requer inspeção antes.
- Trata credencial commitada como exposta, incluindo revogação/rotação; não confia no `.gitignore` para apagar histórico.
- Identifica o risco de `git reset --hard` e pede inspeção/preservação antes de qualquer uso.

Considere a atividade concluída com pelo menos 6 pontos e sem recomendar uma operação destrutiva sem inspeção e intenção explícita.

### 3. Transferência — construa e inspecione um histórico local

Em uma pasta temporária, inicialize um repositório Git e crie `README.md`, `plano.md` e `.gitignore`. Faça um primeiro commit com esses arquivos. Acrescente ao `.gitignore` o caminho `/local.env` e crie `local.env` contendo apenas um valor fictício, como `TOKEN=exemplo-sem-valor-real`; use `git check-ignore -v local.env` para confirmar que o padrão corresponde. Não adicione esse arquivo ao staging.

Anote o nome da branch inicial com `git branch --show-current`. Altere `README.md` e `plano.md` de maneiras diferentes. Use `git status` e `git diff` para preparar apenas `README.md`, inspecione o staging e faça um commit descritivo. Em seguida, registre a alteração de `plano.md` em outro commit. Crie uma branch com `git switch -c pratica/branch`, faça nela uma alteração pequena e commitada, volte ao nome de branch que anotou e inspecione o histórico com `git log --all --oneline --graph --decorate`.

Por fim, edite um arquivo rastreado, prepare a mudança, inspecione o diff e retire-a do staging com `git restore --staged -- arquivo`. Confirme com `git status` que a edição continua na working tree. Não use `git restore -- arquivo` nem `git reset --hard` nessa etapa.

**Aceite:** o repositório mostra commits descritivos; o primeiro commit seletivo contém somente a mudança pretendida; a branch e seu commit aparecem no histórico; `local.env` é ignorado e não foi commitado; a mudança retirada do staging continua editada; a pessoa explica working tree, staging e commit sem usar credenciais reais.

## Critério de conclusão
Explicar working tree, staging area e repositório, criar commits e branches e escolher uma operação segura para desfazer uma mudança, descrevendo antes o estado que será afetado.
