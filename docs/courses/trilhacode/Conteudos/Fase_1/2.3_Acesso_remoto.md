# 2.3 — Acesso remoto

## Objetivo
Explicar o propósito do SSH, conectar-se a um servidor remoto com segurança e configurar uma chave para autenticar no GitHub, sem compartilhar a chave privada.

## Teoria

### O que é SSH
SSH (Secure Shell) é um protocolo para comunicação segura com outro computador ou serviço por uma rede. Pode oferecer um terminal remoto, transferência de arquivos ou outros canais protegidos. O cliente SSH inicia a conexão; o servidor SSH recebe e autentica a tentativa. O nome “servidor” aqui pode se referir ao serviço executado na máquina remota.

Uma conexão costuma identificar o destino por usuário e host, como `ana@servidor.exemplo`. Em redes configuradas para isso, pode ser necessário informar uma porta diferente da padrão. A conexão pode falhar porque o host está inacessível, o serviço não está ativo, a rede bloqueia o acesso ou a autenticação não corresponde.

### Chaves pública e privada
Uma chave SSH é um par criptográfico: **chave privada** e **chave pública**. A privada fica sob controle da pessoa e não deve ser enviada a terceiros, publicada ou adicionada ao Git. A pública pode ser cadastrada no serviço remoto. Durante a autenticação, o cliente demonstra que controla a chave privada associada à chave pública cadastrada.

Uma frase secreta (passphrase) pode proteger a chave privada armazenada. Um agente SSH pode manter a chave desbloqueada durante uma sessão, evitando digitar a frase repetidamente. Proteja o dispositivo e remova chaves que não devem mais ter acesso. A chave SSH não é a mesma coisa que um token de API: são credenciais e fluxos de autenticação diferentes.

### Usar SSH com GitHub
Para usar SSH com GitHub, gere ou escolha uma chave compatível, adicione somente a chave pública à conta e teste a autenticação. O endereço remoto do repositório deve usar o formato SSH, por exemplo `git@github.com:organizacao/repositorio.git`; um endereço HTTPS usa outro método de autenticação. A chave de conta não deve ser confundida com uma deploy key associada a um repositório específico.

Antes de aceitar a identidade de um servidor, verifique a impressão digital por um canal confiável, sobretudo na primeira conexão. A confirmação salva uma chave de host conhecida; se ela mudar inesperadamente, pare e investigue em vez de ignorar o aviso.

## Resumo
- SSH cria um canal seguro para acessar serviços e máquinas remotas.
- A chave pública é cadastrada no destino; a privada permanece secreta e protegida.
- Uma passphrase pode proteger a chave privada; um agente pode mantê-la disponível na sessão.
- GitHub aceita acesso SSH quando a chave pública está cadastrada e o remoto usa URL SSH.
- Token de aplicação e chave SSH são credenciais distintas.
- Confira mudanças inesperadas na chave de host e nunca compartilhe a chave privada.

## Verificação — quiz
1. Qual chave pode ser cadastrada na conta do GitHub? **A)** A chave privada. **B)** A chave pública. **C)** As duas em um repositório público. **D)** Nenhuma. **Resposta: B.** A privada fica no dispositivo.
2. Para que serve a passphrase da chave privada? **A)** Proteger a chave armazenada localmente. **B)** Substituir DNS. **C)** Tornar pública a chave privada. **D)** Definir o nome do repositório. **Resposta: A.**
3. Uma mensagem informa que a chave de host mudou inesperadamente. O que fazer? **A)** Ignorar sempre. **B)** Investigar a identidade do servidor por um canal confiável antes de continuar. **C)** Enviar sua chave privada ao servidor. **D)** Desativar toda verificação. **Resposta: B.**
4. O que distingue chave SSH de token de API? **A)** São nomes diferentes para a mesma credencial. **B)** São mecanismos distintos de autenticação e acesso. **C)** Token sempre é público. **D)** SSH só funciona localmente. **Resposta: B.**
5. `ssh -T git@github.com` retorna `Permission denied (publickey)`. Qual é uma boa próxima etapa? **A)** Colar a chave privada em um chamado para alguém testar. **B)** Investigar, sem compartilhar segredos, se o remoto usa SSH, se a chave pública correspondente está cadastrada e se o cliente está oferecendo a chave esperada. **C)** Desativar a verificação da chave de host. **D)** Apagar todas as chaves do dispositivo. **Resposta: B.** A mensagem indica falha de autenticação por chave pública, mas sozinha não identifica qual etapa está incorreta.

## Prática — três níveis

As atividades usam GitHub como exemplo e devem seguir a documentação oficial correspondente ao seu sistema. Nunca inclua chave privada, passphrase ou saída com dados sensíveis em entregas, capturas de tela ou chamados.

### 1. Guiada — classifique os dados de uma conexão

Considere estes elementos de uma configuração fictícia:

```text
~/.ssh/id_ed25519       arquivo da chave privada
~/.ssh/id_ed25519.pub   arquivo da chave pública correspondente
git@github.com:acme/app.git
https://github.com/acme/app.git
SHA256:AbCdEf...        impressão digital apresentada na primeira conexão
```

**Tarefa:** classifique cada elemento como privado, público, endereço SSH, endereço HTTPS ou impressão digital de chave de host. Depois, responda: qual arquivo pode ser cadastrado na conta; qual endereço usa SSH; o que precisa ser confirmado antes de aceitar uma chave de host desconhecida?

**Gabarito comentado:** `id_ed25519` é a chave privada e permanece protegida no dispositivo; `id_ed25519.pub` é a chave pública e pode ser cadastrada na conta; o endereço que começa com `git@github.com:` usa SSH; o que começa com `https://` usa HTTPS; a impressão digital identifica a chave de host apresentada pelo servidor. Na primeira conexão, compare-a com a impressão digital publicada pelo GitHub em um canal oficial confiável antes de confirmar. A chave de host do servidor é diferente da chave de autenticação da sua conta.

### 2. Independente — diagnostique uma falha de autenticação

Uma pessoa informa que a conexão SSH falhou com `Permission denied (publickey)`. Ela afirma que cadastrou “a chave”, mas não sabe dizer qual arquivo. O repositório pode estar configurado com URL SSH ou HTTPS.

**Entregue:** uma sequência de até seis verificações, em ordem, que ajude a localizar o problema. Para cada etapa, diga que resultado observar e qual hipótese ele ajuda a avaliar. Inclua como confirmar o tipo de URL remota e como testar a autenticação. Não peça nem exponha a chave privada ou a passphrase.

**Dicas progressivas**

- Primeiro confirme se o repositório realmente usa SSH. Uma URL HTTPS segue outro fluxo e não depende dessa chave SSH.
- A mensagem de falha é compatível com várias causas: chave pública ausente ou diferente da privada oferecida, chave não carregada/selecionada, conta errada ou configuração do cliente. Avance por evidências, sem desativar a verificação do servidor.

**Referência para autocorreção:** uma sequência razoável identifica a URL remota (`git remote -v` ou `git remote get-url origin`); confere localmente quais pares de chave existem sem abrir nem copiar a privada; verifica se a chave pública correspondente foi cadastrada na conta correta; confere qual chave o cliente oferece, seguindo os comandos oficiais do sistema; executa `ssh -T git@github.com`; e compara qualquer impressão digital de host com a publicada pelo GitHub. A saída de `ssh-add -l` pode ajudar a inspecionar chaves carregadas, mas lista vazia, isoladamente, não prova que não exista uma chave padrão utilizável. Se o teste autenticar, o GitHub pode informar que não oferece acesso shell; essa mensagem é compatível com o teste bem-sucedido. Se persistir a falha, registre sistema, cliente e mensagem sem incluir segredos.

**Critérios de autocorreção (0–2 pontos cada; total 10)**

- Confirma se a URL remota usa SSH ou HTTPS.
- Verifica a relação entre chave privada local e chave pública cadastrada sem revelar a privada.
- Considera seleção/carregamento da chave e conta correta, sem concluir a causa apenas pelo erro.
- Testa a conexão e confirma a identidade do host por fonte confiável.
- Registra evidências úteis sem compartilhar chave privada, passphrase ou dados sensíveis.

Considere a atividade concluída com pelo menos 8 pontos e sem expor credenciais ou ignorar uma mudança inesperada de chave de host. Caso contrário, revise a etapa que falhou e refaça a sequência.

### 3. Transferência — configure e confirme o acesso SSH

Use um repositório de teste ou um repositório ao qual você já tenha acesso. Siga a documentação oficial para verificar se já possui uma chave adequada; gere um par novo somente se necessário. Proteja a chave privada, cadastre apenas a pública na conta correta e teste a conexão. Antes de confirmar uma chave de host na primeira conexão, compare a impressão digital com a publicada pelo GitHub. Depois, confira a URL remota do repositório e identifique se ela usa SSH ou HTTPS.

Registre um relatório sem segredos com o sistema usado, as etapas concluídas, o tipo de URL remota, o resultado observável do teste SSH e a diferença entre chave pública, privada e token. Não inclua conteúdo de arquivos de chave nem passphrase.

**Aceite:** a identidade do host foi verificada por fonte oficial; o teste identifica a conta esperada ou registra um diagnóstico da falha; a chave privada permanece local; somente a pública foi cadastrada; a URL remota foi classificada corretamente; o relatório não contém segredos. Se a saída informar que o GitHub não fornece acesso shell, isso por si só não invalida uma autenticação bem-sucedida.

## Critério de conclusão
Autenticar por chave SSH no GitHub e explicar o papel de cada chave, como proteger a privada e a diferença entre chave SSH e token de aplicação.
