# 3.2 — Trabalho com histórico

## Objetivo
Integrar mudanças com merge, rebase e cherry-pick, resolver conflitos e escrever mensagens de commit que expliquem a intenção da mudança.

## Teoria

### Três formas de integrar mudanças
`git merge outra-branch` incorpora o trabalho da outra branch na branch atual. Dependendo do histórico, Git pode avançar a referência (fast-forward) ou criar um commit de merge com os pais relevantes.

`git rebase base` reaplica commits da branch atual sobre outra base, criando novos commits com novos identificadores. Isso pode deixar a sequência mais linear, mas reescreve o trecho reaplicado. Evite reescrever commits que outras pessoas já usam sem combinar com elas; isso pode exigir sincronização cuidadosa.

`git cherry-pick <commit>` reaplica em outra branch a mudança de um commit escolhido, criando um novo commit. É útil quando você quer selecionar uma mudança específica, sem integrar todo o conjunto da branch.

### Conflitos
Um conflito ocorre quando Git não consegue combinar automaticamente partes alteradas, por exemplo quando duas branches mudam a mesma região de um arquivo de maneiras incompatíveis. Git marca a região em conflito no arquivo. Leia o contexto, escolha ou combine as mudanças corretas, remova os marcadores e revise o resultado. Depois marque o arquivo como resolvido (`git add`) e conclua ou continue a operação. Se não sabe o que preservar, converse com quem escreveu a mudança antes de escolher.

É possível abortar operações em andamento (`git merge --abort` ou `git rebase --abort`) para voltar ao estado anterior à tentativa, quando aplicável. Confira `git status` para saber qual operação está ativa. Antes de iniciar uma integração, conclua ou preserve as mudanças locais: `git merge --abort` tenta reconstruir o estado anterior, mas mudanças não commitadas podem dificultar essa recuperação. Não apague marcadores sem validar o conteúdo.

### Mensagens de commit
Uma mensagem deve ser curta o bastante para resumir a mudança e específica o bastante para distinguir intenção. Uma convenção como Conventional Commits usa tipos (`feat`, `fix`, `docs`, `refactor`) e uma descrição, podendo incluir escopo e notas de mudança incompatível. É uma convenção adotável, não um requisito do Git.

Exemplo: `docs(guia): explicar resolução de conflitos`. Evite mensagens vagas como `ajustes`, `coisas` ou `final`. Se for obrigatório escrever em inglês, mantenha o idioma consistente, mas preserve clareza.

## Resumo
- Merge integra históricos e pode criar commit de merge ou fast-forward.
- Rebase reaplica commits em outra base e gera novos identificadores; cuidado ao reescrever histórico compartilhado.
- Cherry-pick reaplica a mudança de um commit selecionado.
- Conflito exige compreender as alternativas, editar e revisar o resultado antes de marcar como resolvido.
- `git status` indica a operação em andamento; abortar pode ser preferível a uma resolução incerta.
- Mensagens de commit devem explicar a mudança; Conventional Commits é uma convenção opcional.

## Verificação — quiz
1. Você quer integrar toda uma branch ao trabalho atual. Qual operação normalmente representa isso? **A)** `merge`. **B)** `cherry-pick` de um commit aleatório. **C)** `gitignore`. **D)** `grep`. **Resposta: A.**
2. Qual efeito principal do rebase? **A)** Apagar todas as branches. **B)** Reaplicar commits sobre uma nova base, criando novos identificadores. **C)** Fazer upload ao GitHub. **D)** Apenas renomear arquivos. **Resposta: B.**
3. Quando cherry-pick é especialmente útil? **A)** Para selecionar uma mudança de commit específico. **B)** Para copiar todo o diretório sem histórico. **C)** Para resolver permissões. **D)** Para ignorar arquivos. **Resposta: A.**
4. Git informa conflito durante merge. O que fazer? **A)** Remover todo o arquivo. **B)** Examinar as versões, combinar conscientemente, revisar e marcar como resolvido. **C)** Executar `reset --hard` sem verificar. **D)** Publicar os marcadores de conflito. **Resposta: B.**
5. Uma branch já foi publicada e outras pessoas criaram trabalho a partir dela. Você precisa integrar seu conteúdo à branch atual. Qual decisão inicial preserva melhor o histórico compartilhado? **A)** Rebasear a branch publicada sem avisar. **B)** Preferir integrar por merge ou combinar com a equipe antes de reescrever commits compartilhados. **C)** Apagar os commits antigos. **D)** Fazer cherry-pick de todos os commits sem inspecioná-los. **Resposta: B.** Rebase cria novos identificadores para os commits reaplicados; alterar uma linha compartilhada pode exigir coordenação.

## Prática — três níveis

Faça as atividades em repositórios locais descartáveis, com arquivos fictícios. Antes de integrar, confira `git status` e conclua ou preserve mudanças locais. Não reescreva histórico compartilhado.

### 1. Guiada — escolha a integração pelo objetivo

Considere este histórico, com `main` atualmente selecionada:

```text
A---B  main
 \
  C---D  feature
```

Escolha uma operação para cada objetivo e explique o efeito no histórico:

1. Integrar todo o trabalho da branch `feature`, mantendo a relação entre as linhas de desenvolvimento visível.
2. Reaplicar os commits `C` e `D` sobre `main` para deixar a linha de trabalho privada mais linear.
3. Trazer apenas a correção registrada em `D` para `main`, sem integrar o restante da branch.

**Gabarito comentado:** (1) `git merge feature` integra o conjunto; como os históricos divergiram, pode criar um commit com os dois pais. (2) Na branch `feature`, `git rebase main` reaplica os commits sobre `B`, criando novos identificadores, por exemplo `C'` e `D'`; faça isso em histórico privado ou com coordenação se já tiver sido compartilhado. (3) `git cherry-pick D` aplica a mudança daquele commit à branch atual e cria um novo commit; o commit original continua na branch de origem. A escolha depende do objetivo e de quem já usa o histórico.

### 2. Independente — resolva um conflito com intenção

Em um conflito de merge, o arquivo `agenda.md` contém este trecho:

```text
## Entregas
<<<<<<< HEAD
- publicar o relatório mensal
=======
- publicar o relatório semanal
>>>>>>> feature/frequencia
```

O requisito confirmado pelo grupo é publicar os relatórios mensal e semanal. Descreva a edição final e a sequência para revisar e concluir o merge. Depois, descreva o que faria se não tivesse informação suficiente para escolher uma resolução.

**Dicas progressivas**

- `HEAD` identifica a versão da branch atual nesse conflito; a outra seção mostra a versão vinda da branch integrada. Os marcadores não fazem parte do conteúdo final.
- Consulte `git status` para identificar a operação; revise o arquivo e o diff antes de marcar a resolução. Se não puder decidir, peça contexto ou aborte a operação quando for seguro fazê-lo.

**Gabarito comentado:** uma edição possível é:

```text
## Entregas
- publicar os relatórios mensal e semanal
```

Remova todos os marcadores, confira `git diff` e `git status`, prepare o arquivo com `git add agenda.md` e conclua com `git merge --continue` (ou o fluxo indicado pelo projeto). Se a operação for um rebase, o comando de continuação é `git rebase --continue`. Sem contexto suficiente, não escolha uma versão ao acaso: consulte quem definiu o requisito ou, se necessário, use `git merge --abort` para cancelar o merge e voltar a um estado anterior, depois de confirmar que não havia trabalho local desprotegido.

**Critérios de autocorreção (0–2 pontos cada; total 8)**

- Produz resultado que atende ao requisito e mantém o sentido das duas mudanças.
- Remove todos os marcadores e inspeciona o diff antes de concluir.
- Usa `git status` para distinguir merge de rebase e escolhe a continuação correspondente.
- Reconhece quando pedir contexto ou abortar é mais seguro do que escolher sem evidência.

Considere a atividade concluída com pelo menos 6 pontos e sem deixar marcadores de conflito no resultado.

### 3. Transferência — compare merge, rebase e cherry-pick

Em três repositórios descartáveis, crie um commit-base com `agenda.md` e anote o nome da branch inicial. Em cada repositório, faça mudanças pequenas em arquivos diferentes para evitar conflitos acidentais.

1. **Merge:** crie uma branch `feature/completa`, faça nela dois commits; volte à branch inicial, faça um commit independente e integre `feature/completa` com `git merge`. Inspecione `git log --all --oneline --graph --decorate`.
2. **Rebase:** parta de outro commit-base; crie `feature/privada` e faça dois commits; volte à branch inicial e faça um commit independente; retorne à branch privada e reaplique-a sobre a branch inicial com `git rebase <branch-inicial>`. Compare o grafo antes e depois e identifique que os commits reaplicados têm novos identificadores.
3. **Cherry-pick:** parta do terceiro commit-base; crie `feature/correcao`, faça um commit pequeno e anote seu identificador; volte à branch inicial e aplique somente esse commit com `git cherry-pick <identificador>`. Confirme que o commit original permanece na branch de origem e que a branch atual recebeu um novo commit.

Use mensagens que expliquem a intenção, como `docs: incluir frequência de publicação`. Registre para cada caso: objetivo, branch em que estava, comando de integração, efeito no grafo e risco relevante. Não publique essas branches nem reescreva histórico compartilhado.

**Aceite:** os três grafos correspondem aos efeitos esperados; o conflito guiado não deixa marcadores; a pessoa explica quando integrar tudo, reaplicar uma linha privada ou selecionar um commit; mensagens identificam a mudança; nenhum histórico compartilhado foi reescrito.

## Critério de conclusão
Explicar merge, rebase e cherry-pick com um caso de uso para cada; resolver um conflito e justificar a solução; reconhecer o risco de reescrever commits já compartilhados.
