# 3.5 — Projeto incremental da fase

## Objetivo
Criar a base de trabalho que acompanhará o curso: escolher uma ideia para o projeto acumulado, documentar o ambiente, versionar uma parte segura do setup e manter um repositório de estudos com README e histórico legível.

## Teoria

### O repositório como caderno de engenharia
O repositório de estudos registra exercícios, decisões, referências e pequenas entregas do curso. Organize-o para você conseguir encontrar o que estudou e para outra pessoa entender como começar. Um exemplo de estrutura, adaptável às necessidades reais:

```text
estudos/
├── README.md
├── setup/
│   └── README.md
├── fase-1/
│   ├── ambiente/
│   ├── terminal/
│   └── git/
└── projetos/
    └── trilho-a/
```

Não crie diretórios vazios apenas para preencher uma árvore. Inclua arquivos quando houver conteúdo e revise a estrutura conforme o curso cresce.

### Escolha de uma ideia para o Trilho A
O projeto principal evoluirá durante o curso. Escolha um problema que ainda seja interessante quando ganhar novas funcionalidades, mas que possa começar simples. Três candidatos definidos no roadmap:

- **Gestor de tarefas:** exercita colaboração, organização por usuário ou empresa e fluxos de trabalho.
- **Loja virtual:** exercita catálogo, pedidos e regras transacionais.
- **Base de conhecimento:** exercita conteúdo, busca e evolução para recursos de IA.

Não é necessário desenhar agora a arquitetura final. Registre o problema, quem poderia usá-lo, uma primeira necessidade e por que a ideia combina com o que quer aprender. A escolha pode ser trocada uma única vez até o fim da Fase 4, com o motivo registrado no README, conforme o roadmap.

### Dotfiles e setup seguro
Dotfiles são arquivos de configuração do usuário, frequentemente com nomes iniciados por ponto em sistemas Unix. Versionar configurações pode facilitar a reprodução do ambiente, mas não copie indiscriminadamente sua pasta pessoal. Revise cada arquivo e remova tokens, chaves privadas, caminhos específicos, dados pessoais e configurações que possam prejudicar outra máquina. Prefira documentar o processo e versionar uma seleção pequena e segura.

O setup deve explicar pré-requisitos e passos para criar um ambiente funcional. Separe instruções gerais de preferências pessoais e inclua como verificar que cada ferramenta está disponível. Não inclua estimativas de tempo nesta entrega.

### Critérios de um repositório sustentável
Um bom repositório tem objetivo identificável, instruções que funcionam, organização simples, histórico compreensível e dados sensíveis fora do controle de versão. README não precisa ser longo; precisa responder às perguntas de quem chega. Issues podem registrar próximas etapas, mas não substituem a documentação essencial.

## Resumo
- O repositório de estudos será uma base contínua para exercícios e projetos.
- Organize por conteúdo real; mantenha a estrutura simples e evolutiva.
- Escolha gestor de tarefas, loja virtual ou base de conhecimento para o Trilho A e registre a justificativa.
- A escolha pode ser trocada uma vez até o fim da Fase 4, documentando o motivo.
- Versione apenas configurações revisadas e seguras; nunca inclua chaves privadas ou tokens.
- README deve permitir compreender objetivo, requisitos e primeiros passos.

## Projeto — base de trabalho do curso

Entregue o projeto em quatro marcos. Mantenha o mesmo repositório ao longo do curso e acrescente conteúdo conforme aprender. Não desenvolva agora a arquitetura nem as funcionalidades finais do produto: esta fase prepara uma base segura, reproduzível e compreensível.

### Marco 1 — escolha do problema e primeiro escopo

**Tarefas:** escolha gestor de tarefas, loja virtual ou base de conhecimento. Em `projetos/trilho-a/brief.md`, registre o problema, um possível usuário, uma necessidade inicial pequena e por que a ideia combina com o que quer aprender. Delimite o que ficará fora do primeiro passo. A possibilidade de trocar a escolha uma única vez até o fim da Fase 4 continua válida; se mudar, registre a razão.

**Evidência:** brief versionado e uma issue em inglês simples que descreva a primeira necessidade como uma tarefa observável.

**Verificação:** peça a alguém para ler o brief e dizer qual problema o projeto resolve, para quem e qual seria o primeiro resultado. Se trabalhar sozinho, aguarde um dia e faça essa leitura sem consultar suas notas; corrija ambiguidades.

**Aceite:** a ideia está entre as três opções; problema, usuário, necessidade inicial e justificativa estão registrados; a primeira issue tem resultado delimitado e compreensível.

### Marco 2 — repositório e instruções de entrada

**Tarefas:** crie o repositório de estudos com um `README.md` em inglês simples, contendo propósito, ideia escolhida, estrutura atual, requisitos e primeiros passos. Documente sistema, versão, editor, shell e ferramentas em `setup/README.md`; inclua passos de instalação a partir de fontes oficiais e uma forma observável de verificar cada ferramenta. Crie apenas diretórios que já tenham arquivos úteis.

**Evidência:** árvore de arquivos, README, guia de setup e commits com mensagens que descrevem as mudanças.

**Verificação:** faça uma cópia limpa do repositório em outra pasta e siga o setup usando somente o guia. Registre qualquer pré-requisito ou passo ausente; atualize as instruções e repita a conferência.

**Aceite:** outra pessoa consegue explicar o propósito e reproduzir o ambiente; shell e sistema estão identificados; cada ferramenta essencial tem verificação; o README corresponde à estrutura real.

### Marco 3 — histórico e configuração segura

**Tarefas:** adicione um `.gitignore` adequado ao ambiente; revise e versione somente configurações pessoais que possam ser compartilhadas com segurança, ou explique no README por que não adicionará dotfiles. Faça commits pequenos e claros. Antes de cada commit, inspecione `git status`, `git diff` e `git diff --staged`.

**Evidência:** `.gitignore`, histórico recente, estado limpo após os commits e justificativa sobre dotfiles.

**Verificação:** use apenas um arquivo de teste com valor fictício para conferir se o padrão de ignore funciona; confirme que ele não aparece como rastreado. Revise os arquivos preparados e os já commitados em busca de credenciais e dados pessoais. Se uma credencial real tiver sido commitada, interrompa a entrega, revogue/rotacione-a e siga o processo de resposta antes de prosseguir.

**Aceite:** o histórico é legível; o arquivo de teste é ignorado e não rastreado; configs compartilhadas foram revisadas; não há credenciais nem dados pessoais versionados. O `.gitignore` não é tratado como remoção de algo já commitado.

### Marco 4 — publicação e conferência remota

**Tarefas:** publique o repositório no GitHub sem arquivos sensíveis. Atualize a issue inicial conforme o resultado do trabalho. Revise README, commits, estado da branch e conteúdo remoto; registre no README como navegar pelos exercícios e projetos.

**Evidência:** repositório remoto acessível, issue atualizada, commits publicados e README final.

**Verificação:** clone o remoto em uma pasta limpa, confira se a branch e os arquivos esperados chegaram e siga novamente as instruções do README e do setup. Compare o resultado com o repositório original e corrija divergências.

**Aceite:** a cópia remota contém a versão pretendida; um clone novo permite entender o projeto e preparar o ambiente; issue e README apontam para o estado atual; nenhum segredo ou arquivo local sensível foi publicado.

**Rubrica comum para cada marco (0–4):** 4 = evidências completas e verificação aprovada; 3 = entrega aprovada com uma lacuna menor; 2 = artefato existe, mas falta evidência ou uma verificação importante; 1 = entrega incompleta ou difícil de usar; 0 = sem evidência avaliável. Os marcos 3 e 4 não são aceitos enquanto houver credencial real ou dado pessoal versionado.

### Revisão final do projeto

- [ ] Os quatro marcos têm evidência registrada e verificação aprovada.
- [ ] README em inglês simples descreve propósito, requisitos, estrutura e uso.
- [ ] Setup foi seguido a partir de um clone limpo.
- [ ] Histórico e issues têm mensagens claras e atualizadas.
- [ ] `.gitignore` foi conferido com um arquivo fictício; não há segredos ou dados pessoais versionados.
- [ ] A ideia e o primeiro escopo estão documentados; qualquer troca até o fim da Fase 4 tem justificativa.

## Critério de conclusão
Uma pessoa consegue compreender a ideia escolhida, preparar o ambiente seguindo a documentação e navegar pelo repositório; o histórico é legível e não há credenciais ou dados pessoais versionados.
