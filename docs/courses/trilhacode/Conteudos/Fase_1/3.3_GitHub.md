# 3.3 — GitHub

## Objetivo
Publicar um repositório no GitHub, sincronizar mudanças com `clone`, `fetch`, `pull` e `push`, colaborar por pull requests e revisão, organizar o projeto e manter segredos fora do histórico.

## Teoria

### Local e remoto
Um repositório **local** está no seu computador; um **remoto** é uma cópia hospedada em outro lugar, como GitHub. `git clone` cria uma cópia local de um remoto e configura uma referência chamada normalmente `origin`. `git fetch` busca objetos e referências novas sem integrar automaticamente as mudanças à sua branch. `git pull` busca e integra alterações (por padrão, em geral por merge; a configuração pode mudar esse comportamento). `git push` envia commits locais para o remoto, se as permissões e regras permitirem.

Antes de sincronizar, confira branch e estado. Se o remoto rejeitar um push por ter commits novos, busque as mudanças, integre-as conscientemente e tente novamente. Não use force push como atalho em branch compartilhada.

### Pull request e code review
Uma **pull request** (PR) propõe integrar mudanças de uma branch em outra no GitHub. Ela reúne contexto, commits, diferenças e conversa. A revisão deve verificar se a mudança atende ao objetivo, se o diff está coerente e se há riscos, testes ou documentação que precisam ser considerados. Feedback útil aponta evidência e sugere ações específicas; autores podem responder e enviar novos commits.

Uma PR é uma ferramenta de colaboração, não prova automática de qualidade. Regras de proteção podem exigir aprovação ou verificações antes do merge; essas regras dependem da configuração do repositório.

### Organização e fluxo
README explica propósito, uso, requisitos e como contribuir. Issues ajudam a registrar tarefas e decisões; labels e milestones podem organizar o trabalho se forem necessários. GitHub Flow é um fluxo simples comum: criar branch, fazer mudanças, abrir PR, revisar e integrar. GitFlow é outro modelo com branches e convenções próprias; não é requisito universal nem nome genérico para qualquer trabalho com branches.

### Segredos e credenciais
Não adicione `.env`, tokens, senhas, chaves privadas ou dados pessoais ao repositório. Use `.gitignore` para evitar rastrear arquivos locais apropriados, mas lembre que isso não remove conteúdo já commitado. Se um segredo for exposto, revogue ou rotacione imediatamente; depois avalie a remoção do histórico e avise colaboradores, pois cópias e forks podem continuar contendo o valor antigo.

## Resumo
- Clone copia um repositório remoto; fetch baixa atualizações; pull baixa e integra; push envia commits.
- Uma PR propõe mudanças e facilita discussão e revisão antes da integração.
- Code review examina diffs e contexto; aprovação e bloqueios dependem das regras do repositório.
- README explica como entender e usar o projeto.
- GitHub Flow e GitFlow são modelos diferentes; escolha conforme contexto.
- Nunca comite segredos; `.gitignore` não apaga o histórico; credencial exposta deve ser revogada/rotacionada.

## Verificação — quiz
1. Qual comando busca referências remotas sem integrar automaticamente as mudanças à branch atual? **A)** `git fetch`. **B)** `git push`. **C)** `git commit`. **D)** `git init`. **Resposta: A.**
2. O que uma pull request propõe? **A)** Apagar o remoto. **B)** Integrar mudanças de uma branch em outra, com contexto e revisão. **C)** Guardar senha no GitHub. **D)** Criar uma chave privada pública. **Resposta: B.**
3. `gitignore` impede o vazamento de um token já commitado? **A)** Sim, remove todos os commits antigos. **B)** Não; revogue/rotacione o segredo e trate o histórico. **C)** Só se mudar o nome do arquivo. **D)** Sim, após push. **Resposta: B.**
4. Qual afirmação sobre GitHub Flow e GitFlow é correta? **A)** São sinônimos. **B)** São modelos de trabalho diferentes; nenhum é obrigatório para todo projeto. **C)** Ambos são comandos Git. **D)** Pull request só existe no GitFlow. **Resposta: B.**
5. `git push` é rejeitado porque a branch remota tem commits que você ainda não buscou. Qual é o próximo passo mais seguro? **A)** Repetir o push com `--force` sem examinar a diferença. **B)** Buscar as referências, inspecionar o histórico e integrar as mudanças conforme o fluxo combinado antes de tentar enviar novamente. **C)** Apagar a branch remota. **D)** Criar um token e colocá-lo no README. **Resposta: B.** O push rejeitado é um sinal para entender a divergência; sobrescrever uma branch compartilhada pode remover trabalho de outras pessoas.

## Prática — três níveis

Use repositórios próprios de estudo ou material fictício. Não envie credenciais reais, dados pessoais ou arquivos locais sensíveis ao remoto.

### 1. Guiada — faça uma revisão baseada no diff

Uma pull request chamada “Ajusta cálculo” altera esta função. O requisito diz que o total deve somar o imposto ao preço:

```diff
 function calcularTotal(preco, taxa) {
-  return preco + preco * taxa;
+  return preco - preco * taxa;
 }
```

Para `preco = 100` e `taxa = 0.10`, o resultado esperado é `110`.

**Tarefa:** escolha entre comentar, aprovar ou solicitar mudanças. Escreva um comentário curto que cite o comportamento observado, o caso que demonstra o problema e uma ação concreta para corrigir ou verificar. Mantenha o comentário respeitoso e ligado à mudança proposta.

**Gabarito comentado:** a revisão deve solicitar mudanças, pois o sinal subtrai o imposto. Um comentário útil seria: “Com preço 100 e taxa 0,10, esta expressão retorna 90, mas o requisito espera 110. Pode somar a parcela do imposto e incluir um teste para esse caso?” O comentário identifica o resultado, mostra a evidência e pede uma ação verificável. A decisão de revisão não substitui a configuração de regras do repositório.

### 2. Independente — responda a dois incidentes de colaboração

Escreva um procedimento curto para cada situação, em ordem, separando observação, decisão e ação:

1. O push foi rejeitado porque `origin` contém commits novos. Você não sabe se outras pessoas também usam a branch.
2. Um token real apareceu em um commit enviado ao remoto, mas a pull request ainda não foi integrada.

Inclua para cada caso: o que verificar primeiro, qual ação imediata reduz risco, o que não se deve presumir e quando envolver responsáveis pelo repositório. Não inclua comandos com segredos nem valores de tokens.

**Dicas progressivas**

- No caso do push, `git fetch` atualiza as referências remotas sem integrar por si só. Compare os históricos e siga a convenção acordada para merge ou rebase; não presuma que a branch é privada.
- No caso do segredo, removê-lo em um commit posterior não invalida o valor já exposto. A credencial precisa ser revogada/rotacionada; depois, trate o histórico e as cópias com os responsáveis.

**Referência para autocorreção:** (1) registre a mensagem de rejeição; confira `git status -sb`; busque com `git fetch origin`; inspecione o grafo com `git log --oneline --graph --decorate --all`; confirme se a branch é compartilhada e integre conforme o fluxo do projeto; revise o resultado e tente o push novamente. Não use `--force` para contornar a divergência. (2) avise os responsáveis e revogue/rotacione o token imediatamente junto ao provedor; avalie o alcance do acesso e quais sistemas receberam o commit; só então coordene a remoção do histórico, sabendo que clones, forks e caches podem manter cópias. Não espere a pull request ser integrada e não considere a exclusão do arquivo suficiente.

**Critérios de autocorreção (0–2 pontos cada; total 10)**

- Usa `fetch` e inspeciona a divergência antes de integrar mudanças remotas.
- Confirma o estado compartilhado da branch e segue a convenção do projeto.
- Não recomenda sobrescrever histórico com force push sem coordenação.
- Prioriza revogar/rotacionar o segredo exposto e envolver os responsáveis.
- Reconhece que remover um arquivo ou commit não garante que cópias remotas desapareceram.

Considere a atividade concluída com pelo menos 8 pontos e sem expor credenciais ou sobrescrever trabalho remoto às cegas.

### 3. Transferência — publique e revise uma pull request

Crie um repositório de estudo sem dados sensíveis, clone-o, faça uma branch e altere o README para explicar propósito, requisitos e uso. Envie a branch e abra uma pull request para a branch principal. Peça revisão a alguém; se estiver trabalhando sozinho, faça uma auto-revisão do diff e registre uma observação concreta e a melhoria correspondente. Responda ao feedback recebido com uma alteração ou justificativa e integre a mudança conforme as permissões e regras do repositório.

Antes de enviar, inspecione o diff e confirme que `.env`, tokens, chaves, dados pessoais e arquivos de ambiente não aparecem nele. Na descrição da PR, inclua contexto, mudança realizada e como verificar o resultado. Depois da integração, confira o estado final da branch e do remoto.

**Aceite:** README explica objetivo e uso; branch e PR têm nomes e descrições claros; o diff foi revisado; feedback é específico ou, no exercício individual, a observação e melhoria ficam registradas; não há credenciais ou arquivos sensíveis no diff; a integração e o estado final são compreendidos.

## Critério de conclusão
Conduzir o fluxo clone → branch → commit → push → pull request → revisão → integração, explicar a diferença entre fetch e pull e demonstrar como prevenir e responder à exposição de credenciais.
