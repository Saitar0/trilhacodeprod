## Objetivo
Ler o caminho de uma API ASP.NET Core e relacionar endpoint, injeção de dependências, acesso a dados e testes a conceitos de Node, distinguindo EF Core e Dapper. Construir a API completa apenas se esta for a stack escolhida.

## Teoria
### 1. C#, SDK e pipeline de API
C# é uma linguagem tipada executada no ecossistema .NET. O .NET SDK fornece comandos e ferramentas para criar, compilar, executar e publicar projetos; NuGet distribui e restaura pacotes. Leia o `.csproj`, `global.json` quando existir e as dependências do projeto para identificar target framework, SDK esperado e bibliotecas.

ASP.NET Core processa requisições por um pipeline configurado no ponto de entrada, geralmente `Program.cs`. Middleware envolve a requisição e resposta; endpoints podem ser declarados como **Minimal APIs** ou por **controllers**. Minimal APIs reduzem cerimônia em endpoints diretos; controllers dão organização e convenções familiares quando há muitas ações, validação e filtros. Ambos podem compor a mesma aplicação, e nenhum estilo é automaticamente mais adequado para todo caso.

Um percurso de leitura comum: rota/endpoint → middleware/autenticação → handler/controller → serviço de domínio injetado → persistência → resposta. Compare responsabilidades com rotas, middleware, handlers e módulos em Node, mas confira a configuração explícita do projeto .NET.

### 2. Injeção de dependência e persistência
ASP.NET Core tem container de injeção de dependências. Três ciclos comuns:
- **Transient:** instância nova a cada resolução;
- **Scoped:** instância compartilhada dentro do escopo, normalmente uma requisição web;
- **Singleton:** uma instância durante a vida da aplicação, potencialmente usada por várias requisições.

Não capture um serviço scoped, como `DbContext`, dentro de um singleton: o serviço mais curto passa a ser retido por tempo maior e pode quebrar escopo de dados ou segurança concorrente. Um singleton com estado compartilhado também precisa ser thread-safe. Configure e valide os ciclos de vida deliberadamente.

**EF Core** mapeia modelos via `DbContext`, usa LINQ e oferece migrations para registrar mudanças de schema. Migrations geradas precisam de revisão: uma propriedade renomeada pode ser interpretada como excluir uma coluna e criar outra, perdendo dados. Para produção, escolha estratégia de deployment, credenciais de migração, revisão de SQL/script ou bundle e plano de rollback; não entregue alterações de banco a cada réplica da aplicação ao iniciar sem avaliar o risco.

**Dapper** é um micro-ORM sobre ADO.NET que executa SQL e mapeia resultados para objetos. A consulta permanece explícita; use parâmetros, não concatene entrada do usuário. EF Core e Dapper podem coexistir em partes diferentes do sistema. Escolha pelo tipo de consulta, manutenção e necessidade de controle, não por um ranking geral.

### 3. Testes, suporte e produção
xUnit é uma opção comum de testes em .NET. Testes unitários cobrem lógica isolada; integração cobre colaboração real entre API, banco, provider ou autenticação quando essa fronteira importa. Mockar `DbContext` não comprova que uma migration funciona no provider relacional de produção; use banco/provider de teste apropriado para esse risco. Registre qual comportamento cada teste demonstra.

Versão do runtime importa. Em **15/10/2026**, o .NET 10 está em suporte LTS até 15/11/2028. Os ciclos de suporte oficiais indicam encerramento de .NET 8 LTS e .NET 9 em 11/11/2026; planeje novo conteúdo e projetos com a matriz vigente, sem confundir .NET moderno com .NET Framework legado. Atualize esta nota antes da produção efetiva do curso.

**Se esta for a stack escolhida:** reclassifique a unidade como obrigatória/média; estude C#, SDK e NuGet; implemente API com validação, DI, EF Core/migration revisada, teste unitário e integração, deploy sandbox e consulta Dapper apenas se houver razão documentada. Fixe versão suportada e provedores compatíveis.

## Resumo
- ASP.NET Core recebe requisições via pipeline; Minimal APIs e controllers são estilos para expor endpoints.
- DI tem ciclos transient, scoped e singleton; lifetime e concorrência devem ser compatíveis.
- EF Core oferece ORM e migrations, que precisam ser revisadas e aplicadas por estratégia segura.
- Dapper mantém SQL explícito; parâmetros protegem entrada e deixam o comportamento da consulta visível.
- Escolha testes pelo risco e runtime conforme suporte oficial; confirme a versão quando for produzir.

## Flashcards
- **Uma migration EF Core deve ser aplicada em produção sem revisão?** Não. Revise o código/SQL, escolha estratégia de deployment e avalie perda de dados e reversão.
- **Dapper elimina SQL?** Não. SQL explícito faz parte do uso; parâmetros devem representar dados de entrada.
- **Um singleton pode depender diretamente de serviço scoped, como DbContext?** Em geral não. Isso captura uma dependência de escopo curto em objeto compartilhado; crie/consuma escopo corretamente.

## Práticas

### Atividade 1 — Trace endpoint e ciclo de vida
**Contexto:** uma API tem `GET /orders/{id}`, controller `OrdersController`, serviço `OrderService` e `AppDbContext`. O DbContext está registrado como scoped; `OrderService` foi registrado como singleton.

**Instruções:** desenhe a requisição desde rota até resposta; marque em que ponto cada dependência é resolvida; explique o problema potencial no lifetime atual; proponha registro coerente e indique qual consulta/verificação faria. Compare esse caminho a uma rota Node com middleware/controller/service.

**Entrega:** diagrama curto, ciclo de vida proposto e justificativa de até 120 palavras.

**Dica gradual:** acompanhe a árvore de dependências. O serviço singleton retém suas dependências por mais tempo do que o escopo de uma requisição.

**Feedback de referência:** um `DbContext` scoped não deve ser injetado diretamente no construtor de serviço singleton; avalie tornar `OrderService` scoped/transient ou criar escopos de forma explícita conforme a necessidade. Use validação de escopo e testes que cruzem requisições.

**Erro comum:** considerar que o container resolve os lifetimes automaticamente sem consequência ou que `DbContext` é seguro para uso concorrente compartilhado.

### Atividade 2 — Escolha persistência e revise migração
**Contexto:** um endpoint precisa gravar pedidos com mudanças de modelo frequentes e relações; outro endpoint monta um relatório com consulta SQL já otimizada. Uma migration gerada renomeia `CustomerName` para `Name` por meio de `DropColumn` seguido de `AddColumn`.

**Instruções:** indique onde EF Core pode ser adequado e onde Dapper pode ser considerado; proponha como parametrizar a consulta do relatório; explique o risco de dados da migration; descreva artefato e revisão necessários antes de aplicar em produção. Selecione um teste unitário e um de integração que forneçam evidência distinta.

**Entrega:** nota técnica com decisão por endpoint, migration corrigida/revisada em nível conceitual, evidências de testes e uma condição de rollback.

**Dica gradual:** a migration não sabe sempre se uma coluna removida e outra criada representam renomeação; Dapper ainda recebe parâmetros de consulta, não valores concatenados.

**Feedback de referência:** EF Core facilita modelo/relacionamentos e evolução do schema; Dapper pode dar controle para consulta especializada. Revise o SQL para preservar dados, gere script/bundle ou use processo controlado de aplicação, e teste o comportamento com provider relacional apropriado.

**Erro comum:** aceitar a migration só porque foi gerada automaticamente ou testar apenas com mock e concluir que o SQL/provider está correto.

## Critério de conclusão
Mapear endpoint, middleware, controller/handler, DI e persistência; explicar um conflito de lifetime e diferenciar EF Core de Dapper; justificar migration/testes para um caso concreto.
