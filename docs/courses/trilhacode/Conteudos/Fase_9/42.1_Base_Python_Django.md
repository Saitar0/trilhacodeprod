## Objetivo
Reconhecer o caminho de uma requisição numa API Django REST Framework (DRF), relacionar seus componentes aos conceitos de Node já estudados e identificar onde ficam validação, persistência e autorização. Construção completa é opcional e só se aplica se Django for a stack escolhida.

## Teoria
### 1. Python, projeto e app Django
Python organiza código em módulos e pacotes. Um ambiente virtual isola as dependências de cada projeto; registre versões e confira a compatibilidade entre Python, Django e bibliotecas antes de iniciar um projeto.

No Django, **project** reúne configurações e aplicações para um site; um **app** agrupa uma capacidade reutilizável. `settings.py` configura apps, middleware, banco e políticas; `urls.py` encaminha caminhos; `manage.py` executa comandos do projeto. O app costuma concentrar modelos, views, configuração e migrations. Um app não é necessariamente um microsserviço: pode permanecer no mesmo processo e banco do projeto.

O comando `runserver` é para desenvolvimento. Para produção, siga o guia de deploy da versão escolhida e use um servidor WSGI/ASGI adequado, configurações seguras e infraestrutura operacional.

**Checagem:** `project` e `app` significam a mesma coisa? Não. O projeto configura uma instância do site e pode reunir vários apps.

### 2. Do URL ao modelo: ciclo Django
Uma requisição entra pelo servidor e passa pelo middleware configurado. O resolvedor compara o caminho com `urlpatterns` e chama uma view. A view interpreta a solicitação, pode consultar ou alterar dados pelo ORM e devolve uma resposta. Modelos definem campos e comportamento dos dados; migrations registram mudanças de esquema que podem ser aplicadas ao banco.

Mapa aproximado com conceitos já vistos em Node:

| Django | Papel aproximado | Analogia possível em Node |
|---|---|---|
| URLconf | associa caminho à execução | router |
| middleware | lógica ao redor de várias requisições | middleware |
| view | coordena requisição e resposta | controller/handler |
| model e ORM | dados e consultas | model/repositório/ORM |
| migration | histórico declarativo do schema | migration de ORM |
| settings e apps | configuração e organização | configuração e módulos |

As equivalências são guias de leitura, não correspondências exatas. Convenções do framework participam da resolução e execução; siga o caminho concreto no projeto em vez de presumir que um nome tem a mesma função em toda stack.

**Checagem:** onde procurar a rota e onde procurar a estrutura persistida? Em `urls.py`/URLconf para o mapeamento e em `models.py` e migrations para dados e evolução do esquema.

### 3. DRF: serialização, views e controle de acesso
DRF adiciona ferramentas para APIs sobre Django:
- **Serializer:** valida entrada e converte dados entre representações externas e objetos Python/modelos. Serializer não é, por si só, autenticação ou autorização.
- **APIView, generic views e ViewSet:** implementam o comportamento da API. ViewSet reúne ações como listar, criar, recuperar, atualizar e excluir.
- **Router:** pode gerar rotas convencionais para um ViewSet; uma URL explícita pode ser mais clara em fluxos simples ou especiais.
- **Authentication:** identifica quem fez a requisição segundo o mecanismo configurado.
- **Permissions:** permitem ou negam ações. `IsAuthenticated` confirma que há usuário autenticado, mas não significa que ele só veja os próprios registros.
- **Queryset:** também define quais objetos entram em uma listagem. Para dados por usuário, filtre o queryset pelo usuário atual; confira separadamente criação, detalhe, atualização e exclusão.

Exemplo conceitual: se `GET /tarefas/` retorna `Task.objects.all()` com `IsAuthenticated`, qualquer usuário autenticado pode potencialmente receber tarefas de outros usuários. A lista precisa ser limitada, por exemplo, às tarefas cujo proprietário seja `request.user`. Em endpoint de criação, o proprietário deve ser atribuído no servidor conforme a política, sem confiar cegamente num `owner_id` enviado pelo cliente. Permissões por objeto também exigem atenção para listagem e criação: o DRF não aplica automaticamente cada verificação de objeto a todos os itens de uma lista.

**Checagem:** um endpoint com login ativo já protege os dados de todos os outros usuários? Não; autenticação identifica; queryset e permissões definem acesso.

**Se Django for a stack escolhida:** siga o tutorial oficial atualizado da versão estável; implemente uma pequena API CRUD de tarefas com ORM, migrations, validação, autenticação e autorização; teste isolamento entre usuários e erros; faça deploy de teste. A documentação consultada para Django 6.1 indica suporte a Python 3.12 ou posterior; confirme a matriz no momento da produção. Essa trilha de implementação é opcional para esta unidade de repertório.

## Resumo
- Project reúne configuração e apps; app organiza uma capacidade dentro do Django.
- URLconf, middleware, view, model/ORM e migration conduzem e persistem uma requisição.
- DRF usa serializers, views/ViewSets, routers, autenticação e permissões para APIs.
- Login não equivale a autorização por objeto: filtre dados visíveis e valide criação/alterações.
- `runserver` serve ao desenvolvimento; produção requer servidor e configurações adequados.

## Flashcards
- **O que distingue project de app no Django?** Project reúne configurações e apps do site; app agrupa uma funcionalidade/capacidade.
- **Serializer do DRF controla autorização?** Não. Valida/converte dados; autenticação, permissions e queryset controlam identidade e acesso.
- **`runserver` pode ser usado como servidor de produção?** Não. É servidor de desenvolvimento; use um servidor WSGI/ASGI e o guia de deploy correspondente.

## Práticas

### Atividade 1 — Siga uma requisição até a resposta
**Contexto:** considere `GET /api/tarefas/` atendido por um `TaskViewSet`, registrado em um router, usando `TaskSerializer` e o modelo `Task`.

**Instruções:** monte uma sequência com URL/router → ação `list` → queryset → serializer → resposta. Para cada etapa, indique o arquivo/componente provável e uma pergunta que faria ao revisar o código. Depois escreva uma equivalência aproximada com um endpoint Node que você já conhece e uma diferença que não deve ser escondida pela analogia.

**Entrega:** diagrama de cinco etapas ou tabela com componente, responsabilidade e evidência procurada.

**Dica:** separe “selecionar os objetos” de “converter os objetos”; são responsabilidades relacionadas, mas não iguais.

**Feedback de referência:** router resolve o caminho; viewset executa `list`; queryset escolhe registros; serializer prepara a representação; DRF constrói a resposta. Uma analogia razoável é router/controller/ORM/schema, mas convenções e ciclo exato variam por framework.

**Erro comum:** atribuir ao serializer o trabalho de escolher quais linhas o usuário pode consultar.

### Atividade 2 — Revise o isolamento entre usuários
**Contexto:** uma API tem `permission_classes = [IsAuthenticated]` e `queryset = Task.objects.all()`. Cada tarefa possui um campo `owner`. A listagem responde com tarefas de todas as contas.

**Instruções:** explique por que o login não resolve o vazamento; proponha um queryset limitado ao usuário atual; diga como a criação deve definir `owner`; descreva os casos a verificar ao abrir, alterar e excluir uma tarefa de outra pessoa. Use o guia de permissões do DRF como referência.

**Entrega:** revisão curta com falha, ajuste proposto e quatro casos de aceite: listar apenas próprias; criar sem poder forjar proprietário; acessar tarefa alheia; alterar/excluir tarefa alheia.

**Dica:** pense no conjunto retornado pela listagem separadamente da permissão geral de acesso à view. Para criação, não existe ainda um objeto recuperado do banco sobre o qual aplicar a verificação de objeto.

**Feedback de referência:** `get_queryset()` pode limitar por `request.user`; atribua o owner no servidor (por exemplo, em `perform_create`) conforme o desenho. Verificações de objeto aplicadas ao detalhe não filtram automaticamente listagens; um usuário sem autenticação e um usuário autenticado sem acesso podem resultar em respostas diferentes conforme o mecanismo configurado.

**Erro comum:** testar somente que uma requisição sem token falha e concluir que o isolamento entre contas está garantido.

## Critério de conclusão
Traçar corretamente URL → view/viewset → queryset/model → serializer → resposta; explicar a diferença entre autenticação e autorização, identificar o risco de queryset sem filtro e completar as duas práticas curtas.
