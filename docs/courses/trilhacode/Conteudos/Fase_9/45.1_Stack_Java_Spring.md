## Objetivo
Ler o fluxo de uma API Java com Spring, explicar como injeção de dependências, persistência e testes se conectam e reconhecer os limites de uma integração assíncrona com Kafka.

## Teoria

### 1. Java, Spring e o caminho de uma requisição
Java é compilado para bytecode executado pela JVM. Maven e Gradle automatizam resolução de dependências, compilação, testes e empacotamento; o projeto registra qual ferramenta e versão usa para tornar o build reproduzível. O Java define a linguagem e a plataforma; Spring Framework oferece componentes para configuração, injeção de dependências e aplicações web; Spring Boot reúne convenções, starters e auto-configuração para iniciar uma aplicação Spring com menos configuração manual. Auto-configuração depende do que está presente no classpath e pode ser ajustada quando a convenção não serve.

Em um endpoint típico, o **controller** interpreta HTTP e valida a entrada de borda, o **service** coordena a regra de negócio e o **repository** acessa a persistência. A entidade ou modelo persistido não precisa ser o formato público da resposta. A injeção por construtor declara as dependências necessárias e facilita fornecer substitutos em testes. Ela não torna a regra de negócio correta por si só: essa regra ainda precisa ser observável e testada.

Ao ler código, percorra: rota e parâmetros → controller → service → repository → resultado e resposta HTTP. Identifique onde erros de domínio viram respostas, onde a transação começa e quais dependências o container cria. Em Node, compare o papel desses componentes com rota/controller, serviço e camada de dados; a comparação é de responsabilidades, não de equivalência obrigatória de frameworks.

### 2. Persistência: especificação, implementação e consultas
Jakarta Persistence (JPA) define contratos para mapeamento objeto-relacional e operações de persistência; Hibernate é uma implementação popular. Spring Data JPA adiciona abstrações de repository e pode derivar consultas a partir de nomes de métodos ou executar consultas declaradas. A conveniência reduz código repetitivo, mas não elimina a necessidade de entender SQL, índices, cardinalidade e o comportamento da consulta gerada.

Entidades e relacionamentos têm ciclo de vida e estratégia de carregamento. Acessar uma coleção lazy fora do contexto de persistência pode falhar; percorrer relações em uma lista pode gerar muitas consultas (N+1). Analise a consulta e o volume esperado, use paginação quando a lista puder crescer e confirme o comportamento com banco de teste quando ele for parte do risco. Delimite transações em torno de uma operação de negócio coerente; não presuma que cada método de repository, isoladamente, dá atomicidade ao fluxo inteiro.

### 3. Testes e integração com Kafka
Escolha o teste pela fronteira que precisa verificar. Um teste de controller com contexto reduzido pode validar rota, serialização e status HTTP; teste de service com dependências substituídas examina decisões de negócio; teste de integração com banco verifica mapeamento, consulta e transação reais. Um mock do repository é útil para isolar comportamento, mas não prova SQL, configuração do ORM ou compatibilidade com o banco de produção.

Spring for Apache Kafka fornece abstrações para publicar mensagens e receber eventos. No consumo, a aplicação precisa definir quando confirma o offset, como trata falhas e redelivery, e o que acontece após esgotar retries; política de erro pode encaminhar mensagens para uma dead-letter topic, conforme a configuração. Se o efeito no banco ocorrer e o processo falhar antes da confirmação do offset, o evento pode ser entregue novamente. Projete o efeito para ser idempotente, por exemplo registrando um identificador de evento processado junto da alteração de negócio, com restrição atômica. Confirmação do broker, transação Kafka e gravação no banco não formam automaticamente uma única transação de negócio de ponta a ponta.

**Se esta for a stack escolhida:** reclassifique a unidade como obrigatória ou média e faça uma trilha prática de Java, tipos, exceções, coleções e Maven/Gradle antes de construir uma API CRUD Spring Boot. Inclua migrações, testes adequados às fronteiras e, se Kafka fizer parte do projeto, um consumidor com política explícita de retry e deduplicação. Consulte as matrizes oficiais de compatibilidade e fixe versões de Java, Spring Boot, Spring Data e Kafka no projeto; elas mudam ao longo do tempo.

## Resumo
- Spring Boot aplica convenções sobre Spring; controller, service e repository organizam responsabilidades, e DI conecta componentes.
- JPA é uma especificação, Hibernate é uma implementação e Spring Data JPA simplifica repositories sem esconder o custo das consultas.
- Testes com mocks isolam decisões, enquanto testes com banco verificam integração e persistência.
- Kafka pode redeliver mensagens; offsets, retries e efeitos idempotentes precisam de desenho explícito.

## Flashcards
- **JPA é um ORM específico?** Não. É uma especificação; Hibernate é uma implementação conhecida.
- **Spring Data repository elimina a necessidade de entender SQL?** Não. É preciso avaliar consulta, transação, volume e índice.
- **Confirmar o offset do Kafka garante que banco e negócio ocorreram exatamente uma vez?** Não. Falhas entre gravação e confirmação podem provocar redelivery; o efeito precisa tolerar repetição e as fronteiras transacionais devem ser compreendidas.

## Critério de conclusão
Dado um endpoint e um consumidor Kafka, a pessoa consegue traçar controller → service → repository, apontar o limite de um teste com mock e explicar como uma redelivery pode duplicar um efeito se não houver idempotência.

## Prática
### Atividade 1 — Rastrear um endpoint
Leia uma API Spring Boot pequena ou um exemplo fornecido. Para `GET /orders/{id}`, desenhe o caminho da entrada HTTP até a consulta e o retorno. Marque onde estão validação, regra de negócio, acesso a dados, conversão para resposta e injeção de dependências. Em seguida, associe cada responsabilidade a uma possível camada de uma API Node que você conhece.

**Entregável:** diagrama ou lista de 5–8 passos e uma tabela curta com as responsabilidades Spring e a comparação em Node.

**Feedback para revisar:** a resposta está completa se cada passagem aponta para uma classe ou função identificável, se regra de negócio não foi atribuída ao repository e se reconhece que a estrutura de camadas é uma escolha de organização. Se só listar nomes das camadas, volte ao código e registre o dado que entra e sai de cada uma.

### Atividade 2 — Escolher testes e proteger o consumo
Considere duas situações: (a) um método de service calcula o total de um pedido e usa um repository; (b) um consumidor Kafka grava uma alteração no banco e só depois confirma o offset. Para cada situação, escolha o teste que dá evidência adequada. Na segunda, descreva o que acontece se o processo cair depois da gravação e antes da confirmação e proponha uma proteção contra duplicidade.

**Entregável:** uma matriz com situação, risco, teste e evidência esperada, mais um parágrafo descrevendo a falha e a proteção para Kafka.

**Feedback para revisar:** para (a), um teste de unidade com repository substituído verifica a regra, mas não a consulta SQL; complemente com integração se o mapeamento/query for risco. Para (b), reconhecer redelivery é necessário; uma resposta adequada usa deduplicação/idempotência atômica ou outra estratégia explícita e não afirma que o ack, sozinho, resolve a consistência entre Kafka e banco.

**Construção opcional se Java/Spring for a stack escolhida:** API CRUD com Spring Boot, JPA e migração de banco, teste de controller e integração com Kafka local que demonstre redelivery idempotente. Registre as versões de Java e das ferramentas de build.
