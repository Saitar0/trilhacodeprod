## Objetivo
Comparar FastAPI, Flask e Django para um cenário pequeno de API, reconhecendo validação, documentação, convenções, operação e limites do modo assíncrono, sem tratá-los como um ranking universal.

## Teoria
### 1. API, validação e documentação
**FastAPI** organiza operações HTTP usando declarações Python e modelos de dados. Type hints e modelos Pydantic ajudam a interpretar parâmetros, validar/serializar dados e gerar um schema OpenAPI com documentação interativa. Esse fluxo reduz repetição em APIs orientadas a contratos, mas não define sozinho regra de negócio, autorização, persistência, limites de uso ou testes. Um campo com tipo correto não prova que o usuário pode alterar aquele recurso.

**Flask** oferece rotas e ciclo de requisição com um núcleo pequeno. Validação, schema OpenAPI, ORM, autenticação e outras funções costumam vir de bibliotecas/extensões escolhidas pela aplicação. A equipe ganha liberdade para montar a composição, assumindo decisões de compatibilidade, integração, atualização e segurança.

**Django com DRF**, da unidade 42.1, oferece um conjunto mais integrado e convencionado: apps, ORM, migrations, serializers, views/routers e controles de acesso. Para API pequena, isso pode ser mais estrutura do que o caso precisa; para uma aplicação com persistência, administração e convenções comuns, pode evitar escolhas dispersas.

**Checagem:** geração de OpenAPI ou serializer valida autorização? Não. Validação descreve/limita dados; autorização decide quem pode realizar qual ação.

### 2. Convenções, composição e custo de equipe
| Dimensão | FastAPI | Flask | Django + DRF |
|---|---|---|---|
| Ponto forte | Construção de API com tipos/modelos e schema OpenAPI integrados | Núcleo pequeno, simples de compor e ampliar | Estrutura de aplicação e componentes integrados/convencionados |
| Decisões da equipe | Modelos, dependências, persistência, auth, deployment e divisão do projeto | Mais decisões e extensões: dados, validação, auth, estrutura e schema | Organização de apps, modelos, settings e componentes DRF dentro das convenções |
| Pergunta de custo | A equipe domina contratos e dependências escolhidas? | Há tempo e critério para selecionar e manter extensões? | As convenções integradas atendem ao caso sem impor estrutura excessiva? |

“Microframework” não significa apenas uma aplicação de um arquivo, nem prova que Flask não possa crescer. FastAPI também não fornece automaticamente toda a aplicação de negócio. Em qualquer opção, examine maturidade e manutenção das dependências, suporte de segurança, documentação, migração de dados, logs, autenticação/autorização e deploy.

Compare uma fatia real de trabalho — validar uma entrada, persistir um registro, proteger acesso e publicar — em vez de comparar apenas o código “Hello World”. Registre também experiência da equipe, contratação, bibliotecas existentes e custo de operação.

**Checagem:** menos linhas no exemplo inicial bastam para concluir menor custo total? Não; faltam manutenção, segurança, dependências, deploy e trabalho de integração.

### 3. Síncrono, async e operação
FastAPI permite handlers `async def` e foi projetado para trabalhar com funções assíncronas quando as bibliotecas chamadas também oferecem operações awaitable. Se uma biblioteca de banco ou HTTP for bloqueante, marcá-la como `async` não a torna não bloqueante. Use async para concorrência de I/O que o stack suporta; não espere acelerar trabalho intensivo de CPU só por mudar a assinatura da função.

Flask é WSGI e aceita views assíncronas com a dependência extra correspondente, mas sua documentação explica que cada requisição ainda ocupa um worker durante o ciclo; async permite, entre outros usos, aguardar I/O concorrente dentro da requisição, mas não muda automaticamente a capacidade de requisições simultâneas de cada worker. Tarefas lançadas sem espera numa view podem ser canceladas quando o ciclo de eventos termina; trabalho durável de fundo deve usar uma fila/worker apropriado, como o padrão discutido em 42.2.

Django também tem suporte assíncrono em partes do stack, mas compatibilidade de middleware, ORM e bibliotecas depende de versão e uso. Não faça afirmações gerais a partir de um benchmark isolado. Compare o servidor/protocolo, bibliotecas, chamadas bloqueantes, concorrência, carga, latência, observabilidade e requisitos de WebSocket/long-lived connections na versão que pretende usar.

Todos precisam de configuração de produção adequada. Servidores de desenvolvimento e modo debug são para desenvolvimento; deployment envolve servidor compatível, variáveis/secrets, segurança, limites e telemetria.

**Checagem:** mudar um endpoint Flask para `async def` garante que uma requisição atendida deixa o worker livre para outra? Não; no modelo WSGI descrito pelo Flask, cada ciclo ainda ocupa um worker.

## Resumo
- FastAPI integra declarações tipadas, modelos de dados, validação e OpenAPI para APIs.
- Flask oferece um núcleo leve/extensível; a equipe seleciona e mantém mais componentes.
- Django/DRF inclui mais convenções e recursos de aplicação; pode ser adequado ou excessivo conforme o caso.
- Async depende de bibliotecas não bloqueantes e do servidor; não é sinônimo de mais rápido ou de tarefa em background durável.
- Escolha por caso real, experiência, segurança, dependências, deploy e custo operacional.

## Flashcards
- **Qual papel de FastAPI em APIs?** Usa declarações tipadas/modelos para validar dados e produzir schema OpenAPI/documentação; isso não substitui regras de negócio ou autorização.
- **Flask inclui ORM obrigatório?** Não. A aplicação escolhe persistência, validação e extensões necessárias.
- **`async def` no Flask aumenta automaticamente o número de requisições simultâneas por worker?** Não; Flask continua usando o ciclo WSGI que ocupa um worker por requisição; async pode ajudar com I/O concorrente dentro daquele ciclo.

## Práticas

### Atividade 1 — Matriz de escolha de framework
**Contexto:** compare (A) uma API interna pequena que recebe modelos JSON e precisa de schema/documentação claros; (B) um endpoint simples em aplicação já existente que usa extensões conhecidas pelo time; (C) uma aplicação web com admin, ORM, migrations e várias áreas de negócio.

**Instruções:** escolha um candidato entre FastAPI, Flask e Django/DRF para cada caso. Registre requisitos, benefício principal, uma decisão/dependência que ainda cabe à equipe, risco operacional e uma evidência a levantar antes de adotar. Pode recomendar a mesma opção para mais de um cenário, desde que justifique.

**Entrega:** tabela com três cenários, escolha e justificativa de 2–4 frases cada.

**Dica gradual:** separe necessidade de schema/API, componentes de aplicação já existentes e ferramentas integradas para dados/admin. Depois considere experiência da equipe e implantação.

**Feedback de referência:** FastAPI é candidato natural para (A) se os tipos/modelos e o contrato OpenAPI forem úteis; Flask pode atender (B) se a extensão e o padrão atual forem adequados; Django/DRF pode atender (C) pelas convenções integradas. Nenhuma resposta é automática: manutenção, segurança e ambiente podem alterar a escolha.

**Erro comum:** escolher FastAPI para qualquer API porque gera documentação ou Flask para qualquer serviço pequeno porque tem menos estrutura inicial.

### Atividade 2 — Revise uma afirmação sobre async
**Contexto:** numa revisão, alguém afirma: “Vou converter todas as rotas Flask para `async def`; assim cada requisição libera o worker e consigo executar tarefas de fundo sem Celery”. O serviço faz chamadas bloqueantes a banco e envia e-mails.

**Instruções:** marque cada parte da afirmação como correta, incorreta ou incompleta; identifique protocolo e comportamento do worker; proponha o que verificar para decidir entre Flask, FastAPI ou manter o framework; indique como fazer o envio de e-mail de forma durável e como medir a capacidade.

**Entrega:** revisão de até 200 palavras com dois riscos, um desenho alternativo e três medidas/testes de carga ou integração.

**Dica gradual:** consulte o modelo WSGI do Flask; se a biblioteca chamada não oferece I/O awaitable, `async def` não remove o bloqueio; uma view não é uma fila persistente.

**Feedback de referência:** no Flask WSGI, cada requisição continua ocupando um worker durante o ciclo; bibliotecas bloqueantes limitam o benefício; tarefas de fundo que precisam sobreviver ao fim da resposta devem ir a um worker/fila. Avalie concorrência, latência, I/O real, custo de worker e compatibilidade de extensões.

**Erro comum:** confundir concorrência de operações de I/O dentro de uma requisição com aumento automático de throughput ou execução confiável em segundo plano.

## Critério de conclusão
Justificar a escolha para cenários concretos considerando validação/schema, recursos integrados, dependências, experiência e operação; detectar limites da afirmação de que async sempre melhora escala.
