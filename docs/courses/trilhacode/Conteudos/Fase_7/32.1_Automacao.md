# 32.1 — Automação

- key: 32.1
- tipo: solo
- carater: obrigatorio
- profundidade: media
- estimativa_minutos: 180
- tags: [#infra, #qualidade]
- status: rascunho

## Objetivo
Criar um workflow de integração contínua que execute lint, build e testes em pull requests, produza sinais reproduzíveis e impeça integração quando um requisito obrigatório falhar.

## Teoria

### Microtópico 1 — Workflow, evento, job e step

GitHub Actions executa automações declaradas em arquivos YAML dentro de `.github/workflows`. Um **evento** inicia o workflow, por exemplo `pull_request` ou `push`; um **job** agrupa trabalho em um runner; e cada **step** executa uma ação ou comando. Jobs podem rodar em paralelo ou declarar `needs` para depender de outro job. A escolha do evento define quando e em qual contexto a automação roda.

Para validação de código de pull request, `pull_request` costuma ser a opção apropriada: o workflow recebe o contexto de validação do PR e o token tem permissões limitadas conforme configuração e origem do PR. `pull_request_target` executa no contexto confiável do repositório base e pode ter acesso a permissões e segredos; não faça checkout e execução do código não confiável do PR nesse contexto. Separar validação de código de tarefas privilegiadas reduz a chance de um PR executar comandos com credenciais do projeto.

Use nomes estáveis e específicos para workflows e jobs. O nome do job pode ser referenciado na configuração de checks obrigatórios; alterá-lo pode exigir atualizar essa configuração.

### Microtópico 2 — Reprodutibilidade e quality gates

Um check confiável deve produzir resultado comparável para o mesmo commit e configuração. Para Node.js, escolha uma versão compatível com o projeto, use o lockfile e instale com `npm ci`, que falha quando o lockfile e o manifesto não estão sincronizados. Execute os scripts que o próprio projeto declara para lint, build e testes. Se o repositório usa outro gerenciador, siga o lockfile correspondente (`pnpm-lock.yaml`, `yarn.lock` etc.) e o comando de instalação imutável daquela ferramenta.

Cache de dependências pode reduzir tempo, mas não deve ser necessário para que o workflow funcione corretamente. A chave deve refletir o arquivo de dependências relevante; a instalação limpa ainda precisa ser válida sem cache. Não use o cache como prova de que dependências estão atualizadas ou de que os testes são determinísticos.

Um job verde só informa que aquele job terminou com sucesso. Para transformá-lo em **quality gate**, configure a regra de proteção da branch para exigir o check correto antes do merge. Se a organização usa fila de merge, o workflow também pode precisar do evento `merge_group`. O check obrigatório precisa ser estável, ter nome inequívoco e executar em todos os contextos exigidos pela política do repositório.

### Microtópico 3 — Permissões, secrets e dependências de Actions

Defina `permissions` explicitamente e conceda somente o necessário. Um workflow que apenas lê o código geralmente precisa de `contents: read`; não habilite `write-all` por conveniência. Jobs de publicação ou implantação devem ser isolados e receber permissões adicionais somente quando forem executar essa tarefa.

Segredos devem ficar no armazenamento de secrets do GitHub, ser disponibilizados somente para o job que precisa deles e nunca ser escritos no YAML, em fixtures ou nos logs. Pull requests de forks normalmente não recebem secrets; não desenhe o fluxo supondo que eles estarão presentes. Para publicar em um serviço compatível, prefira credenciais curtas por OIDC quando essa integração estiver corretamente configurada.

Uma Action é código executado no runner. Revise quem a mantém, permissões solicitadas, versão e alterações. Tags como `@v7` são mais legíveis e facilitam atualizações, mas podem apontar para uma nova revisão; fixar o SHA completo é a opção imutável. Quando a equipe adotar SHA, registre a versão legível em comentário, use uma origem confiável e atualize o SHA por processo revisado. Não copie um SHA sem verificar que corresponde à release pretendida.

### Microtópico 4 — Leitura de falhas e limites da análise estática

CI deve dizer qual requisito falhou e preservar informação suficiente para corrigir o problema. Separe lint, build e testes em steps identificáveis, mantenha a saída do comando e evite mascarar falhas com `continue-on-error` em um gate obrigatório. Se o comando retorna código diferente de zero, o step e o job falham, a menos que a configuração altere essa regra.

Ferramentas de análise estática, como SonarQube, podem encontrar padrões suspeitos, duplicação e problemas de manutenção. Elas complementam testes e revisão; um score não prova correção, segurança ou qualidade total. Defina o que o gate mede, como tratar falsos positivos e quem mantém o limiar. Evite adicionar ferramenta ou threshold sem uma decisão de equipe e uma forma de interpretar o resultado.

Exemplo ilustrativo para projeto npm com scripts `lint`, `build` e `test:ci` já definidos. As referências de versão mostram o formato; em repositórios com exigência de Actions imutáveis, substitua cada tag por SHA completo verificado e documente a versão correspondente.

```yaml
name: CI
on:
  pull_request:
permissions:
  contents: read
concurrency:
  group: ci-${{ github.event.pull_request.number || github.ref }}
  cancel-in-progress: true
jobs:
  quality:
    name: quality
    runs-on: ubuntu-latest
    steps:
      - name: Baixar o código
        uses: actions/checkout@v7
      - name: Preparar Node.js
        uses: actions/setup-node@v7
        with:
          node-version: '24'
          cache: npm
      - name: Instalar dependências do lockfile
        run: npm ci
      - name: Verificar estilo e erros estáticos
        run: npm run lint
      - name: Gerar build
        run: npm run build
      - name: Executar testes de CI
        run: npm run test:ci
```

Adapte `node-version` à versão suportada pelo projeto e confirme que os scripts existem no `package.json`. Se não houver `test:ci`, crie um script explícito e documentado; não suponha que opções como `--run` funcionam com qualquer runner de testes. O exemplo usa uma única job para produzir um check obrigatório previsível. Separar em jobs pode acelerar feedback, desde que os checks requeridos e dependências estejam configurados com clareza.

## Resumo
- Evento inicia o workflow; jobs executam em runners e steps fazem o trabalho verificável.
- `npm ci`, versão de runtime e scripts definidos pelo repositório ajudam a reproduzir o resultado.
- Workflow verde não bloqueia merge sem regra de branch que exija o status check correto.
- Permissões mínimas, cuidado com eventos privilegiados e secrets protegem o runner.
- Actions são dependências executáveis; revisar versões e fixar SHAs aumenta a imutabilidade.
- Análise estática complementa testes e revisão, sem transformar score em prova de qualidade.

## Quiz

1. **Múltipla escolha:** qual configuração torna um check um requisito de merge em uma branch protegida?  
   A. Adicionar uma badge ao README.  
   B. Configurar a proteção da branch para exigir o status check correspondente.  
   C. Rodar o workflow apenas em `push`.  
   **Resposta esperada:** B. O workflow produz o check; a regra de proteção exige que ele passe.

2. **Diagnóstico:** o workflow está verde, mas um PR ainda pode ser integrado mesmo quando o check falha. Qual hipótese deve ser verificada primeiro?  
   **Resposta esperada:** a regra de proteção pode não exigir aquele status check, pode apontar para outro nome/contexto ou não se aplicar à branch examinada.

3. **Leitura de configuração:** o projeto usa `package-lock.json`, mas o workflow executa `npm install`. Que mudança favorece instalação consistente em CI, e qual condição ela pressupõe?  
   **Resposta esperada:** usar `npm ci`, que depende de manifesto e lockfile sincronizados e falha se houver divergência.

4. **Segurança:** um workflow acionado por `pull_request_target` faz checkout do código do PR e executa `npm install` com secrets disponíveis. Qual é o risco principal?  
   **Resposta esperada:** código não confiável pode executar no contexto privilegiado do repositório base e tentar acessar token, secrets ou recursos do runner. Separe validação de código não confiável de tarefas privilegiadas.

5. **Decisão técnica:** a equipe quer fixar Actions por SHA completo. Cite uma vantagem, um custo operacional e uma prática para tornar a referência revisável.  
   **Resposta esperada:** SHA completo torna a referência imutável; atualizações deixam de acompanhar a tag e exigem manutenção explícita; registrar a versão legível em comentário e revisar o SHA verificado torna a atualização compreensível.

## Atividades práticas

### Atividade 1 — Monte o workflow mínimo reproduzível

**Desafio:** crie um workflow de CI para um repositório Node.js que valide cada pull request.

**Passos:**
1. Inspecione `package.json`, lockfile e documentação para identificar o gerenciador, runtime compatível e scripts reais de lint, build e teste.
2. Crie `.github/workflows/ci.yml` com gatilho de PR, `contents: read`, instalação limpa pelo lockfile e passos separados para os três checks.
3. Escolha a versão da Action conforme política do projeto: tag de release ou SHA completo verificado com comentário legível.
4. Garanta que um teste ausente ou um comando inválido produza falha visível; não use `continue-on-error` nos checks requeridos.
5. Registre como executar localmente os mesmos comandos e quais limitações ainda dependem da plataforma.

**Evidências:** workflow; scripts do projeto usados; diff; saída dos comandos locais; execução do workflow no PR ou validação de sintaxe disponível no repositório.

**Verificação:** confira que o lockfile correto é usado, que todos os checks têm nomes legíveis e que o job falha quando um comando retorna erro.

**Aceite:** instalação e scripts correspondem ao projeto; permissões são explícitas e mínimas; os três checks aparecem no workflow e não há credenciais no arquivo.

### Atividade 2 — Prove o bloqueio do quality gate

**Desafio:** demonstre a diferença entre executar CI e exigir seu resultado para integrar uma mudança.

**Passos:**
1. Execute o workflow em um PR de exercício e identifique o nome/contexto exato do status check produzido.
2. Configure ou inspecione a regra de proteção da branch de exercício para exigir esse check. Se não tiver permissão de configuração, use uma captura/registro da política existente ou uma simulação documentada da configuração esperada.
3. Em um commit isolado, faça um dos checks falhar de forma deliberada e segura; confirme que o resultado fica vermelho e que a política não permite integração enquanto o check obrigatório estiver pendente/falho.
4. Restaure a mudança, execute novamente e registre o resultado verde.
5. Se o repositório usa merge queue, confira se o workflow atende também ao evento `merge_group`.

**Evidências:** nome do check; configuração ou registro da proteção; execução falha e recuperação; indicação do que foi realmente observado e do que foi apenas simulado.

**Verificação:** compare o check selecionado na política ao check produzido; não conclua que o merge está bloqueado apenas por ver um job vermelho.

**Aceite:** falha é detectada; a regra exige o status check correto; limite de permissão ou ausência de branch protegida fica declarado sem ser apresentado como bloqueio verificado.

### Atividade 3 — Faça uma revisão de segurança e manutenção

**Desafio:** revise o workflow como uma dependência executável e documente riscos e ações.

**Passos:**
1. Liste eventos, jobs, `GITHUB_TOKEN` permissions, secrets acessíveis e Actions chamadas.
2. Identifique se algum evento privilegiado executa código de PR, especialmente combinação de `pull_request_target`, checkout e comandos de instalação/build.
3. Confira origem, release e SHA das Actions conforme política do projeto; não trate versão citada no material como substituto da revisão atual.
4. Verifique se o cache usa a chave de dependências adequada e se a instalação continua correta sem cache.
5. Se Sonar ou outra análise estiver configurada, descreva o sinal que o gate verifica, limiar, falso positivo e responsável por manutenção. Se não for necessária, registre a decisão de não incluir.
6. Corrija problemas encontrados no workflow de exercício e registre cada decisão com impacto e evidência.

**Evidências:** inventário de eventos/permissões/dependências; revisão do diff; achados e correções; justificativa de análise estática e de cache.

**Verificação:** um colega consegue identificar qual código executa em cada evento, quais credenciais ficam disponíveis e como uma Action será atualizada.

**Aceite:** nenhuma credencial está hard-coded ou impressa; permissões seguem menor privilégio; código não confiável não é executado em contexto privilegiado; versões e limites estão documentados.

## Critério de conclusão
O workflow executa lint, build e testes de CI de forma reproduzível nos pull requests. O check correto é exigido pela proteção de branch (ou a limitação de acesso é registrada sem alegar bloqueio não verificado), uma falha deliberada é detectada e restaurada, e a revisão documenta eventos, permissões, secrets e dependências de Actions.
