# 32.2 — Entrega

- key: 32.2
- tipo: integrado

- profundidade: media
- estimativa_minutos: 180
- tags: [#infra]
- status: rascunho

## Objetivo
Publicar automaticamente uma versão em staging, controlar sua promoção e demonstrar um rollback reproduzível da aplicação, reconhecendo limites relacionados a dados e migrações.

## Teoria

### Microtópico 1 — Construa uma vez e identifique o artefato

Um pipeline de entrega começa com uma versão de código identificável, executa validações e produz um **artefato**: por exemplo, um pacote web ou uma imagem de container. O artefato deve ter identidade rastreável, como commit/tag e, quando aplicável, digest. A equipe consegue então responder: qual código originou esta implantação e qual saída foi publicada?

Construa o artefato depois dos checks e promova essa mesma saída entre ambientes. Não rode um build independente para staging e outro para produção sem controlar diferenças: dependências, relógio, configuração ou fontes externas podem gerar resultados distintos. Configuração específica do ambiente deve ser injetada no deploy ou em runtime, sem alterar silenciosamente o conteúdo do artefato. Secrets não devem ser embutidos no pacote cliente.

No GitHub Actions, artefatos de workflow podem passar arquivos de um job para outro e persistir após a execução. São diferentes de caches: use cache para acelerar dados regeneráveis, artefato para transportar o resultado de build/teste. O job de deploy deve baixar o artefato produzido pelo job de build da execução correspondente e registrar commit, nome/digest e ambiente.

### Microtópico 2 — Ambientes, autorização e promoção

**Staging** deve se aproximar de produção nos aspectos que importam para o comportamento — runtime, configuração relevante, integração e processo de deploy — mas usa recursos, contas, credenciais e dados isolados. Se staging não reproduz uma dependência essencial, registre essa diferença porque a aprovação não cobre o cenário ausente.

Um GitHub Environment representa um alvo como `staging` ou `production`. Um job que referencia o ambiente pode usar suas regras de proteção e secrets; o histórico de deployments ajuda a rastrear o que foi publicado. Regras podem restringir branches/tags e exigir aprovação. A disponibilidade de revisores obrigatórios e outras proteções depende do plano GitHub e da visibilidade/configuração do repositório; confirme no repositório do exercício antes de afirmar que a aprovação é aplicada.

Uma aprovação controla a passagem do job, mas não prova que o artefato é seguro ou saudável. Restringir branches de deploy, usar permissões mínimas, aprovar mudanças com contexto e manter secrets no ambiente adequado são controles complementares. Se o provedor permitir OIDC, configure confiança com condições específicas para repositório, branch ou ambiente; `id-token: write` permite solicitar o token OIDC, mas a policy no provedor é que limita quais identidades recebem credenciais temporárias.

Serializar deployments para o mesmo ambiente evita concorrência sobre recursos compartilhados. Para um job de deploy, avalie o comportamento de cancelamento: cancelar um deploy já ativo pode deixar a aplicação num estado intermediário. Use uma política deliberada e documente como uma nova versão aguarda ou substitui uma implantação pendente.

### Microtópico 3 — Verifique a saúde depois de publicar

Deploy concluído significa que a ferramenta terminou a operação; ainda é preciso confirmar que a aplicação iniciou e atende às condições esperadas. Um **health check** pode verificar disponibilidade básica e dependências críticas. Um **smoke check** percorre uma capacidade mínima importante, por exemplo abrir uma rota e consultar um endpoint essencial. Eles precisam ter timeout, critério de sucesso claro e falha visível no pipeline.

Não use apenas uma resposta HTTP 200 genérica se ela não valida a função necessária. Tampouco transforme um teste extenso e instável em gate de deploy sem entender o sinal que ele fornece. Registre URL/rota, timeout, tentativas, versão testada e resultado. Se o check falha, interrompa a promoção e decida se a versão deve ser corrigida ou revertida.

Uma promoção controlada pode seguir: construir e testar → guardar artefato → implantar em staging → executar health/smoke checks → revisar evidências → promover o mesmo artefato. Em produção, limites de tráfego, rollout gradual, janela e observabilidade dependem da plataforma e do risco. A unidade demonstra o fluxo em staging; não exige experimentar em produção.

### Microtópico 4 — Faça rollback sem confundir aplicação e dados

Rollback da aplicação normalmente significa voltar a servir uma versão anterior conhecida, seja redeployando seu artefato, seja mudando o tráfego para uma versão ainda disponível. A estratégia precisa dizer qual versão é válida, como identificá-la, quem pode disparar a reversão, quais sinais a acionam e como confirmar recuperação. Um rollback não é reproduzível se depende de encontrar manualmente arquivos ou reconstruir a versão antiga sem rastreabilidade.

Aplicação e banco têm ciclos diferentes. Voltar o código não restaura automaticamente linhas alteradas nem desfaz uma migração. Uma coluna removida, formato de dados alterado ou escrita feita apenas pelo novo código pode tornar a versão antiga incompatível. Planeje migrações compatíveis com as versões que coexistirão: um padrão comum é expandir (adicionar estrutura compatível), migrar/levar leituras e escritas para o novo formato, e só depois remover o formato antigo em outra mudança. A ordem e a reversibilidade dependem do banco e do tráfego.

Antes de mudanças destrutivas, faça backup testado e defina recuperação de dados, dono da decisão e impacto aceitável. Backup sem teste de restauração não comprova que recuperação funciona. Quando o rollback de dados não é seguro, prefira correção para frente ou procedimento de recuperação explícito, em vez de prometer reversão automática.

Exemplo conceitual de jobs: adapte scripts, artefatos e referência das Actions à aplicação. As tags ilustrativas devem ser substituídas por referências verificadas conforme a política do repositório; o job de produção foi omitido para manter o exercício em staging.

```yaml
name: Deploy staging
on:
  push:
    branches: [main]
permissions:
  contents: read
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - name: Build e validação
        run: npm ci && npm run lint && npm run build
      - name: Guardar o artefato desta versão
        uses: actions/upload-artifact@v4
        with:
          name: web-${{ github.sha }}
          path: dist/
  deploy-staging:
    needs: build
    runs-on: ubuntu-latest
    environment: staging
    concurrency:
      group: deploy-staging
      cancel-in-progress: false
    steps:
      - name: Baixar o artefato do commit
        uses: actions/download-artifact@v5
        with:
          name: web-${{ github.sha }}
          path: dist/
      - name: Implantar em staging
        run: ./scripts/deploy-staging.sh dist/
      - name: Verificar saúde
        run: ./scripts/smoke-staging.sh
```

O exemplo supõe que scripts de deploy e smoke existem, que `dist/` é a saída correta e que as Actions escolhidas são compatíveis. Não contém credenciais: o script deve receber autenticação por mecanismo configurado com privilégio mínimo, de preferência OIDC quando suportado e corretamente restrito. O exercício deve comprovar que o nome identifica o artefato da mesma execução; um nome sozinho não é atestado de integridade.

## Resumo
- Construa e teste um artefato identificável e promova a mesma saída entre ambientes.
- Staging reproduz condições relevantes, mas mantém dados e credenciais isolados.
- Environments, aprovações e concorrência organizam a autorização e o histórico de deploy.
- Health/smoke checks confirmam comportamento após implantação e interrompem promoção quando falham.
- Rollback da aplicação não reverte automaticamente dados nem schema; compatibilidade precisa ser planejada.
- Backup e estratégia de recuperação só são confiáveis quando há evidência de restauração.

## Quiz

1. **Múltipla escolha:** qual caminho preserva melhor a identidade da versão validada?  
   A. Fazer um build para staging e outro independente para produção.  
   B. Promover o mesmo artefato testado e registrar commit/digest e ambiente.  
   C. Recompilar no servidor de produção sem guardar metadados.  
   **Resposta esperada:** B. A saída testada é a mesma que segue para o próximo ambiente e pode ser rastreada.

2. **Diagnóstico:** o deploy terminou com sucesso, mas o smoke check recebe erro de conexão. O pipeline deve promover a versão mesmo assim? Explique.  
   **Resposta esperada:** não. O critério pós-deploy falhou; interromper promoção, coletar diagnóstico e decidir correção ou rollback antes de avançar.

3. **Aplicação de conceito:** por que staging não deve compartilhar credenciais e dados de produção, mesmo que replique a configuração da aplicação?  
   **Resposta esperada:** um erro, exposição ou teste destrutivo em staging poderia afetar produção; reproduzir o runtime não requer compartilhar identidade ou dados sensíveis.

4. **Análise de cenário:** após uma migração que remove uma coluna, a versão nova falha. Por que simplesmente voltar ao container anterior pode não recuperar o serviço?  
   **Resposta esperada:** o código anterior pode depender da coluna removida e as alterações de dados não são desfeitas pelo rollback do container; é necessário compatibilidade/recuperação de schema e dados.

5. **Decisão técnica:** qual evidência demonstra que um backup pode apoiar um plano de recuperação?  
   **Resposta esperada:** uma restauração ensaiada em ambiente isolado, com dados e tempo de recuperação verificados conforme o objetivo definido; a existência do arquivo de backup não basta.

## Atividades práticas

### Atividade 1 — Produza e promova um artefato

**Desafio:** monte um fluxo que constrói uma aplicação uma vez e disponibiliza a mesma saída em staging.

**Passos:**
1. Identifique o commit de origem, o comando de build e a pasta/imagem produzida.
2. Faça os checks da unidade 32.1 dependerem do build e salve o artefato com nome associado à versão/commit.
3. Configure o job de staging para baixar o artefato da execução correspondente e implantar essa saída sem executar um novo build.
4. Separe configuração e secrets do pacote; use uma conta e dados de staging isolados.
5. Registre commit, nome/digest do artefato, ambiente, horário e resultado da implantação.

**Evidências:** workflow; log de build e deploy; identificação do artefato antes/depois; configuração sem segredos; URL ou registro do ambiente de staging.

**Verificação:** compare a identidade do artefato produzido com a implantada; confirme que o workflow não recompila durante a promoção e que staging não aponta para recursos reais de produção.

**Aceite:** artefato e commit são rastreáveis; a mesma saída chega ao staging; configuração é externa e segura; o processo é reproduzível em uma nova execução.

### Atividade 2 — Detecte falha e recupere a aplicação

**Desafio:** prove que um smoke check impede promoção e pratique a volta a uma versão conhecida.

**Passos:**
1. Defina um health check e um smoke check com endpoint, timeout e resposta esperada.
2. Implante primeiro uma versão conhecida como saudável e registre o identificador.
3. Em ambiente isolado, publique uma alteração de exercício que faça o smoke check falhar sem danificar dados compartilhados.
4. Confirme que o job fica falho e que a próxima promoção não continua automaticamente.
5. Reverta para o artefato anterior registrado, execute novamente health/smoke e anote tempo e passos de recuperação.
6. Documente também a alternativa de correção para frente e quem decidiria entre corrigir e reverter.

**Evidências:** critério do check; logs do caso saudável e falho; registro de bloqueio; identidade do artefato anterior; execução de recuperação e limitações.

**Verificação:** uma falha realista é detectada pelo check, o ambiente retorna à versão anterior e a recuperação é confirmada por uma verificação funcional.

**Aceite:** critério é objetivo; falha interrompe a promoção; rollback usa versão rastreada e é reproduzível; o ambiente fica saudável após a operação.

### Atividade 3 — Planeje compatibilidade e restauração

**Desafio:** mostre como uma mudança de schema e dados convive com deploy e rollback.

**Passos:**
1. Escolha uma alteração fictícia ou de banco isolado, como trocar uma coluna de nome ou formato.
2. Desenhe estados do banco e versões da aplicação antes, durante e depois da transição.
3. Identifique em cada passo qual versão consegue ler e escrever; proponha expansão compatível, migração de dados e remoção posterior, quando aplicável.
4. Marque quais operações não são reversíveis automaticamente e proponha correção para frente, backup/restauração ou procedimento manual seguro.
5. Faça uma restauração de ensaio se o ambiente permitir; sem execução, registre como proposta e indique que ainda não foi comprovada.
6. Registre sinais de decisão, responsáveis e condição para parar ou reverter a implantação.

**Evidências:** sequência de migração; matriz versão × schema; plano de rollback/forward fix; registro de backup e restauração de ensaio ou lacuna explícita; critérios de decisão.

**Verificação:** a versão anterior continua compatível durante os passos em que rollback é prometido; os dados necessários não dependem de uma operação destrutiva já executada.

**Aceite:** compatibilidade e limites são explícitos; nenhuma reversão de dados é alegada sem mecanismo; backup tem restauração ensaiada ou permanece identificado como risco não verificado.

## Critério de conclusão
O pipeline constrói um artefato rastreável uma vez e o implanta em staging isolado. Um smoke check pós-deploy bloqueia avanço quando falha; a pessoa demonstra rollback da aplicação para versão conhecida e explica, com uma sequência de migração, por que dados e schema exigem tratamento próprio. Evidências distinguem o que foi executado do que foi apenas planejado.
